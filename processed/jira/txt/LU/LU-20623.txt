--- Comment (adilger, Fri, 11 Sep 2026 20:42:58 +0000) ---
It looks like I might have a root cause for this issue.  In patch https://review.whamcloud.com/61962 ("LU-12187 llapi: EC layout creation support") landed on 2026-03-31 it added a check in llapi_layout_comp_del() that a data component which has a linked parity component cannot be deleted:

+       if (comp->llc_flags & LCME_FL_PARITY) {
[snip]
+       } else {
+               /* A data comp that is protected by a parity comp can't be
+                * deleted until the parity comp is deleted.
+                */
+               if (comp->llc_mirror_link_id != LLAPI_MIRROR_LINK_NONE) {
+                       errno = EINVAL;
+                       return -1;
+               }
+       }

However, in LU-20718 we see that the lcme_timestamp is not zeroed properly and has random garbage written into it (for a yet unknown reason) in non-EC/non-NOSYNC files.  This causes llc_mirror_link_id to randomly be non-zero and the llapi_layout_comp_del() check fails.

Fixing the source of the garbage lcme_timestamp field is the purview of LU-20718, but since those bad timestamps are known to date back to at least 2021 (according to my home filesysem), this is a real interop issue that needs to be fixed.

It looks like the best way to handle this is for the llapi_layout_comp_del() check to be conditional on there actually being an EC component with the matching llc_mirror_link_id, or it will cause 2.18+ clients to be randomly unable to delete existing mirror components with garbage lcme_timestamps, regardless of whether EC is enabled or not.
