--- Description ---
sanity test_154ea fails because its EXIT cleanup attempts to remove unrelated test directories. The readdir assertion itself did not fail.

In change 69468 patchset 3, enforced RHEL 8.10 ldiskfs DNE testing reported:

rm: cannot remove '/mnt/lustre/d125.sanity': Input/output error

rm: cannot remove '/mnt/lustre/d22.sanity': Input/output error

test_154ea returned 1

FAIL 154ea (51s)

Session: https://testing.whamcloud.com/test_sessions/469f4a87-437f-47fb-add3-876720c62d7f

Test set: https://testing.whamcloud.com/test_sets/c0e8f6e0-4382-4d3e-9421-1419b06c9178

The pre-existing test in lustre/tests/sanity.sh registers:

stack_trap "rm -rf $MOUNT/[abcdeg]*" EXIT

This includes every d*.sanity directory, rather than only the long filenames created by this test. The subshell cleanup returns nonzero and the test framework reports test_154ea returned 1.

The same cleanup defect predates this patch. On unrelated change 64875/16, ldiskfs DNE testing on 2026-07-15 reported:

rm: cannot remove '/mnt/lustre/d60g.sanity': Directory not empty

test_154ea returned 1

FAIL 154ea (57s)

https://testing.whamcloud.com/test_sets/7c51fabb-e1dd-4738-8517-cfbf99a21a81

Change 64875/17 also had the same cleanup failure on ZFS:

https://testing.whamcloud.com/test_sets/16cd22aa-e1ab-4ac8-8062-ebf294f60825

The broad cleanup has been present since commit 609fc54142 (LU-18138, 2024-08-13), which is on the target branch. Change 69468 only reserves an unused connection flag, adds its display name, and wire checks. It changes neither this test nor directory removal behavior. There are no unmerged parents in this checkout.

Rainshadow found no linked tickets or candidates. JIRA searches for 154ea, the affected directory names, and cleanup glob behavior found no covering ticket. LU-18138 concerns .lustre being returned by readdir; LU-7344 concerns connection loss during test_154g, neither describes this cleanup defect.

Restrict cleanup to the files created by test_154ea. The underlying I/O errors on unrelated directories are not diagnosed by this report. No guest reproduction was needed for the cleanup defect, which is explicit in the code and both sets of logs.
