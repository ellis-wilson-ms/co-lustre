--- Description ---
conf-sanity test_33c builds a second filesystem on fs2mds/fs2ost devices, exactly as test_33a does, but does not carry test_33a's guard against a mixed loopback/real-device configuration:

        if [ -z "$fs2ost_DEV" -o -z "$fs2mds_DEV" ]; then
                local dev=${SINGLEMDS}_dev
                local MDSDEV=${!dev}

                is_blkdev $SINGLEMDS $MDSDEV &&
                        skip_env "mixed loopback and real device not working"
        fi

test_33c was added by LU-17034 ("quota: lqeg_arr memmory corruption", https://review.whamcloud.com/c/fs/lustre-release/+/52094) as a reproducer, structurally copied from test_33a. It keeps test_33a's

        [ -n "$ost1_HOST" ] && fs2ost_HOST=$ost1_HOST

line, immediately above where the guard sits in test_33a, but not the guard itself. The check appears never to have been included rather than removed later.

Why it matters more in 33c than elsewhere

On a cluster whose main targets are real block devices and which sets no fs2mds_DEV/fs2ost_DEV, test_33a skips as designed. test_33c proceeds, and two further differences turn that into an indefinite hang rather than a failure:

	test_33a formats its second filesystem under its own name (FSNAME2=test-$testnum). test_33c uses --fsname=${FSNAME} with no explicit MDT index, so its second MDT lands on index 0 of the live filesystem.

	Neither start fs2mds nor start fs2ost is checked, so the collision is swallowed and the test carries on to mount_client.

Observed on 2.17.56, ldiskfs, 4 servers / 2 clients, separate MGS, MDSCOUNT=2, OSTCOUNT=4, real block devices for all main targets and no fs2* devices configured:

LustreError: (tgt_mount.c:2611:server_fill_super()) Unable to start targets: -98
LustreError: (tgt_mount.c:2129:server_put_super()) no obd lustre1-MDT0000
LustreError: (tgt_mount.c:116:server_deregister_mount()) lustre1-MDT0000 not registered
Lustre: server umount lustre1-MDT0000 complete
LustreError: (super25.c:177:lustre_fill_super()) llite: Unable to mount : rc = -98
Lustre: lustre1-OST07c6: new disk, initializing

fs2mds fails to start with -98 (EADDRINUSE) against the running lustre1-MDT0000. After that error path the node serves no MDT at all:

# findmnt -t lustre
/var/mnt/lustre/client-mgs     /dev/mapper/mgs_flakey     lustre ... svname=MGS
/var/mnt/lustre/client-fs2ost  /dev/mapper/fs2ost_flakey  lustre ... svname=lustre1-OST07c6

The subsequent mount_client then blocks indefinitely:

task:mount.lustre    state:S
  ptlrpc_set_wait+0x234/0x640 [ptlrpc]
  ptlrpc_queue_wait+0x84/0x258 [ptlrpc]
  mdc_statfs+0xe0/0x428 [mdc]
  obd_statfs+0x250/0x600 [lmv]
  lmv_statfs+0x1e8/0x648 [lmv]
  client_common_fill_super+0x43c/0x2908 [lustre]
  ll_fill_super+0x918/0xe58 [lustre]

The run does not recover. In our CI this consumed roughly 3.5 hours of a 4 hour budget on two separate occasions, each time stopping the suite at the same point and costing the ~80 tests that would have followed.

Suggested fix

Add test_33a's guard to test_33c. Checking the two start calls would also convert any residual collision into a clear failure rather than a hang.

Related: same guard missing elsewhere, lower severity

A scan of conf-sanity.sh finds twelve tests that build a second filesystem on fs2* devices. Seven carry the guard (21e, 24a, 24b, 33a, 36, 43b, 77). Besides 33c, three do not: test_74, test_157a and test_157b. All three use their own filesystem name (FSNAME2 / fs$RANDOM) and check every add and start with || error, so in an unsupported environment they fail rather than hang. They may still be worth guarding for a clean skip, but they do not have 33c's failure mode. (test_32newtarball also lacks it and is a manual helper with no run_test, so it never runs in a suite.)
