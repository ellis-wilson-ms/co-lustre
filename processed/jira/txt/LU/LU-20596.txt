--- Comment (hornc, Sat, 15 Aug 2026 17:13:26 +0000) ---
analysis from claude

Root cause

Test_233 adds drop rules with rate 2. A rate 2 rule has a special case in

lnet_drop_rule_add() (lnet/lnet/net_fault.c:212). The rule always drops the

first message that it matches. Commit c892edc14a ("LU-18555 lnet: Track

successful and failed resends") added this special case.

After the first drop, drop_rule_match() (net_fault.c:499) drops exactly 1

message in each pair. The drop position in each later pair is random.

The ping gets 3 attempts, because lnet_retry_count is 2. The test fails only

when all 3 attempts hit a drop slot. Two facts make this impossible on one

rule alone:

	Drops alternate. Two attempts in a row on one rule never both drop.

	A resend keeps the source NI, because the ping pins it with --source. The

peer NI on the same net stays the same. All 3 attempts use one rule.

Therefore a foreign GET must consume a slot in that same rule between the

attempts. The foreign GET shifts the parity of the drop schedule, and the

resend then lands on a drop slot.

LNet arms such a GET at the moment of the first drop. The kernel adds the

peer NI to the recovery queue. The recovery ping then goes to the same source

and destination pair as the test ping:

 

{{lnet_health_check() health check: ...198@tcp->...177@tcp: GET: REMOTE_DROPPED

lnet_peer_ni_add_to_recoveryq_locked() 172.16.100.177@tcp added to recovery

    queue. ping count: 0 next ping: 28015 last alive: 28014 health: 900}}

The local_* statuses do not have this problem. A local failure puts the

local NI in recovery, and the local recovery ping goes to the NI itself. That

GET matches the self rules, not the rule that the test ping uses.

Evidence from the VM cluster

I reproduced the drop rule accounting on the co3 cluster with 2 nodes and the

same tunables as test_233. Results:

Run
Result

30 clean iterations
30 pass, 0 fail

15 iterations, peer NI health lowered
15 pass, 0 fail

40 iterations, concurrent ping traffic
40 pass, 0 fail

Every pass shows the same trace. The first send drops, the resend keeps the

same source and destination, and the resend passes as message 2 of the pair:

 

{{lnet_send_error_simulation() src ...198@tcp->dst ...177@tcp: GET simulate

    health error: REMOTE_DROPPED

lnet_resend_pending_msgs_locked() resending ...198@tcp->...177@tcp: GET

    recovery 0 try# 1

drop_rule_match() Drop Rule ...198@tcp->...177@tcp: next drop: 3}}

The window between the drop and the resend is microseconds, because one

monitor thread pass does both. The recovery ping is due 1 s later. My VM

cluster is quiet, so the recovery ping never landed in the window. The CI

node hit the window once.

Confidence: the arithmetic and the code path are proven. The identity of the

foreign GET in the CI run is an inference. The CI debug logs are not in the

Maloo artifact bundle, so I cannot name the message.
