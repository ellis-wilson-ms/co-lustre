--- Description ---
Attached script can be used to re-create the issue. Even after the soft limit is reached and the client knows that the soft limit has expired, the client can still perform small writes and continue writing until the hard limit is reached. This appears to be a flaw in the code (please let me know if this understanding is correct).

While debugging the issue, I observed that osc_quota_chkdq() returns EDQUOTA because cl_quota_exceeded_ids is set, and "cl_quota_exceeded_ids" flag set happens during the last failed write transaction. After this point, my assumption was that any further writes would be blocked. However, writes are still allowed because the client relies on the server to fail the write. Since the write is queued and sync is called. In the case of small I/O the write may not reach the server (I still need to verify this). In contrast, when the write size matches the cache size, the write does reach the server and an EDQUOTA error is returned.

I have included the return codes for 1 KB and 1 MB writes, which explain why the 1 MB write fails (the cache size is set to 1 MB).

My question is: should we use the return value of osc_quota_chkdq() to prevent the I/O from being queued? Or does this require more consideration? I understand that once the client detects an expired quota, we should not allow further writes, but we still need to allow deletes so that pages can be released. I would appreciate input on this before proposing a fix and later realizing that a change was not required.

--- Comment (sergey, Tue, 24 Feb 2026 12:57:58 +0000) ---
Hi rajeevm , 

I have a couple comments to your reproducer that may cause undefined results. You are enabling user and group quotas only for OST0001. At the same time files striping doesn't suspect that stripes are located only at the OST0001. If you look at sanity-quota.sh, we usually define the index of the OST: lfs setstripe -i 0 -c 1 .... This could be the reason of the problem you see, as a half or even quarter of test files stripes located at different OSTs. Quotas on another OSTs may be not enabled, is this the case?

Even if quotas are enabled on all OSTs, appropriate OSC doesn't know about the -EDQUOT before sending BRW to the OST even if the other OSC already got an -EDQUOT. I.e. if the user reached it's quota limits at the OST0, it is still able to write at the OST1 until it gets an EDQUOT.

I haven't started your script, but I  have a question. Why do you need Pool Quotas at all? This makes harder to understand the root of the problem if it exists. I mean if the problem exists at the client side and you are going to fix the client side code, it touches the basic quotas mechanism and should not directly relate to Pool Quotas.

My question is: should we use the return value of osc_quota_chkdq() to prevent the I/O from being queued? Or does this require more consideration? I understand that once the client detects an expired quota, we should not allow further writes, but we still need to allow deletes so that pages can be released.

osc_quota_chkdq returned value is used to switch async IO to sync IO. Even if a client got -EDQUOT, all pages already added to the cache must be sent and written at the OSDs. Since the IO swiched to sync mode, it continues to send BRW to the server, but now with no guarantee it will be written. If there is still no quotas at the OSD(OST or MDT), -EDQUOT is returned. If quotas present, the data will be written, a client will get 0(success) and switch back to async IO mode.

It prevents continued buffered/cached writes once quota has already been exceeded on one OST.

It reduces the timing gap caused by asynchronous per-OST quota flag propagation.

when user space is freed by delete/truncate activity, or

when corresponding user quota-exceeded flags are cleared (usr_bits=0) consistently.

Quota EDQUOT / overshoot analysis

When a client issues a write, the OSC first checks the cl_quota_exceeded_ids map for the file's owner ID (uid/gid/projid):

If the flag is not set: the write proceeds to the OST. If the OST (QSD) has enough already-granted quota space, the write completes locally without contacting the QMT. If the OST is short on grant, the QSD sends a DQACQ request to the QMT. Quota is handed out in units of qunit (for block/data quota the minimum qunit is one max-BRW, ~4 MB, not 1 KB). If the QMT can satisfy at least one qunit, the OST gets the grant and the write succeeds.

If the OST cannot get more grant (user is within less than one qunit of the hard limit), the OST returns a reply that sets OBD_MD_FLUSRQUOTA, which causes the client to set cl_quota_exceeded_ids for that ID.

On the next write, because the flag is now set, the client refuses to buffer the page into async cache and switches that write to sync mode, sending it straight to the server for the final verdict. If no grant is available, the write fails with EDQUOT (surfaced to the app as EDQUOT/ENOSPC).

This is the mechanism that contains over-limit writes: the overshoot is bounded and not unbounded. The amount a user can exceed the hard limit is roughly proportional to the grant the OST(s) were already holding (up to about one qunit per active OST), so a small overshoot beyond the hard limit is expected behavior, not a bug.

On the client system observation: I was only able to overshoot by ~2 MB, which is itself not guaranteed and varies with how much grant each OST held at the time. To characterize this precisely on the customer system, we need to collect grant/qunit state during the run (per-OSC cur_grant_bytes, per-OST quota usage from lfs quota -v, and qunit values) to confirm what grant was outstanding when the writes stopped.

When I was able to write ~2mb OVER THE HARD LIMIT it was due to lowering the the quota limit which left ostensibly with extra grant.

Summary: Quota is working as designed. Writes can overshoot the hard limit by a small amount determined by the grant the OST already held; the overshoot is always bounded and self-correcting.

Hence I am going to close this defect as working as design
