--- Comment (bzzz, Wed, 3 Apr 2024 14:47:47 +0000) ---
layout refresh is a two-step process: 1) release current configuration with all objects 2) re-initialize a new one. the problem is that group locks are referenced by the objects used in the current configuration, meaning we can't release them technically.

but I guess the most interesting question is what kind of layout changes are acceptable while a grouplock is taken? I guess one more (stale) component should be OK, but what if it changes the components involved in migration itself? say, it just marks the original component stale?

--- Comment (JIRAUSER21604, Wed, 2 Sep 2026 17:58:23 +0000) ---
Group lock ioctl ignores O_NONBLOCK (same blocking site as this ticket)       

                                                                                

While reproducing this deadlock, I hit a separable defect: LL_IOC_GROUP_LOCK cannot honour O_NONBLOCK.

 

In cl_get_grouplock() the nonblock argument is only consumed at the enqueue:

enqflags = CEF_MUST | (nonblock ? CEF_NONBLOCK : 0);

...

rc = cl_lock_request(env, io, lock);

  

but cl_io_init(env, io, CIT_MISC, io->ci_obj) runs earlier in the same function, and that is where vvp_io_init() > ll_layout_refresh() blocks in lov_layout_wait(). The blocking step sits above the only line the flag affects, so ll_get_grouplock() passing (file>f_flags & O_NONBLOCK) cannot prevent it — a non-blocking group-lock request can block indefinitely.

Observed on 2.17.57: the ioctl on an O_NONBLOCK fd sat in lov_layout_wait() for 490s+ in TASK_IDLE (ps shows I, not D) and was not reapable — SIGKILL and timeout(1) both ineffective; only a reboot cleared it.

  

Same stack as this ticket, different caller:

 

lov_layout_wait > lov_conf_set -> cl_conf_set -> ll_layout_conf -> ll_layout_lock_set -> ll_layout_refresh -> vvp_io_init > __cl_io_init -> cl_get_grouplock -> ll_get_grouplock -> ll_file_ioctl

 

This looks separable from the design question in the 2024-04-03 comment:

whatever is decided about which layout changes are acceptable while a grouplock is held, a non-blocking request should arguably fail rather than wait.

--- Comment (JIRAUSER21604, Wed, 2 Sep 2026 18:01:40 +0000) ---
This deadlocks with a single process and no external layout change

  

  The reproducer on 54343 (sanity-flr.sh test_213) needs two mounts and a second

  party: one process holds the grouplock, $MOUNT2 does setstripe 

  --component-add, then the holder is poked to refresh. The deadlock doesn't

  need any of that — one process, two fds, one mount, nothing else touching the

  file:

  lfs setstripe -N -c 1 -N -c 1 /mnt/lustre/f     /* any mirrored file */

  fd1 = open(f, O_RDWR|O_CREAT);    ioctl(fd1, LL_IOC_GROUP_LOCK, 1234);  /* ok 

  */

  fd2 = open(f, O_RDWR);            ioctl(fd2, LL_IOC_GROUP_LOCK, 1234);  /* 

  never returns */

 

  The layout change is self-inflicted. ll_get_grouplock() raises

  LAYOUT_INTENT_WRITE over 0..EOF before taking the lock; on a mirrored file

  that hits the lov_flr_state(obj) == LCM_FL_RDONLY case in lov_io.c which sets

  ci_need_write_intent, so the state flips ro -> wp — and that transition is a

  layout change. Measured across the first ioctl on a freshly created file:

  lcm_flags ro -> wp, lcm_layout_gen -> 4. The second acquisition then refreshes

  into lov_layout_wait(), waiting on the lo_active_ios pin its own first group

  lock holds.

  So the pre-instantiation that exists to keep layouts stable during a group

  lock is, on a mirrored file, the thing that closes the cycle.

  Not claiming mirroring is required — test_213 shows a plain composite plus an

  external change is enough, so mirroring is one way to supply the trigger, not

  a precondition. The point is only that no second party is needed. A plain PFL

  file with no layout changer present does not reproduce, which is consistent.

 

  Given this ticket is filed Minor: a single-process, single-mount reproducer

  that wedges in about a second and leaves an unkillable TASK_IDLE task might be

  worth re-rating.
