--- Comment (adilger, Thu, 11 Jun 2026 00:57:29 +0000) ---
When I saw the 66536 patch I was going to comment that it would be better to optimize the real data path with zero-copy receive, but I now see that is the end goal for this ticket, and presumably 66536 is only for showing the ideal receive performance with zero copy.

It should be possible with Lustre to have "perfect" zero copy receive for bulk data transfer, since both sides know the size and alignment of the data pages in advance.  That would require MTU > 4096 or > 8192 in order to allow full-page receives on the target, but in theory it should also be possible with multiple MTU=1500 receives into a single page that is tiling the buffer contiguously.  In the past, there was a "hack" done by LLNL to set MTU=(8192 + LNet header + SockLND header  + TCP header + IP header) so that the receive data would "coincidentally" be page aligned, but that was fragile and not efficient in practice.  AFAIK the kernel now allows allocating network receive buffers with the headers at a "negative" offset from the start of the page so that the received data is properly aligned.

--- Comment (JIRAUSER19463, Thu, 11 Jun 2026 17:01:09 +0000) ---
True data copy for real workload always relies on the NIC hardware to be able to recognize the protocol and strip the header, including proto header like TCP header and options, application header like LNet. This is beyond the scope of this ticket.

This ticket addresses the zero copy issue by discarding the data on the receiving path, therefore, it can get similar throughput from iperf3. I used to get a lot of complaints like lnet_selftets is less performant so this work will probably stop it.
