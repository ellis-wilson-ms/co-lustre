--- Description ---
When using nodemap with the deny_unknown=1 option enabled, an unauthorized user (not mapped in the nodemap) is able to stat a file after an authorized user has performed a stat operation on the same file. This bypasses the intended access control and represents a potential security vulnerability. The issue is cache dependent and permission is denied again once caches are cleared.

Potential root cause:

Metadata caching on the client side may not be properly invalidated when deny_unknown is enabled, allowing cached stat information to be accessed by unauthorized users.

--- Comment (zam, Fri, 26 Jun 2026 07:34:34 +0000) ---
The opencache feature makes possible for a not mapped user to read file contents:

just an attempt to read a file after a mapped user has read it:

[root@rocky98 tests]# su rocky -c "cat  /mnt/lustre/foodir/file-0" ; su foouser -c "cat  /mnt/lustre/foodir/file-0"
top secret
cat: /mnt/lustre/foodir/file-0: Permission denied
[root@rocky98 tests]#

and the same after getting an open lock:

[root@rocky98 tests]# su rocky -c "for i in {0..999}; do cat  /mnt/lustre/foodir/file-0 > /dev/null; done" ; su foouser -c "cat  /mnt/lustre/foodir/file-0"
top secret
[root@rocky98 tests]#

the issue is not reproducible after disabling opencache:

[root@rocky98 tests]# umount -f /mnt/lustre
[root@rocky98 tests]# mount -t lustre 192.168.122.127@tcp:/lustre /mnt/lustre
[root@rocky98 tests]# ../utils/lctl set_param llite.*.opencache_threshold_count=off
llite.lustre-ffff8b38c4fa9800.opencache_threshold_count=off
[root@rocky98 tests]# su rocky -c "for i in {0..999}; do cat  /mnt/lustre/foodir/file-0 > /dev/null; done" ; su foouser -c "cat  /mnt/lustre/foodir/file-0"
cat: /mnt/lustre/foodir/file-0: Permission denied
[root@rocky98 tests]#
