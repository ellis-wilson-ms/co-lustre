--- Description ---
For various format strings which can be handed to a command like "lfs find $path --printf $format_string", the handling of directive width parsing is incorrect or inconsistent, either between validate_printf_str() and parse_format_width(), or with GNU find.

Example erroneous cases:

"% -6p" // '-' not detected, '-6' parsed as negative number, incidentally is treated the same as if the width was parsed as '1023'
"%+6p" // validate_printf_str() prints warning however parse_format_width() accepts it normally
"% 6p" // validate_printf_str() prints warning however parse_format_width() accepts it normally

Beyond those two cases which definitely should be fixed, there are other inconsistencies with how GNU find handles width parameters:

	The # char is not accepted

	The + char is only accepted when immediately followed by a digit

	Space with no width digit after ("% p") is rejected

	Precision, i.e. "%.5p" not implemented (I think leaving this out is fine, doesn't seem very useful)

	parse_format_width() accepts a greater range of whitespace characters (space, \t, \n, \r, \v, \f) than GNU find (space)

I think the simplest solution here is to reject whitespace / +. It doesn't seem necessary to have full parity with GNU find, as much as a strict implementation of the needed subset.
