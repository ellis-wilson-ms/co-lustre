The customer therefore suspects that the issue originates from PID 926158 and requested that we investigate it from the Lustre/PCC perspective.

The preceding commands establish the following dependency chain:                

  PID 926526 (PCC read)                                                         

      has executed pcc_io_init()                                                

      pcci_active_ios is therefore 1                                            

      has not yet executed pcc_io_fini()                                        

      waits for a READ lock on mmap_sem ff2171f5700dc270                             

                                  v                                             

  PID 926158 (PCC mmap)                                                         

      owns mmap_sem ff2171f5700dc270                                            

      sleeps in pcc_mmap_mapping_set()                                          

      waits for pcci_active_ios to become 0                                     

                                  v                                             

  PID 926526 must finish its PCC I/O and execute pcc_io_fini()                  

In compact form:                                                                

  PID 926526                                                                    

      -> waits for mmap_sem                                                     

      -> mmap_sem is owned by PID 926158                                        

      -> PID 926158 waits for pcci_active_ios == 0                              

      -> the outstanding PCC read is PID 926526, after pcc_io_init() and before 

         pcc_io_fini()                                                          

      -> PID 926526 cannot reach pcc_io_fini() because it is waiting for the    

         mmap_sem held by PID 926158                                            

      -> back to PID 926526                                                     

Therefore the vmcore evidence is consistent with this circular wait:            

  PID 926526 -> mmap_sem -> PID 926158 -> pcci_active_ios -> PID 926526.

More precisely, PID 926526 waits for PID 926158 to release mmap_sem, while      

PID 926158 waits for PID 926526's PCC I/O to complete so that                   

pcci_active_ios changes from 1 to 0.  This conclusion is limited to the facts   

demonstrated by the crash output and disassembly reproduced above.
