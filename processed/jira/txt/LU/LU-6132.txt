--- Environment ---
RHEL 6.5 with MLNX_OFED 2.3 and ConnectX3/ConnectX3 Pro/ConnectIB  HW (but I'm guessing is reproducible with any OS and any OFED/upstream kernel).

--- Description ---
Unloading IB drivers results in hung task message and driver unloading is stuck forever.

Steps to reproduce:

1) Have a lustre mount to server

2) On server do /etc/init.d/openibd stop

3) openibd script is stuck

--- Comment (yanb, Tue, 20 Jan 2015 08:41:23 +0000) ---
One scenario would be reboot. Also, device removal event will be received upon PCI reset to device or unbind/hotplug.

From my experience on other projects, there are two changes that need to be done to support this:

1) Be able to differentiate between CM IDs of the listener and of connections

2) If CM ID is of a connection, do the same handling as disconnected event. In case of listener, just destroy the CM ID

--- Comment (isaac, Mon, 2 Mar 2015 19:55:43 +0000) ---
I think the shutdown scripts should be fixed to honor the correct dependency - i.e. shutdown the IB users (e.g. LNet) before any attempts to shutdown any part of IB. As to LNet support of device removal, if there's a valid use case for that we should certainly support it. But I'd tend to say incorrect shutdown order isn't a valid use case. --- Comment (yanb, Wed, 4 Mar 2015 12:55:45 +0000) ---
Other use cases where you may get device removal event are:

1) Card/FW failure and reset issued on the card

2) VPI - changing in runtime between ethernet and IB port type

3) Unloading driver perhaps for maintenance

4) Hotplug of card (as well as VF in SRIOV case)

--- Comment (dmiter, Wed, 18 Jan 2017 16:49:14 +0000) ---
This happens when you have Lustre share mounted but try to unload OFED drivers. The shutdown sequence should be following:

	umount /mnt/lustre

	lustre_rmmod

	unload OFED drivers

We can make first 2 steps in our shutdown script but cannot guarantee that OFED drivers will not be unloaded first.

--- Comment (adilger, Thu, 19 Jan 2017 22:29:52 +0000) ---
I don't see why the client would need to be evicted, per-se if the IB interface is stopped.  In theory, if the client has some other form of communication with the server (e.g. TCP or OPA) it could continue to work after the IB interface is stopped.  Handling that cleanly would definitely need some development work, and is best left until after the LNet Multi-Rail code is landed, since I suspect it will need to deal with that situation in any case.

One simple option for handling this in the short term is adding an /sbin/umount.lustre script which tries lustre_rmmod to unload the modules, but fails silently if the modules are in use (i.e. another filesystem is mounted).  That would drop the LNet references and disconnect the client, allowing the IB modules to be unloaded.  However, this depends on the client unmount happening before the IB modules are cleaned up.  The other option is a systemd script (see patch http://review.whamcloud.com/21457 "LU-8384 scripts: Add scripts to systemd for EL7").

--- Comment (hornc, Mon, 12 Oct 2026 19:47:48 +0000) ---
The fault is still present on master (2.17.59). A VF reset or rdma link delete with LNet up blocks ib_unregister_device() in cma_process_remove(). On ddn 2.16 branch, lustre_rmmod then hangs in kiblnd_shutdown() with "waiting for 1 peers to disconnect". The node needs a hard reset.

Cause: kiblnd_cm_callback() ignores RDMA_CM_EVENT_DEVICE_REMOVAL. After that event, rdma_cm sends no DISCONNECTED, so each conn keeps its CM ref and its cm_id. cma_process_remove() waits for every cm_id on the device.

A 4-patch series will add device-removal support to o2iblnd:

	o2iblnd: release the pools of an old HCA. A failed pool that is in use now goes when its last node returns, not at net shutdown.

	o2iblnd: drop the CM conn ref one time. The CM ref drop is now idempotent. A passive connreq now gets the connreq timeout.

	o2iblnd: fix races with the failover thread. The dev destroy and the net shutdown wait for the failover thread. Each dev holds a netns ref.

	o2iblnd: release and rebuild an HCA on device removal. ko2iblnd registers an ib_client. The RDMA core calls its remove() before rdma_cm sends DEVICE_REMOVAL. The callback closes the conns and releases each hdev on the device. The add() callback rebuilds the hdev when the device returns.

VM result, Soft-RoCE, 2 nodes, rdma link delete then rdma link add:

Tree
Delete
LNet after add
lustre_rmmod

master without the series
blocked for more than 60 s
not tested
hangs (b_es7_0)

master with the series
1 s, 6 of 6 cycles
lctl ping OK in 0 s
clean

We have not tested a real VF reset on hardware yet.

Outstanding: push the series to Gerrit.
