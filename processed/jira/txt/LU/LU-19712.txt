--- Description ---
Admins or users would want to pin files to a given pool, as a way of staging files before use, or to prevent any mirroring or purging of files to/from a given pool. One way to accomplish this would be to designate an xattr that external tools would check for and honor.

A pin xattr, lustre.pin, has already been introduced for PCC purpose. It currently supports PCC info, and is only used by PCC for now, but the spec already plans to include other information such as pool names in this xattr. The content of this xattr is in JSON format, and is like:

lustre.pin=[{"hsm":2},{"hsm":3},{"pool":"ssd"}]

If a pool is specified (multiple are possible), we would consider the file is pinned to this pool, and a mirror stored on this pool cannot be deleted from that pool.  For lfs mirror extend, it should be possible to create new mirrors of the file on other pools, but lfs mirror split/delete should not be able to remove the mirror from a pinned pool.

We could also introduce the "exclude pool" property, so that the file is pinned exclusively to this pool. This means lfs mirror extend could not create a mirror on a different pool in that case, though it should be possible to create another mirror on the same pool.

That would give us the following possible values as examples:

# pin file to two different pools
lustre.pin="pool": ["ssd","hdd"]

or

# pin file to one pool, deny creation on any other pools
lustre.pin=pool: ["ssd", "^any"]

"ssd" and "^any" pool would be mutually exclusive given their meaning.

# deny creation on specific pools
lustre.pin=pool: ["^hdd", "^archive"]

Using this already existing xattr lustre.pin provides the ability to control which GIDs can pin/unpin files, as this feature was already added for PCC by patch "LU-10499 pcc: tunable GID to pin/unpin files". This patch adds a tunable "mdt.*.enable_pin_gid" that controls the GID to pin/unpin files. Default is gid=0, so it is limited to root, gid=-1 means any user can pin/unpin, and gid= is used to allow a specific GID (e.g. wheel).

To support the new pool pin/unpin capability on Lustre, we would need to extend the llapi with dedicated functions, e.g:

int llapi_pool_pin_fd(int fd, char* pool);
int llapi_pool_pin_file(const char *path, char* pool);
int llapi_pool_pin_fid(const char *lustre_dir, const struct lu_fid *fid, char* pool);
int llapi_pool_unpin_file(const char *path, char* pool);
bool llapi_pool_is_pinned_fd(int fd, char* pool);
bool llapi_pool_is_pinned_file(const char *path, char* pool);
bool llapi_pool_is_pinned_fid(const char *lustre_dir, const struct lu_fid *fid, char* pool);

These could be inspired from their PCC equivalents, see all the llapi_pcc_*pin* functions.

We would also need dedicated lfs commands, such as lfs pool pin/unpin/get. pin/unpin would take a path or FID and optionally a pool name. If no pool is specified, we would internally pin to the pool that is configured in the file layout as the primary mirror.

Apart from the userspace side of things, it is important for the lustre.pin xattr to be automatically inherited for files and subdirectories when set on the parent directory. That would allow setting it for instance once at the project directory or group directory level, and then automatically benefit from it for all new files and directories created in there. We do inherit layout already, which is basically an xattr we process and then write, so we would have to implement a similar behavior for the lustre.pin xattr.

--- Comment (sebastien, Wed, 20 May 2026 13:31:50 +0000) ---
Yes we should modify the commands that handle mirrors so that they can interpret the pool pin information. I can think of:

	lfs mirror extend

	lfs mirror split

	lfs mirror create

	lfs mirror delete

	lfs migrate

So these commands would return an error and do nothing if the pool pin info contradicts the requested action.

But for scripts that do massive mirror operations, this behavior might not be optimal, as it implies the Lustre command internally fetches an xattr for each file, and then takes an educated decision. One way to avoid that could be to introduce a new semantic for the pool pin attribute, such as [\{defaultpool: \\}]. When defaultpool (or whatever better name) is specified on a directory, all files in this directory (let's consider for now we do not go beyond the first level in the tree hierarchy) would implicitly apply the pool pinning of the parent. That would allow the aforementioned scripts to read only the pin xattr of the parent with lfs pool pin_info, and decide not to call mirror primitives for the files in this directory if it has a default pool that contradicts the desired mirror action.

In any case, defaultpool would be a second step optimization, and at first we need to update the lfs commands listed above to interpret the already defined pool pin xattr.

--- Comment (adilger, Thu, 21 May 2026 02:08:47 +0000) ---
Niko, before you get into the implementation, please describe the semantics you intend for each of the commands.  From my POV, in most cases when a user requests to do something, that is what they want to do, unless it is forbidden by the administrator, so I'm reluctant to put roadblocks in their way. It would just mean more inconvenience when trying to take some action (eg. add a new mirror to a file first requires removing the pool pin, adding the mirror, then re-pinning the file).

The original proposal for "pool pin" in LU-13171 was to store this pinning attribute in the file layout in a specific component/mirror, and it would be that mirror that is pinned,  it wasn't necessarily intended to prevent the addition or removal of other mirrors. Having to modify the file layout during pinning was considered too complex, so storing the pin attribute in a separate xattr was implemented, where the file is pinned to a named pool (or in the case of PCC-RO a specific HSM archive ID). 

If we want to change the semantics of the pinning so that it isn't possible to create another mirror on the file, then that should be stored explicitly in the pin xattr in some manner, rather than the intent just being inferred. Essentially, that would be a "pin the non-existence of a mirror on a specific pool", or "pin the non-existence of a file on any other pool", or possibly even "pin the non-existence of any other mirror on this file, even if it is on the same pool", though the latter would prevent any other mirror creation and may be quite undesirable. 

Since xattr space inside the inode is at a premium, this should be expressed in a compact manner. I could imagine "{{ pool: hdd,!nvme }}" or "{{ pool: hdd,-nvme }}" (or whatever is best suited to YAML), preventing creation on the nvme pool. Maybe "{{ pool: +hdd,-any }}" (or similar) would restrict new mirrors to only the hdd pool.

One concern about storing state on the parent directory that affects the files themselves is that this has the chance to become inconsistent, either due to file rename from one parent directory into another where the parents have different policies, or if the parent xattr is changed after the files are created. I'm not against it, just that care is needed to have sane semantics, or at least document what the limitations are (though typically users don't read documentation so the semantics should preferably be sane from the beginning).
