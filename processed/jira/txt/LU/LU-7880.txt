--- Description ---
In order to facilitate transfer of OST and MDT performance statistics for userspace applications, such as global NRS scheduling, SCR checkpoint scheduling, QOS and allocation decisions on the MDS, etc, it is useful to transport them via obd_statfs to the clients.

The statistics should include  .

The OSS and MDS already collect these statistics for presentation via /proc and it should be possible to include them into struct obd_statfs in newly-added fields at the end of the struct.

The stats should be fetched and printed with lfs df --stats command for all targets, but not necessarily for regular statfs() requests. With LU-10018 "MDT as a statfs() proxy", the MDT_STATFS request now has an mdt_body in the request which can be used to request different behaviour for the RPC.

--- Comment (adilger, Thu, 29 May 2025 15:54:18 +0000) ---
The statfs data is cached at each level of the stack, so that reading from multiple "kbytesfree", "kbytestotal", "filesfree", etc. parameters doesn't generate separate RPCs for each one. 

I don't think it matters which one you use. Depending on where the stats are available, you could fill in the stats at one level and they will be accessible up the stack. 

Each of the main lprocfs stats structures has its own timestamp since it was last reset (eg. lprocfs_stats.ls_init), which is printed by lprocfs_stats_header(), so that should be used instead of the mount time. This ensures the time range of the stats matches the values that are accumulated there. 

As for the decay factor, I don't have a fixed number in mind. We typically try to avoid hard-coding constants into the code, but I'm not sure whether this needs to be configurable or not. We need to have both the decay factor as well as the decay interval. If we calculate calculate the stats every 5s to determine "instantaneous" peak IOPS/BW, and the decay by 0.4 after 1 minute, then we need a decay factor of 0.6=a^(60/5), so a=245/256 would work out to be 41% decay after a minute, 93% decay after 5 minutes, which seems reasonable.

--- Comment (adilger, Fri, 5 Jun 2026 22:14:59 +0000) ---
The next part of this feature is the data path from userspace applications via llapi_obd_statfs() to populate struct obd_statfs returned to userspace with OS_STATFS_PERFSTATS set to indicate that the extra fields contain valid data.

This might not happen for a number of reasons

	a new client will typically not request the extra data, so it won't be returned

	a new client with old userspace library will also not request the extra data

	an old client with a new userspace library will not understand LL_STATFS_PERFSTATS in the ioctl(IOC_OBD_STATFS)/ll_obd_statfs() code, so it won't request the extra data

	a new client with new library will see LL_STATFS_PERFSTATS in ioctl(IOC_OBD_STATFS), and if the reply buffer is large enough it will pass this down to the low-level mdc_statfs() and osc_statfs() functions.  It looks like MDS_STATFS_NEW requests have a struct mdt_body buffer, so we need to pass the flag in there.  Currently, it is implicit that "mbo_valid |= OBD_MD_FLAGSTATFS" means only OBD_STATFS_SUM, but this could be extended to also send "mbo_flags = flags = OBD_STATFS_*" to the MDS to avoid using more bits in OBD_MD_FL* flags.

	an old server ignores all of these flags and not return OS_STATFS_PERFSTATS anyway

	a new MDS, seeing "mbo_flags & OBD_STATFS_PERFSTATS" will return the extra stats and set OS_STATFS_PERFSTATS in the reply.  The new client will copy this up to userspace which knows the extra data is valid.

	it looks like OST_STATFS does not (yet) have a "struct obdo" buffer in the request, so this would need to be added into an OST_STATFS_NEW, like we did for MDT_STATFS_NEW.  Then we can set "o_valid |= OBD_MD_FLAGSTATFS" and "o_flags = flags = OBD_STATFS_*" as is done for the MDT RPC and handle this the same way.  Old OSTs should ignore the extra buffer.

It looks like there is a mishmash of different flags:

	LL_STATFS_* from userspace requests

	OBD_STATFS_* flags are client-side internal-only request flags

	OS_STATFS_* are in the server reply to indicate extra state

Having two sets of request flags adds unnecessary complexity and could be cleaned up to avoid further duplication.

The OBD_STATFS_* names are better than LL_STATFS_*, IMHO, and would be better to maintain for the long-term interface, with the few LL_STATFS_* flags kept for compatibility.  Since OBD_STATFS_* are internal-only they could be changed to overlay on the LL_STATFS_* flag numbering without issues, so that we have unified requests from userspace as well (except OBD_STATFS_NESTED used only for internal lockdep, and OBD_STATFS_MDT0 which can be requested already via ll_obd_statfs(), which should remain internal-only and masked off from userspace).

It would be good to make a separate patch to move the existing OBD_STATFS_* flags into a named enum like "enum obd_statfs_req_flags" in lustre_user.h preserving the existing LL_STATFS_* values, and then adding the non-duplicate values and use this as the type in the various statfs functions that use these values, instead of using a plain "u32 flags" variables (or in the case of "struct obd_info" it has a __u64 for some reason).  It looks like this will also need an OBD_STATFS_PERFSTATS flag there.
