--- Description ---
A unique portal picks its match table – and with it the per-CPT

resource lock that guards it – by hashing the peer NID alone, in

lnet_match2mt().  Every buffer posted for one peer and every

message arriving from that peer therefore take the same lock,

however many CPTs the node has.

That is the bulk path: a client posts each bulk buffer against the

server's NID, so all of one client's bulk attach, match and

completion work for a given server serializes on a single lock.

Measured on a 192 core node over 0@lo, where every target shares one

NID: with 128 writers, that one lock accounted for roughly two

thirds of the busy CPU time.

A unique portal accepts only exact-match MEs, so attach and match

see the same match bits.  Hashing the match bits in as well spreads

one peer's traffic over every match table, while still sending a

given buffer and the message that matches it to the same table.

The effect is largest where many targets share a NID – loopback, or

a server exporting many OSTs on one NID – but the serialization is

not specific to that case.
