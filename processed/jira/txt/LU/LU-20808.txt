--- Comment (adilger, Thu, 24 Sep 2026 00:19:37 +0000) ---
diwa thanks for the document. Definitely improving DNE performance is of interest to many people. I think there are two main areas that can be improved:

	RPC protocol optimization as you discuss here, to reduce or completely eliminate round-trip times. Your document already discusses this in detail.

	reducing DNE recovery llog overhead/serialization, as proposed in LU-7426 and LU-7427. Alex has been doing work in this area for some time (in particular indexed llog) that would reduce the needless serialization and sync writes that were added to avoid 1-bit writes to the remote llog over OUT.

I think the two optimizations could potentially be done independently, but if we are already making a protocol change/OBD_CONNECT2_xxx for one of them, then it would be simpler to have that compatibility check cover both of these changes.

Some review comments from AI review of your document.  One issue that appears with the benchmarks is that the rr=2 testing appears to mostly generate remote-MDT rename operations, so the "local MDT" slowdown for crossdir rename is likely caused by BFL overhead and the conclusion that it doesn't matter whether the directory is local or remote is wrong.

There is a slowdown for renames across pathnames that cross into a remote MDT but land back on the same MDT due to an unnecessary mdo_is_subdir() call (which is Read 1 in the design) when renaming regular files that cannot be ancestors of any directory.  This overhead increases with the number of directories crossed by the rename.

Major issues

	Thread starvation or deadlock on the mdt_out service.
	
		Enqueues from one MDT to another go to OUT_PORTAL (ldlm_lib.c:329, mdt_mds.c:309). The same mdt_out threads also run the OUT_UPDATE requests.

		A plain enqueue replies right away, and the requester waits for the completion callback. For the intent result to be computed "under the exact lock being granted", the handler has to wait for the grant on the server side, the way mdt_intent_getattr() does. That means an mdt_out thread blocks.

		If the lock that conflicts is held by an operation that needs an OUT_UPDATE on this same MDT to finish, and every mdt_out thread is blocked in an intent enqueue, nothing can make progress.

		Fix to specify: run the intent only if the lock can be granted immediately. Otherwise grant it the normal way with an empty result, so the coordinator falls back to today's reads.

	
	

	Running permission and inheritance checks on the parent MDT causes more problems than it solves.
	
		Credentials: the document says the intent carries the "full caller context" in one place and "limited supplementary groups" in another. It also says handlers "adopt user identities directly from incoming RPC contexts", but on a connection between two MDTs, the RPC context is the other MDT, not the user.

		Per-MDT settings: policy settings can differ between MDTs (enable_remote_dir_gid, the RBAC check on DNE operations, the SGID behaviour). Default layout choice depends on the coordinator's own view of pools and free space.

		Recursive RPCs: when the parent has no default layout, the fallback is the root's default layout. Root lives on MDT0000, which may be remote from the parent MDT, so the handler would need its own remote reads. That contradicts "avoiding recursive OSP RPCs".

		Rolling upgrades: different MDD versions would compute the child's inherited state differently.

		Inconsistency: the unlink and rename paths in the same document already bring attributes back and check them on the coordinator.

		Recommendation: use a generic "read under lock" intent instead. It would return the parent's attributes, access ACL, default ACL, default LMV and LOV, pin, linkEA and LMV, plus the looked-up child FID, as bitmask-selected buffers. The existing MDD code would then run unchanged on the coordinator, reading from the OSP cache.

		This keeps almost all of the RPC savings. It removes the need to ship credentials and the MDD refactor, and the protocol shrinks to one opcode. At a minimum, the document must say why it rejected this option; right now it only asserts "operation-aware rather than a generic prefetch".

	
	

	Security: the handler trusts credentials sent by the caller.
	
		"Only over secure MDT-to-MDT connections" is never defined. The handler must reject these opcodes from any export that lacks OBD_CONNECT_MDS_MDS.

		Otherwise any client can send a forged UID and use the handler to test names and permissions in directories it cannot search.

		Issue 2's recommendation would make this much less dangerous.

	
	

	Skipping the lockless pre-lock lookup (LU-10235) undoes that fix.
	
		mdt_create() does that lookup specifically to avoid huge numbers of lock recalls on directories that already exist, as in mkdir -p storms. The venv and git workloads the document cites run mkdir -p constantly.

		The same lookup is also part of the restripe path: when the entry exists and restripe is set, the code continues instead of returning EEXIST (mdt_reint.c:647-653).

		Either keep the lookup, or measure a many-client EEXIST storm before and after the change.

	
	

	The OSP cache rules are not specified.
	
		"Suppress post-lock invalidation… invalidate stale entries immediately after these entries are accessed" is not a rule anyone can implement against.

		Cached data needs to be tied to a specific lock and dropped when that lock is cancelled. The document also needs to cover:
		
			other threads on the coordinator reading the same osp_object without holding the lock;

			how this interacts with opo_stale, which osp_write_interpreter() sets on error.

		
		

		The unexplained −23% directory-stat regression may be a symptom of this. It needs a root cause before landing, not "verify in a larger environment later".

	
	

	Striped and migrating directories are not covered.
	
		The name-hash lock goes to the stripe that owns the name. Picking that stripe needs the LMV first, and in the rename trace that LMV read happens before any lock.

		A directory that is migrating or being split has entries in two stripes, possibly on different MDTs. The intent handler cannot do an authoritative lookup there.

		It must detect this case from the LMV hash flags and layout version, and fall back. Today the document mentions layout versions only for create.

	
	

Medium issues:

	Missing reply buffers:
	
		There is no buffer for the parent's access ACL. The coordinator needs it to check unlink and rename permissions. The "Access ACL" row in the table is the child's computed ACL, not the parent's.

		There is no buffer for linkEA, which rename needs.

		Nothing covers encryption context or the encrypted-parent checks.

		LOV layouts with many components, or with mirrors, can be several KB. The document should say how the reply grows and what happens when it overflows.{}

	
	

	Error semantics:
	
		The three outcomes include "Advisory results", which is never defined.

		A real EACCES, ENOENT or EEXIST needs a status field that is separate from "not prepared". Otherwise a failed operation redoes every read and is slower than it is today.

	
	

	Resend and replay:
	
		A resent intent enqueue needs the same fixup that mdt_intent_fixup_resent() does for client intents.

		After the remote MDT restarts, OSP lock replay sends a plain enqueue with no intent, and the document should say so.

		It should also state explicitly that values computed remotely (mode, GID, ACL) are logged by value in the coordinator's update log, so DNE update-log recovery is unaffected.

		Separately, osp_md_object_lock() turns every error into -EIO, which the new error statuses can't survive as-is.

	
	

	Scope:
	
		A regular file is always created on its parent's MDT, so IT_DNE_CREATE_PREPARE is effectively mkdir-only.

		Hard links and lfs migrate -m are not covered.

		Cross-MDT directory rename is the slowest operation (20.2 ms, with 5 foreground transaction RPCs) and is not addressed at all. It could also be a one-time update-log creation cost caught by a single trace on a fresh tree; check it in steady state.

	
	

	File cross rename and the BFL:
	
		the claim that the rename lock is taken "whether or not the two directories live on the same MDT" is wrong for master.

		With mdt_enable_parallel_rename_crossdir=1, which is the default, need_bfl is set only when the rename involves a remote MDT (mdt_reint.c:2897).

		Both configurations probably measure the same 30 ms because rename_dst is on a different MDT from most task directories in both. The promised treatment "in the next section" does not exist.

	
	

	Wire Protocol:
	
		It should name the OBD_CONNECT2_* flag, and describe renegotiation when a peer reconnects after an upgrade or downgrade.

		Add a tunable to disable the feature and counters for intent hits and fallbacks.

	
	

Suggested Phase 0 (no wire changes)

	fix the name looked up three times;

	fix the duplicate linkEA read caused by mdd_parent_fid() invalidating the cache;

	fix read 8 duplicating read 7.

	remove unnecessary mdo_is_subdir() overhead for cross-directory regular file renames

	determine how much of the gain these fixes deliver alone. That separates the low-risk part of the win from the protocol change.

--- Comment (JIRAUSER24000, Tue, 6 Oct 2026 02:24:24 +0000) ---
> Lustre wire struct protocol review.pdf

	Validity and error contract (4.1, 4.4). The contract is now written in lustre_idl.h:
	
		The owner sets in mdrp_valid only what it read, and ignores want bits it doesn't know. The requester reads anything not answered itself.

		mdrp_status 0 without MDR_FID means the name doesn't exist, and that's authoritative under the lock. Any other status means "not resolved here", for example -EREMOTE for a striped directory.

		mdrq_fid must match the lock resource, or the request gets -EPROTO.

		Senders zero the padding.

	
	

	Size cap and slots (4.2, 4.3, 4.7). The per-xattr buffers are replaced by a name-keyed bundle, following the RMF_EAVALS/RMF_EAVALS_LENS precedent:
	
		The request lists the xattr names.

		The reply has a struct mdt_read_xattr {status, len} per name, and one buffer with the values.

		The status says whether each xattr was read, absent, failed, or too large; when too large, len is the size it needs.

		mdrq_xattr_size is now one budget for all values together.

		Both request and reply have 6 fixed buffers, so adding an xattr (linkEA, encryption context) needs no format change.

		We kept option A over embedding an OUT request, to avoid running OUT handlers inside the intent policy.

	
	

	Security (4.5). The handler checks OBD_CONNECT_MDS_MDS and OBD_CONNECT2_DNE_INTENT on every request, plus MDT authentication under GSS.

	Lock coverage (4.6). The owner takes the lock bits as try bits, all or nothing. If the lock isn't free at once, or the enqueue is a resend, the intent doesn't run (no DISP_IT_EXECD): the lock is granted normally and the requester reads what it needs itself. LDLM_FL_BLOCK_NOWAIT would fail the enqueue instead, which isn't what we want.

	Naming (4.8). The names are unified as IT_MDT_TO_MDT_READ, struct mdt_read_req/rep/xattr, enum mdt_read_item, RQF_LDLM_INTENT_MDT_READ and RMF_MDT_READ_*.

	4.9 The PDF predates the redesign that merged the per-operation intents into one credential-free read. I'll update the design doc.

	WBC (6). There are no bit collisions. The intent is read-only and never replayed: it's skipped on replay. A client-facing variant would need server-side permission checks, so it's not just a different gate.

	Attributes (4.7). The obdo lacks birth time and rdev, which is the same as OUT_ATTR_GET. The attribute buffer is always packed; every caller asks for it.

	the OUT object-update protocol;

	the OUT optimisation work in LU-4215, LU-7426 and LU-7427, including patch https://review.whamcloud.com/15336 ("LU-4215 out: few optimization to the protocol");

	the Metadata Writeback Cache series under LU-10938, starting at patch https://review.whamcloud.com/36924 ("LU-13047 wbc: foundation framework for WBC").

Review of the LU-20808 wire protocol

Design-level comments on the PS4 protocol, which 69254 defines and 69256, 69257, 69259 and 69447 implement. The credential-free "read under lock" model is right: it answers the main points of the 2026-09-24 review (no waiting in mdt_out, no permission logic on the owner, explicit fallback). What remains is mostly about format, reuse and scope.

	R1, design: the new format duplicates OUT at both ends. The owner re-implements OUT_ATTR_GET, OUT_XATTR_GET and OUT_INDEX_LOOKUP through MDD and LOD, and needs a new raw-xattr accessor stack (69255) only to get back the bytes OUT already returns; its replies mix MDD-view attributes with OSD-view xattrs. The requester re-implements reply parsing and caching next to osp_attr_get(), osp_xattr_get() and their async interpreters. The stated reason for not embedding OUT, "to avoid running OUT handlers inside the intent policy", does not hold up: the read handlers are short, local and take only dt_read_lock(); they already run in the same mdt_out threads, and with LOC_F_LOCAL (69446) they cannot reach another target. The prototype runs them unchanged.

	R2, wire: statuses are host errnos. mdrp_status and mdrx_status freeze the host errno ABI; every other wire status goes through ptlrpc_status_hton(), as OUT results already do.

	R3, wire: an owner rejection fails the whole operation. MDT_READ_XATTRS_MAX is a wire constant that only the owner enforces, with -EPROTO, which osp_md_object_lock() turns into -EIO for the user's operation; raising it later would break operations against older owners. An unknown item or a malformed name should cost that item, not the enqueue. The prototype answers an unknown read type with -EOPNOTSUPP, and a read of another object with -EINVAL, in that read's own result, and declines (grants without reading) an intent with more reads than the owner runs.

	R4, performance: the needed size on -ERANGE is returned but not used. The first create under a parent with a large default layout makes LOD try its 64-byte per-thread buffer, probe the size, then read: three OUT RPCs. This is why sanity test_1000e fails on the first run after a mount with PS4 as well (5 OUT RPCs against a budget of 4); it passes on reruns, once the buffer has grown. In the prototype a value that does not fit comes back as its size without the value (what OUT_XATTR_GET already does for an empty buffer), and OSP caches that size, so the probe and the -ERANGE are answered locally: one read, and 1000e passes on the first run with 3 OUT RPCs.

	R5, bug: the intent inside an MDS_BATCH sub-request asserts. mdt_intent_dne_read() asks for RMF_MDT_READ_REQ on a RQF_BUT_GETATTR sub-capsule and hits the LASSERTF in __req_capsule_offset(). Only an export that negotiated MDS_MDS and the flag gets that far. Refuse it when mti_batch_env is set.

	R6, bug: LOHA_EXISTS is not set when attributes are seeded (osp_attr_get() sets it; the aireview comment on 69257 is still open).

	R7, design: lock coverage is implicit. The intent rides the name-hash lock; the attributes and xattrs it returns are protected by the PDO CW lock taken just before it. The IDL comment should say that the requester must already hold, or be granted by this enqueue, a lock covering everything it reads. The seeded state does not outlive the lock: mdt_save_remote_lock() calls mo_invalidate() when a remote UPDATE or XATTR lock is released.

	R8, design: one object per enqueue. The target parent, the target, ancestors and the root default layout are not covered, and the looked-up child FID comes back without attributes, so instantiating a remote child still costs an osp_object_init() attr_get. With OUT reads, a later step can add reads of other objects on the owner MDT without a format change, once a lock rule for them is agreed.

	R9, design: two serial enqueues remain. Every remote-parent operation pays the PDO and name-hash enqueues one after the other (unlink a third, rename a fourth); with the reads gone, they are most of the remaining round trips (step 5).

	R10, design: the contended fallback is the slowest path. When the try-lock fails, the requester falls back to one RPC per read. The same read set could instead go in one OUT_UPDATE after the grant, given independent per-update status (step 2).

	R11, no wire change: the pre-lock read for clients that are not encryption-aware. Caching the encrypt flag on the mdt_object (as LOHA_FSCRYPT_MD is), or checking after the parent lock, saves one RPC per create.

	R12, compat: connect flag name and IT bit. 69320 puts "dne_lock_intent" at the wrong index of obd_connect_names[]. IT_MDT_TO_MDT_READ = 0x00010000 collides with WBC's IT_SETATTR (37137); settle the value now.

	R13, operations: no tunable and no counters for intents sent, executed, declined and rejected, as asked in the 2026-09-24 review.

WBC: overlap or replacement?

The WBC series (64 changes, not landed; the main chain is based on 2.14.56 and the foundation on 2.15.64) adds no new RPC and no MDT-to-MDT protocol. On the wire it uses:

	async intents: IT_CREAT and a new IT_SETATTR with LDLM_FL_INTENT_PARENT_LOCKED or LDLM_FL_INTENT_EXLOCK_UPDATE, the parent's EX handle in lock_handle[1];

	MDS_REINT with a MDS_WBC_LOCKLESS bias, under which the MDT takes no locks;

	MDS_BATCH sub-operations for create, setattr and lock re-acquire.

Only directories the client created become cache roots; the EX grant returns mdt_body, the LMV and the default LMV, but no ACL, pin or default LOV. Children are made in client memory with client-allocated FIDs, and the MDT applies inheritance at flush time. Flush order is the client's job (one directory at a time, top-down; a batch stops at the first failure). Rename and link first flush both sides, then run as normal operations.

Where it meets LU-20808: a lockless flush that creates a child on a different MDT from its parent makes the coordinator read the parent with unlocked OSP getattr and getxattr. These are the reads the intent batches, but with no enqueue to carry them, since the client's EX lock covers the parent. With OUT reads the same read set goes in one plain OUT_UPDATE; a typed intent buffer cannot be reused there.

Conclusion: the two are complementary. Worth unifying: the container code (today OUT_UPDATE and MDS_BATCH are separate protocols, and mdt_batch() was written from out_handle() and duplicates its header and bulk handling, so the proposal is one shared implementation of that part); the "directory state needed to create a child" read set; the rules (grant at once or skip the work; partial execution, the same problem in LU-7319 and LU-15550; network errnos; needed-size hints). Keep the payloads separate: clients send namespace operations that need permission checks and inheritance, and must never send object updates. Settle these collisions before either lands: the IT bit; WBC's LDLM_FL_INTENT_PARENT_LOCKED, which is master's LDLM_FL_CONTENTION bit; and MDS_WBC_LOCKLESS, which has collided with a master bias bit after each rebase.

Proposed design

Principles:

	One vocabulary of object operations (enum update_type) for every MDT-to-MDT read and write.

	Several transports carry that same encoding: OUT_UPDATE, the read-under-lock intent, and later a compound request; one reply format and one requester path (OSP's interpreters and cache).

	Every handler reachable through OUT_PORTAL is non-blocking: it never waits for a lock grant and never calls another target.

	One capability negotiation covers the whole OUT generation, instead of one connect flag per feature.

	Clients never send object updates; WBC shares the container code and the execution rules, not the payload.

Step 1 (LU-20808, prototyped): the read set on the enqueue.

LDLM_ENQUEUE to OUT_PORTAL, ldlm_intent.opc = IT_MDT_TO_MDT_READ
 request: PTLRPC_BODY | DLM_REQ | LDLM_INTENT | OUT_UPDATE_HEADER
   out_update_header      { magic, count = 1, inline_length, reply_size }
   object_update_request  { UPDATE_REQUEST_MAGIC_V2, count }
     OUT_INDEX_LOOKUP  fid = locked dir  "name"                     room 16
     OUT_ATTR_GET      fid = locked dir                             room 208
     OUT_XATTR_GET     fid = locked dir  "system.posix_acl_access"  room = shared budget
     OUT_XATTR_GET     ...  default ACL, pin, LMV, default LMV, LOV
 reply:   PTLRPC_BODY | DLM_REP (DISP_IT_EXECD) | OUT_UPDATE_REPLY
   object_update_reply    { magic, count, lens[] }, then { rc, datalen, data } per read

	Reads only (OUT_ATTR_GET, OUT_XATTR_GET, OUT_XATTR_LIST, OUT_INDEX_LOOKUP) of the locked FID; anything else gets its own -EOPNOTSUPP or -EINVAL result, so a newer requester can ask for more without a new flag.

	The owner takes the lock bits as try bits, all or nothing, then out_reads_run() runs the existing OUT handlers on the OSD object (located with LOC_F_LOCAL) and grants the lock. A failed read does not stop the next one. If the lock is not free, or the enqueue is a resend, nothing runs and the lock is granted the normal way, without DISP_IT_EXECD.

	Values share the reply budget in order; one that does not fit comes back as its size without the value, and OSP caches the size.

	A lookup in a striped directory master is answered -EREMOTE; a missing locked object is -ESTALE, never -ENOENT, so that -ENOENT from a lookup always means "the name does not exist", which is authoritative under the name-hash lock.

	The requester must hold, or be granted by this enqueue, locks covering everything it reads.

	Gate: OBD_CONNECT_MDS_MDS plus the connect flag, MDT authentication under GSS, never inside an MDS_BATCH sub-request.

Step 2 (LU-7319, LU-16554, no new structs): independent updates and right-sized replies in OUT_UPDATE.

	One update flag, value agreed once, for "record rc and continue". It serves the contended LU-20808 fallback (the same read set in one OUT_UPDATE after the grant), WBC's lockless remote-parent reads, rename's pre-lock linkEA and LMV reads, batched destroys (68928), and LFSCK reads across objects. Reads re-execute on resend; only idempotent updates may carry the flag.

	Exact reply sizes (50522), with a shrunk reply when the peer advertises it can take one.

	Read-back in the transaction RPC: an OUT_ATTR_GET after an OUT_ATTR_SET in the same RPC already works, because out_handle() closes the transaction before a read; it keeps the coordinator's cache valid after its own update.

Step 3 (LU-4215 redone, one capability): compact encoding.

	Request magic UPDATE_REQUEST_MAGIC_V3 with a shorter update header: batchid and flags per request instead of per update, a "same FID as the previous update" bit, no result size on mutations. It replaces 15336's in-band guess from the parameter size.

	A variable-size lu_attr carrying every LA_* field it marks valid (including btime, rdev and dirent count, and rejecting unknown bits explicitly), for OUT_CREATE, OUT_ATTR_SET, OUT_ATTR_GET, update-llog records and intent replies.

	Xattr name codes defined in lustre_idl.h and wiretest, with a by-name fallback; add trusted.pin, trusted.som and the encryption context.

	One OBD_CONNECT2 flag plus an OUT capability word in a spare obd_connect_data field (highest update type, LA_* mask, xattr-code table version, short replies, independent updates, target-side append). The 2018 max-known-id agreement fits here.

	Value: bytes and batch density (setattr 256 to 72 bytes, so 15 to 56 per inline RPC), requests under the 4 KB inline and IB-immediate limits, smaller update llogs. It saves no round trips.

Step 4 (LU-7426, LU-7427, largest throughput gain): target-owned update logs.

	An OUT "append record" operation: the target appends the record to its own update log and returns the cookie (Di's 2015 option 2), or finish 57261's remote-llog TODOs. Either way the coordinator no longer computes the peer's header, bitmap and offset, nothing forces the per-pair sending order, and several distributed transactions can be in flight between two MDTs.

	Send each record once: today a remote MDT receives its updates and then the whole record again, through about 296 bytes of header writes plus the record. The target could execute the operations for its local FIDs from the record itself, with the executor recovery already uses (update_recovery_exec()).

	Range and batchid cancels with several batchid slots (LU-7427, LU-8714) replace one cancel transaction per record per participant.

Step 5 (shared with WBC): compound MDT-to-MDT requests.

	Use the MDS_BATCH container between MDTs for several enqueues, each with its read set, plus an OUT request, in one RPC; run in order and stop at the first enqueue that cannot be granted at once. For mkdir under a remote parent, the PDO and name-hash locks and the reads then take one round trip.

	Prerequisites: client MDS_BATCH moved off OUT_PORTAL (69436), the batch-intent capsule fix (R5), and a sub-request status that says "not executed, resend".

	Reserve a per-element "acting under lock handle" field now. WBC's LDLM_FL_INTENT_PARENT_LOCKED needs it when a flush spans MDTs; without it, a coordinator's enqueue on a parent the client holds in EX would de-root the client in the middle of the flush.

Open questions

	Should the owner be allowed to read objects other than the locked one, e.g. the looked-up child when it is on the same MDT, which would save the osp_object_init() read? That needs a rule for which lock covers it, perhaps "attributes only, nothing cached past the operation".

	One "OUT v3" capability for steps 2 and 3, or separate connect flags? The update-flag collisions argue for one.

	Who owns the IT bit and LDLM flag allocations between LU-20808 and the WBC series? The lustre_idl.h comment asks for coordination, but nothing records it.

	Is step 4 better done as an OUT append operation, or by finishing the indexed llog's remote handling? Both remove the coordinator-side header state that forces ordering.
