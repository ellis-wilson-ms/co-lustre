--- Description ---
The data-in-dirent patch was being discussed for upstream inclusion for 64-but inode support, but eventually that was not accepted because the 64-bit inode patch was only partially tested (ie. it built and didn't break 32-bit inodes, but had code and testing gaps for actual 64-bit inode numbers).

Landing the dirdata patch has now become more complex because the "fscrypt+case-insensitive" features are now storing extra information after the name in the dirent. This would have been a perfect case to use dirdata and get it included, except Google had already started using this in Android and didn't want to update the format, so there needs to be additional compatibility added for this case:

https://patchwork.ozlabs.org/project/linux-ext4/patch/20210203090745.4103054-2-drosen@google.com/

An agreed-upon proposal to get dirdata accepted without the Lustre kernel dependency is to add a dedicated test ioctl interface to store dirdata in directory entries, and confirm that it is being handled properly (eg. across rename, with e2fsck, etc). For compatibility with Lustre, this could store the "inode|generation" into the Lustre FID slot, since this is equivalent to an IGIF FID, and is also easy to verify later.

--- Comment (adilger, Wed, 6 May 2026 22:08:01 +0000) ---
I was thinking that the ioctl() would only create the directory entry, maybe like a hard link to an existing file, and optionally remove the previous link?  We had to do that for LFSCK in the past, to allow adding or modifying the FID on an MDT filesystem that was restored from a tar backup at the ldiskfs level that doesn't add any FIDs in new dirents.

In order to make this "test" ioctl() more generally useful, it should be called on the parent directory and take a filename and FID as argument, then lookup the filename in that directory to get the inode number, add a new dirent with the FID into this directory (use IGIF if FOR is empty), and remove the old dirent.  That would also potentially be useful for e.g. userspace LFSCK or similar kind of Lustre repair tool.  Then use "debugfs -c -R 'ls -lD DIR' /dev/XXX" to print out the dirdata fields (decode FID, print hash major/minor, or hex for other fields) to match the Lustre version of debugfs.  Not only does this give us a useful dirdata test case, but it also moves Lustre-specific functionality into upstream debugfs.
