Summary

sanity test_33hh failed with MDT index mismatch 10/250 times. The failure is a threshold flake. It is not a defect in the patch under test. The test also has a counter defect. That defect makes the gate two times more strict than the message reports.

The failure value was exactly at the gate. The test comment on the line above the gate expects 2 to 4.

What the test does

sub_33h crush2 creates a striped directory with the crush2 hash. It then creates a target file and records the MDT index of that file. The test then creates temporary files with mktemp. It uses two name patterns. The client must put each temporary file on the MDT of the target. Each file on a different MDT is one mismatch.

The counter defect

The loop runs 250 times for each of the two patterns. It thus creates 500 files. The failed counter accumulates over both patterns. The gate and the printed denominator use $count, which is 250.

	local failed=0
	local patterns=(".$tfile.XXXXXX" "$tfile.XXXXXXXX")
	...
	echo "$failed/$count MDT index mismatches, expect ~2-4"
	(( failed 

The true tolerance is 10 of 500 files, which is 2%. The message reports 10 of 250 files, which is 4%. A reader of the failure message thus sees a rate two times higher than the real one.

An observation on the distribution

The log shows 9 of the 10 mismatches under the first pattern, which uses a 6-character suffix. The second pattern, which uses an 8-character suffix, gave 1 mismatch. One run is not sufficient to show a difference between the two patterns. The datum can help the person who corrects the threshold.

Why the patch under test is not the cause

Gerrit 67995 adds ldlm_lock_pin_lru() and ldlm_lock_unpin_lru(). No code calls either function at that commit. The caller arrives in the next patch of the series. The only other change from the parent is a refusal in ldlm_lock_add_to_lru_nolock() for a lock with LDLM_FL_NO_LRU. No lock in the tree carries that flag on the path. The patch touches no MDT code, no DNE code and no hash code.

The consoles of all 5 nodes show no LBUG, no stack trace and no Lustre error.

Prior tickets

LU-16198 and its duplicate LU-17990 cover the other assertion in the same helper. That assertion counts the files which match, and not the files which do not match. Andreas resolved LU-16198 with a wider margin. The reason was the same: the threshold was more strict than the random distribution permits. The mismatch half of the helper did not get the same treatment.

Suggested correction

1. Correct the counter. Reset failed for each pattern, or compare against a threshold for 500 files. Print the denominator which the gate uses.

2. Widen the margin, the way LU-16198 did for the sibling assertion.

What is not proven

The expectation of 2 to 4 mismatches comes from the test author. This analysis does not calculate the true rate for the crush2 hash. One failure is not sufficient to separate two causes. The first cause is a threshold which is too strict. The second cause is a change which raises the mismatch rate. A count of 20 or more runs on an unmodified master gives the evidence to choose between them.
