Maloo session: https://testing.whamcloud.com/test_sets/305ba00a-2ed1-492d-860f-5ee22c713338 (build lustre-reviews #132826, review-dne-zfs-part-6, RHEL10.1 client / zfs server, change 69305 patchset 4).

test_70c starts a background tar loop (tar cf - /etc | tar xf -) into a directory default-striped "-i2 -c4" across all 4 MDTs. Within about 15 seconds, well before any engineered MDT failover, the loop died:

tar: etc/pki/entitlement: Cannot utime: Input/output error

tar: etc/firewalld/ipsets: Cannot utime: Input/output error

tar: etc/firewalld/ipsets: Cannot change ownership to uid 0, gid 0: Input/output error

tar: etc/pkcs11/modules: Cannot change ownership to uid 0, gid 0: Input/output error

tar: etc/gdbinit.d: Cannot utime: Input/output error

tar: etc/fonts: Cannot utime: Input/output error

tar: etc/pam.d: Cannot utime: Input/output error

tar: Exiting with failure status due to previous errors

 replay-single test_70c: @@@@@@ FAIL: tar failed in loop

random_fail_mdt() then found the tar pid gone: "FAIL:  stopped".

The client debug log shows the underlying error is MDS_SETATTR (opc 36) RPCs completing with rc=-5 (EIO), e.g. for "fonts" on MDT0002 and "pam.d" on MDT0003. Neither the client nor either MDTs debug log has any LustreError/LBUG/ASSERTION around that time explaining the EIO; the MDTs own lock/getattr/save_lock handling for the same objects looks like ordinary successful processing.

Evidence this is not the triggering changes own bug (change 69305, LU-8933 lod round-robin rebalance): the exact subtest was reproduced twice against that patchset build on a fresh 4-MDT ZFS guest (same MDSCOUNT=4, same default dirstripe) – both passed cleanly through full MDT failovers with no tar errors. There is no comparison history either way on this exact signature (zero occurrences anywhere on the branch or any other change/janitor run in 30 days). The failure happened well before any deliberate MDT failure, which argues against the replay/failover logic the test targets.

This specific test (tar /etc under heavy DNE striping while MDT failovers are engineered) has a long history of occasional, unrelated transient tar I/O errors: LU-8814 and LU-8830 (both 2016, resolved Duplicate), though with a different errno (ESHUTDOWN during an actual failover, here EIO before one).
