--- Description ---
Currently lctl --device MGS llog_catlist does not enumerate either the filesystem-specific sptlrpc llog file, nor the global params file in it's list, for example on a small test system:

[root@server1 ~]# lctl llog_catlist

config_log: lustre-MDT0000

config_log: ost-client

config_log: lustre-OST0003

Analysis

lctl --device MGS llog_catlist enumerates config logs by reading the on-disk CONFIGS directory (mgs_list_logs() in mgs/mgs_llog.c) and filtering each entry through two gates: 

	An allow-list — lu_name_in_white_list() (include/lu_object.h), applied per dirent in class_dentry_readdir()

	A "name contains '-'" check in mgs_list_logs()

-sptlrpc and params are dropped here:

	-sptlrpc: this fails the allow-list, which only has a bare 'sptlrpc' entry, which is checked to be an exact match, but no check is made for the -sptlrpc file.

	params: this passes the allowlist, but fails the check in mgs_list_logs() because it contains no hyphen.

I think this is unintentional and both should be listed.

 

This regression also means that -sptlrpc is invisible to multiple other commands. class_dentry_readdir() which calls lu_name_in_white_list, is the single enumerate CONFIGS function used by:

	mgs_erase_logs

	mgs_clear_configs

	mgs_lcfg_fork

	mgs_lcfg_rename

	mgs_write_log_direct_all (however this explicitly filters out -sptlrpc logs later)

Fixing this issue will mean that all of these cases will now, in my view correctly, clean up a filesystem's sptlrpc log. However this would mean a change in behaviour from currently. In my opinion, this is the expected behaviour anyway and the current situation is unexpected, therefore this should just be fixed.

Let me know if this is not the case.
