--- Description ---
Problem

On a dual-socket client the HCA is attached to one socket's PCIe root complex. Any RDMA the device performs against memory on the other socket crosses the inter-socket link (UPI/xGMI). Without PCIe Relaxed Ordering that path serializes toward single-outstanding-write behavior and consumes inter-socket bandwidth shared with the CPUs.

The cost is direction-asymmetric and large. On ConnectX mlx5 (RO off, fio bs=1m numjobs=32 iodepth=64), a NUMA-remote read sink runs at 2036 MiB/s against 9291 MiB/s for a NUMA-local sink: a cross-socket HCA-write penalty of roughly 4.5x. Writes (HCA reads) are barely affected (about 5%).

Lustre bulk lands in the application's buffer, placed wherever the job's thread ran, so the HCA frequently DMAs cross-socket.

Why the existing lever is not enough

On a multi-rail client this is already mitigated. The client bulk payload is passive and connection-bound: the server drives the RDMA over the connection the request arrived on, targeting the client NID (`rq_source`) the request RPC egressed on. Stock LNet steers that egress by the bulk buffer's NUMA node, because the request MD carries `LNET_MD_BULK_HANDLE` and `lnet_cpt_of_md()` → `lnet_get_first_page()` follow the bulk handle to rank the egress NI by the bulk buffer's first page. With a healthy buffer-local rail, the bulk already lands NIC-local.

That lever cannot help two cases:

1. A single-HCA client has no buffer-local rail to select; the one connection's HCA crosses sockets for any remote buffer. This is exactly the case `numactl` also cannot fix, since you cannot move the NIC.

2. No {}healthy buffer-local rail exists (local rail down or degraded).

Proposed solution

Add an optional NIC-local bounce pool inside ko2iblnd. Stage the bulk through a per-HCA, pre-registered arena allocated on the HCA's own NUMA node, and pay a CPU copy for the last hop. A cross-socket CPU copy is cheaper than a cross-socket NIC DMA and is immune to the PCIe ordering penalty, so one mechanism addresses both costs. The bounce is confined to the LND: transparent to ptlrpc/osc/llite and to the server, client-only, with no wire-protocol change.

	Inbound (read / PUT sink): advertise a NIC-local slot's `REMOTE_WRITE` rkey as the sink; the peer RDMA-writes into it; copy-out runs off the CQ poller on an HCA-CPT-bound workqueue, with `lnet_finalize` deferred behind the copy.

	Outbound (write / GET source): copy-in inline, then the device DMAs from the NIC-local slot. Measured at -16% on writes (FAR 20.0 → 16.7 GiB/s) because HCA reads are barely socket-penalized, so the added copy-in costs more than it saves. Outbound is therefore opt-in (FORCE) only; AUTO never engages it.

Engagement and safety

	OFF by default. `bounce_enable` is tri-state (`0` off / `1` force / `2` auto). AUTO allocates the arena only on a multi-node NUMA box and engages the inbound path only when the buffer is NUMA-remote from the HCA, so local I/O stays zero-copy.

	Slot exhaustion or any rd-build failure falls back to the direct app buffer; a bounce can never fail an I/O.

	Slots are recycled across transfers, so a non-conformant peer that under-writes yet reports success could leak prior-transfer bytes in the untransferred tail. Each slot is zeroed on release (fused into the inbound copy-out while cache-hot); gated by `bounce_scrub`, default on.

	At `bounce_enable=0` the datapath is byte-for-byte identical to stock; the two bulk rd-build sites add count-only predicate math and nothing reroutes.

Tunables (ko2iblnd module params)

parm:           bounce_stats:NIC-local bounce pool counters. Read to dump. Any write resets the cumulative counters (hits misses fallback copyout_wq copyout_inline bytes would_* local_*) for a fresh window without rmmod; NOT reset: the live inflight gauge (leak detector) and the per-pool exhaustion latch.
parm:           bounce_enable:NIC-local bounce pool: 0=off (default), 1=force-on (both directions, allocate even on single-socket; testing), 2=auto (inbound/read only - outbound is a measured cross-socket loss - on if multi-node NUMA); invalid -> off
parm:           bounce_pool_mb:bounce pool size per HCA, MiB (int)
parm:           bounce_slot_kb:bounce slot size, KiB (int)
parm:           bounce_min_nob:min transfer size to consider bouncing, bytes (default 64 KiB: below this a copy+FastReg costs more than the cross-socket DMA it replaces) (int)
parm:           bounce_dist_thresh:engage when node_distance(page, hca) exceeds this (default LOCAL_DISTANCE) (int)
parm:           bounce_bp_node:override HCA NUMA node for the pool (-1 autodetect) (int)
parm:           bounce_scrub:zero NIC-local bounce slots on release to prevent short-write residual disclosure (1=on, default; 0=off for the SEC-1a negative-control test only) (int)
parm:           bounce_copyout_max_active:inbound copy-out workqueue concurrency per HCA CPT (default 2 = the Group 6 knee; 1 = serialized; >2 = marginal/no gain) (int) 

Testing and results

Functional gates on SoftRoCE (byte-exact read+write, exhaustion fallback, scrub invariant via `fail_loc=0xe012`, clean teardown), all passing.

Performance on real ConnectX mlx5 (mlx5_1 on NUMA node 1, RO off, fio bs=1m numjobs=32 iodepth=64), shipping fused+scrub build:

	Inbound read, NUMA-remote sink: 2036 → 7422 MiB/s with the bounce engaged, a 3.65x gain that recovers to about 80% of the NUMA-local ceiling (9291 MiB/s). Copy-out confirmed off the CQ poller (copyout_wq counter tracks engagement 1:1). The residual gap versus local is the inherent 1 MiB slot zero-write that the cache-hot fusion cannot remove (about 8%).

	No regression when local: with a NUMA-local sink, AUTO matches baseline (9312 vs 9291 MiB/s) with engagement count 0, so the topology predicate correctly stays out of the way.

	No regression on writes: with AUTO and a NUMA-remote write buffer, write bandwidth matches baseline (19.6 vs 20.1 GiB/s) with engagement count 0, confirming AUTO never touches the outbound path.
