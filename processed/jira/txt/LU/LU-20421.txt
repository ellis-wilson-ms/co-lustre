Context:

The CEA was performing an online update on the backend storage (SFAOS).

For MDTs, they moved each target one-by-one on the failover controller to shutdown the VMs and update the controller. They waited the recovery for each failover.

A Robinhood trash policy was running in the background. This policy move cold entries from user directories to a replicate trash path (and then chown root:root). The trash directories are created using DNEv3 so the rename create a distributed transaction between 2 MDTs (the source parent+inode and the target parent are not on the same MDT).

--- Comment (adilger, Wed, 24 Jun 2026 08:16:26 +0000) ---
Etienne, the DNE distributed transactions should be able to handle this case properly.  The transaction should be replayed in this case to ensure the update is persisted on the remote MDT.  However, it also depends on where the original error came from and how long it lasts. The recovery cannot block forever on that transaction replay or the filesystem would become unusable.

A Robinhood trash policy was running in the background. This policy move cold entries from user directories to a replicate trash path (and then chown root:root). The trash directories are created using DNEv3 so the rename create a distributed transaction between 2 MDTs (the source parent+inode and the target parent are not on the same MDT).

Doing distributed transactions for every file delete is very expensive. In the TCU feature the files are deleted into a per-MDT directory to avoid this, and with recent rename optimizations it does not need the global rename lock (BFL) for regular file renames within the same MDT.  That would not only avoid the distributed transaction (about 20x slower than a local rename), but also global serialization of all renames.

If you want to keep a striped directory as the trash can (which may also have name collisions), it would be possible to add a unique file suffix that ensures the filename hash remains on the same MDT (which needs a bit of work on the RBH side, but wouldn't be more than generating a random suffix then generating the hash and incrementing the last character until the hash lands the target filename on the same MDT).  I'm not 100% sure if renames into a striped directory shard on the same MDT avoid the BFL, but that would be possible to fix, and at least it would avoid the DNE transaction.
