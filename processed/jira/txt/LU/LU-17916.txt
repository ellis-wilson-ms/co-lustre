--- Description ---
When support for folios are added to generic_perform_write() we can enable folio based allocations without re-writing the lustre i/o path to use iomap:

https://www.spinics.net/lists/linux-nfs/msg104002.html

Updated patch:

https://lore.kernel.org/linux-fsdevel/20240527163616.1135968-2-hch@lst.de/

Depends on (landed for v6.9):

https://patchwork.kernel.org/project/linux-fsdevel/patch/20240521114939.2541461-1-xu.yang_2@nxp.com/

This is tested for NFS

https://www.spinics.net/lists/linux-nfs/msg104003.html

suggesting this alone is enough for a 2x improvement in buffered i/o.

Update lustre to use the folio allocation ie: __filemap_get_folio() instead of the grab_cache_page* family.

Provide a __filemap_get_folio() implementation for compatibility with older kernels.

Assuming no large regressions this should be available in kernel v6.11:

Linux kernel commit: v6.10-rc7-2-g9aac777aaf945

   filemap: Convert generic_perform_write() to support large folios

--- Comment (stancheff, Thu, 9 Apr 2026 08:04:28 +0000) ---
crypto should work with struct folio as it is currently.

Large folios are not enabled until LU-19895 where we can enable large folios by setting the flag in the inode mapping what order of folios can be allocated.

The default is 0 so Lustre will only allocate a 0 order folio. The only other way a folio of order other than zero can be seen is with DIO when the user page is almost certainly embedded in a large folio.

Since the bounce folio/page and the DIO page are treated as PAGE_SIZE units there should be no issue with encryption.

When we get to large folios things get a bit more complicated but it is essentially similar ... we just have more working keeping track of the bounce folio since we now may have many bounce folios of order 0 mapping into PAGE_SIZE chunks of a larger folio.

--- Comment (adilger, Fri, 9 Oct 2026 21:29:40 +0000) ---
[Claude] patch https://review.whamcloud.com/69505 ("1MiB of encrypted file with key loaded corrupts data" class="issue-link" data-issue-key="LU-20896">LU-20896 osc: encrypt direct IO pages at their own file index") adds "always_except LU-17916 66a" to sanity-sec.sh for ZFS, and patch https://review.whamcloud.com/69506 ("1MiB of encrypted file with key loaded corrupts data" class="issue-link" data-issue-key="LU-20896">LU-20896 llite: transfer ciphertext for O_CIPHERTEXT DIO") extends it to "66a 66c".  These tests fail on ZFS because of client races with large folios used for direct IO:

	folio_trylock() in osc_brw_prep_request() can fail when another RPC holds the lock of the same large folio, and that RPC can unlock it before the folio_test_locked() check in osc_encrypt_pagecache_blocks(), which then returns -EINVAL ("prep_req failed: rc = -22").

	osc_brw_fini_request() checks page 0 of the folio for a hole instead of the page being read, so a direct read into a THP buffer can skip decryption.  This is fixed by patch https://review.whamcloud.com/58097 ("LU-17916 clio: switch to struct folio").

The fix for the trylock race, and the removal of these always_except entries, depends on the LU-17916 patches landing first, so it will be based on them rather than adding more page-based code now.
