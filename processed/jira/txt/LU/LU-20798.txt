Since kiblnd_create_tx_pool() allocates all what is needed using LIBCFS_CPT_ALLOC() macro, that some of the requested sizes exceed LIBCFS_VMALLOC_SIZE meaning that finally GFP_NOFS will not be used : 

 

/**
 * allocate \a nr_bytes of virtually contiguous memory that is bound to the
 * partition id \a cpt.
 */
static inline void *
cfs_cpt_vzalloc(struct cfs_cpt_table *cptab, int cpt, size_t nr_bytes)
{
        /* vzalloc_node() sets __GFP_FS by default but no current Kernel
         * exported entry-point allows for both a NUMA node specification
         * and a custom allocation flags mask. This may be an issue since
         * __GFP_FS usage can cause some deadlock situations in our code,
         * like when memory reclaim started, within the same context of a
         * thread doing FS operations, that can also attempt conflicting FS
         * operations, ...
         */
        return vzalloc_node(nr_bytes, cfs_cpt_spread_node(cptab, cpt));
}
 
/**
 * allocate memory for specified CPU partition
 *   \a cptab != NULL, \a cpt is CPU partition id of \a cptab
 *   \a cptab == NULL, \a cpt is HW NUMA node id
 * The allocated memory is zeroed-out.
 */
#define LIBCFS_CPT_ALLOC_GFP(ptr, cptab, cpt, size, mask)                   \
do {                                                                        \
        LIBCFS_ALLOC_PRE((size), (mask));                                   \
        (ptr) = (size) while (0)
 
/** default numa allocator */
#define LIBCFS_CPT_ALLOC(ptr, cptab, cpt, size)                             \
        LIBCFS_CPT_ALLOC_GFP(ptr, cptab, cpt, size, GFP_NOFS)
 

so is seems very likely that we have encountered the same dead-lock scenario that is described/expected by the comment in cfs_cpt_vzalloc() above !!!

To fix this, awaiting that a Kernel API will allow us to specify both GFP_NOFS flag along with a NUMA node specification, would it be reasonable (vs performance regression) to use some other non-NUMA aware Kernel entry point like __ll_vmalloc()/vmalloc() ??
