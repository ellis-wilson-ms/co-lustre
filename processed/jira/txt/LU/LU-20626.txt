--- Description ---
During an OST HA failover, service NID 10.131.100.78@tcp moved to another OSS. Client 10.131.0.131@tcp (node002) received and logged a TCP reset from that NID after imperative-recovery (IR) processing had issued an LNet discovery GET.

The reset is reported to LNet via lnet_notify(..., alive = false), but the outstanding discovery GET is not cancelled then. Its peer remains in a state containing LNET_PEER_PING_SENT until the response MD expires. In this trace, the GET waited 215.359 seconds from send, or 209.664 seconds after the TCP reset, before Ping Unlink ran.

The OSS used an effective IR soft recovery window of 150 seconds and timed out recovery after 175 seconds. It evicted the client export before the client could rediscover the peer and issue a valid recovery connection. The eventual connect was handled without recovery/reconnect flags, so the client became EVICTED.

This is not a request to extend recovery_time_soft: that timeout is the victim. Once a known TCP reset has been reported to LNet, discovery should not remain PING_SENT beyond the server recovery window. Also, another workaround is to reduce the lnet transaction_timeout so that clients timeout the transaction early and get to recovery within the server's recovery window. 

 

Reproduction outline:

	Run I/O from the client to lustrefs-OST000c.

	Fail over the OST, moving 10.131.100.78@tcp from the old OSS to oss23.

	The new OSS mounts the target and starts imperative recovery.

	MGC sends the lustrefs-cliir log; the client creates an LNet peer and sends a discovery GET.

	SockLND receives a TCP reset for the service NID.

	The discovery GET remains outstanding until response expiry; the OSS evicts the stale export before the later retry can complete recovery.

Why this appears to be an LNet discovery state-machine gap

In the  client code:

	lnet_peer_send_ping() sends discovery GET and records an outstanding PING_SENT operation.

	SockLND detects the reset and calls lnet_notify() with alive = false. The trace proves this notification reached router.c:lnet_notify().

	The normal peer-down path updates peer status and may call the LND peer-down callback, but does not cancel the outstanding discovery MD.

	lnet_discovery_event_unlink() is the existing path that clears PING_SENT, sets PING_FAILED, and records ETIMEDOUT. Here it runs only from lnet_finalize_expired_responses() at response-MD expiry.

Thus the transport has conclusively notified LNet that the connection is down, but discovery treats the previous GET as in flight for another 209.664 seconds.

Expected behavior and requested guidance

 

For an LND-originated peer-down notification, if the matching peer has an outstanding discovery ping MD, LNet should unlink that MD immediately. The existing unlink handler can then perform:

PING_SENT -> PING_FAILED (ETIMEDOUT) -> rediscovery/recovery can proceed 

This should be limited to LND peer-down handling; it should not change normal I/O paths, MGC behavior, PtlRPC expiry values, or server recovery-timer policy.

Some Question:

	Could cancelling an outstanding discovery MD from the LND peer-down path the intended fix for this state transition?

	Is there an existing upstream issue or fix for a discovery GET that remains PING_SENT after a SockLND reset notification?

	If not, what implementation and test coverage would be preferred upstream?

Local proof-of-concept validation

After this reproduction, a local diagnostic patch was tested. It retains the exact peer during lnet_notify(..., alive=false), drops lnet_net_lock, calls the existing lnet_peer_cancel_discovery(), then releases the retained peer. It does not change PtlRPC timeout behavior.

In a later 64-client test, five clients hit PING_SENT -> TCP reset -> lnet_notify(down). All five logged Ping Unlink immediately after the down notification. The OSS completed recovery in 45 seconds:

Recovery over after 0:45, of 77 clients 77 recovered and 0 were evicted. 

This supports immediate discovery cancellation as the direction, but the local patch is a proof of concept rather than an asserted upstream-ready change.

2. Regression test added to sanity-lnet.sh

test_252a, Peer-down cancels an outstanding discovery Ping, was added to lustre/tests/sanity-lnet.sh in the LU-20626 change. It automates the same causal sequence as the manual test while preventing an ordinary transaction timeout from producing a false pass.

The test:

	Requires single-rail IPv4 TCP LNet and establishes an initial Ping to form the actual SockLND port-988 connection.

	Sets the client LNet transaction timeout to 90 seconds, then allows only 30 seconds for the peer-down cancellation assertion.

	Adds a one-shot GET drop rule on the remote node for the client-to-peer discovery GET. Because the rule runs in the remote LNet receive path, the GET has traversed SockLND before it is dropped.

	Starts lnetctl discover --force, verifies the peer state contains LNET_PEER_PING_SENT, and confirms the remote drop-rule count shows that the GET was received.

	Verifies the exact remote port-988 TCP socket is still established, then resets only that socket using ss -K.

	Requires LNET_PEER_PING_SENT to clear within 30 seconds. The first, intentionally cancelled discovery may return an error.

	Requires a new forced discovery to complete successfully after the reset.

This layout tests the desired LND-originated path: a real SocketLND connection reset causes lnet_notify(..., alive = false), which must cancel the specific outstanding discovery Ping and permit rediscovery. The 90-second LNet timeout is deliberately longer than the 30-second assertion, so a response-MD expiry cannot satisfy the test.

3. Controlled manual test and A/B result

The manual test uses the same client and service NID. It establishes a live port-988 connection, uses a one-shot remote receive-side rule to drop the next discovery GET, confirms the GET was dropped, and resets that exact TCP connection from the peer. This leaves a valid outstanding discovery response MD at the instant the client sees the real SockLND peer-down event.
