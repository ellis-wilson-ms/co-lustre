--- Description ---

The fs uses a monitoring service that pings (ip + lnet) server peers to assess health of the host fabric links, and potentially failover targets if a server is determined to have lost connectivity.  That service is started when the nodes are booted, it loads lnet.  For this test, nodes were rebooted after cables were pulled, so each server had only a single lnet nid setup.

n02/n03 are an HA pair, n02 has a single target, combined mgt/mdt0.  n03 has a single target, mdt1.  After the monitoring service runs ping checks, the servers all show peer entries for the other servers, a single nid for each server (for the 'UP' interface). --- Comment (hornc, Mon, 29 Jun 2026 22:25:17 +0000) ---
I think this is a regression in ae6d373bc6 "LU-17379 lnet: parallelize peer discovery via LNetAddPeer".

That change has LNetAddPeer() add each non-primary NID as its own peer and lets background discovery consolidate the records afterward, rather than attaching the non-primary NID to the primary peer directly. The consolidation is only armed when lnet_add_peer_ni() returns 0 for the non-primary NID:

    rc = lnet_add_peer_ni(&nids[i], &LNET_ANY_NID, true, 0);
    if (!rc) {
            if (lock_prim_nid) {
                    lp = lnet_find_peer(&nids[i]);
                    if (lp) {
                            lp->lp_merge_primary_nid = pnid;
                            lnet_peer_decref_locked(lp);
                    }
            }
            lnet_discover_peer_nid(&nids[i]);
    }

If a peer record for that non-primary NID already exists, lnet_add_peer_ni() returns -EEXIST, the if (!rc) block is skipped, lp_merge_primary_nid is never set, discovery is never kicked, and the two peers never merge.

On this system that precondition is met on every mount. The monitoring service loads LNet and pings the server NIDs before Lustre starts, so by the time the config llog runs LNetAddPeer() for kjlmo7fs-MDT0001-osp-MDT0000 a peer for 19@kfi already exists and is up to date.

Here are the relevant lines from the dk log captured after the monitoring service start, then mount (prefixes trimmed):

    lnet_peer_alloc() nid 82@kfi
    lnet_peer_attach_peer_ni() peer 82@kfi NID 82@kfi flags 0x100001
    lnet_peer_send_ping() peer 82@kfi
    lnet_peer_add() peer 19@kfi NID flags 0x1: -17
    LNetPrimaryNID() NID 82@kfi primary NID 82@kfi rc 0
    ...
    lnet_peer_push_event() Received Push 19@kfi 2
    lnet_peer_discovery_complete() Discovery complete. Dequeue peer 19@kfi
    LNetPrimaryNID() NID 19@kfi primary NID 19@kfi rc 0

We can see 82@kfi created as a locked primary with a ping sent to it, 19@kfi coming back -17 (-EEXIST) so no merge is armed, and no later set_primary_nid() that joins them. 19@kfi finishes discovery on its own ~17s later as a separate MR peer, and LNetPrimaryNID(82@kfi) keeps returning 82@kfi. The configured

{82@kfi, 19@kfi}

peer never forms.

Two things make that fatal here:

1. lock_prim_nid is on (default) and the osp device was set up on 82@kfi, so the import targets 82@kfi and, being the locked primary, it can't be re-homed or deleted.

2. 82@kfi never came up. Its link was down when LNet started so the NI was never instantiated:

    LNet: Added LNI 19@kfi [16/1024/-1/180]

(no 82@kfi LNI.) So 82@kfi is never discovered, sits alone in its own peer with no reachable NID to fall back to, and MDT0000 never connects to MDT0001.

2.15 doesn't hit this because its LNetAddPeer() attaches the non-primary NID synchronously with lnet_add_peer_ni(pnid, nids[i], mr, flags), so {82@kfi, 19@kfi} forms regardless of the pre-existing 19@kfi peer and MR send routes around the dead 82@kfi.

To fix this, in the non-primary branch of LNetAddPeer() I think we can treat -EEXIST and -EALREADY the same as a freshly created peer. Stamp lp_merge_primary_nid and force a fresh discovery (clear LNET_PEER_NIDS_UPTODATE, set LNET_PEER_FORCE_PING) so the merge runs even when the peer is already up to date.
