--- Description ---
The per-lock flock blocking state — blocking_owner, blocking_export, blocking_refs, and the lock's membership in its owning export's exp_flock_hash — is mutated by ldlm_flock_blocking_link() / ldlm_flock_blocking_unlink() while the request lock's resource lock (lr_lock) is held. The very same state is concurrently read and reference-counted by the deadlock-detection walk:

ldlm_flock_deadlock() -> obd_nid_export_for_each()
    -> ldlm_flock_lookup_cb() -> cfs_hash_lookup() / cfs_hash_put() 

which only holds the flock-hash bucket lock (hsb_lock) of the export being searched. The two paths share no common lock, so a relink performed while a walk holds an in-flight reference on the same lock corrupts both the reference count and the blocking_export pointer. Two distinct failure modes follow from this single root cause.

#2  export refcount mismatch

ldlm_export_flock_get() does class_export_get(flock->blocking_export) and ldlm_export_flock_put() does class_export_put(flock->blocking_export), bothreading the live field. If blocking_link() overwrites blocking_export (req->...blocking_export = lock->l_export) between a walk's hs_get and its matching hs_put, the walk gets export A but puts export B: export A leaks a reference, export B is over-put.
