--- Description ---
lfs support to migrate a stripe to a different OST.

This will be useful for replacing a bad stripe for the data component in an EC protected file using degraded read.

For migrating away from an OST/rack/failure domain before a scheduled maintenance event

For re-balancing of OST usage

...

We do not yet support migration of parity stripes.  That will come later as a separate feature once we decide how that should work.

rsahlberg@whamcloud.com this is great work so far!

I've been following this stuff because it would be very useful to my site, even w/o EC. 

Is the plan in the future to allow other migrate criteria for single stripe migration? I looked through the patches, and didn't see anything specific to pools, but if I missed it, my apologies. 

For instance, at our site, our setup is like this:

	create OST pool containing all storage. We can add/remove from this pool at our admin discretion

	PFL layout: pool="prod", sc=1 

If we want to retire, or do extremely percussive maintenance on a set of OSTs, we'd remove those OSTs from the prod pool for some amount of time (no new writes minus ambitious users that know Lustre),later set osp..max_create_count=0, and finally we'd want to migrate all stripes off said OSTs.

What we'd prefer to do is migrate ONLY the stripes that were on OSTs that we'd like to take offline to OSTs that are in "prod" OST pool.

So I guess as a pseudo pretend command, if I I had a file with 16 stripes, and 1 of those stripes were on an OST I'd like to move them off of, I'd issue something like: "lfs migrate -p prod /path/to/file", and then any stripes NOT in "prod" OST pool would be migrated. What happens right now is that the entire file would be rewritten.

Based on how complex this looks, I also think it's okay for first attempt if you'd have to specify the stripe you'd like to migrate, and it's up to the user/admin to select the stripes to move. So if for instance, if 3/64 stripes out of a pool are on the OSTs you want to do maintenance on, you'd have to issue 3 commands (e.g. "lfs migrate -p prod --stripe-index  /path/to/file", one for each OST)

This may be sounding like an XY problem, so here's a real (non-EC) scenario: we have 10 lustre SSUs, each SSU has 8 OSTs (and all OSTs in "prod" OST pool), that aren't shared between others; horizontally scale SSUs like normal. We need to take a single lustre SSU offline for 3 hours that has 8 OSTs. Under normal circumstances it's a PITA to migrate files off that single SSU because we cannot migrate single stripes from a file with many objects due to PFL layout.
