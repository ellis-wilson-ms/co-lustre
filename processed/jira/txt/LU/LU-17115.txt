We hit this deadlock on Lustre 2.15.8 in production, and I have pushed a b2_15 backport for review:

https://review.whamcloud.com/c/fs/lustre-release/+/68270

The fix landed on master for 2.16.0 but was never backported to b2_15, so 2.15.x is still affected. Note that later quota fixes such as lqe_is_global )" class="issue-link" data-issue-key="LU-17974">LU-17974 and LU-18516 have been backported to b2_15, so this one appears to have simply been missed rather than deliberately skipped.

Two requests, if this seems reasonable:

	Please consider adding 2.15.x to the "Affects Version" field. It is currently empty, which I suspect is why this never showed up in backport triage.

	Please consider re-evaluating the Minor priority. On our systems the effect was a complete MDT stall with no recovery path other than resetting the node.

The osd-zfs variant

The original report shows the lock inversion on ldiskfs (jbd2). We hit the same inversion on osd-zfs, where the threads wait on the ZFS transaction group instead of the ldiskfs journal, which confirms the issue is not backend specific:

qmt_delete_qid holds lqe_write_lock and waits for the txg to commit
  qmt_quotactl -> qmt_delete_qid -> osd_trans_stop
    -> txg_wait_synced -> cv_wait

qmt_dqacq0 holds an open dmu tx handle and waits for lqe_write_lock
  mdt_quota_dqacq -> qmt_dqacq -> qmt_dqacq0
    -> qmt_trans_start_with_slv -> osd_trans_start
      -> dmu_tx_assign -> dmu_tx_wait

txg_quiesce_thread waits for the open tx handles to drain
  txg_quiesce_thread -> cv_wait

The MDT pool stayed in the quiescing state (state Q in /proc/spl/kstat/zfs//txgs) indefinitely. The ZFS sync thread itself was idle and other pools on the same node kept cycling normally, so only the pool holding the MDT was affected. Every subsequent quota request piled up behind lqe_write_lock in qmt_get, and the MDT stopped answering MDS_REINT entirely.

Reproduction

The trigger needs a concurrent quota reader alongside the delete. In our case an on-demand monitor issues "lfs quota -p  " right after each quota API call, which supplies the qmt_dqacq0 side. With that reader present the stall reproduces within about 8 rounds (~7 minutes) of a create / fill to EDQUOT / delete loop on a project quota; with the reader disabled, 20 rounds pass cleanly. That single variable is the difference, so it is straightforward to demonstrate on demand.

lustre  2.15.8
zfs     2.2.9
kernel  4.18.0-553.111.1.el8_10.x86_64

Happy to provide stack dumps or run further tests if that would help.
