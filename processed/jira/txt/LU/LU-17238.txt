--- Description ---
It should be possible to cache negative xattr entries (i.e. xattr names that do not exist) for an inode on the client if it has the MDS_INODELOCK_XATTR lock locally, since a new xattr cannot be created on the inode without the MDS cancelling this lock.

There are a few xattrs that are handled differently.  See ll_xattr_cache_refill():

	XATTR_NAME_ACL_ACCESS is cached under the MDS_INODELOCK_LOOKUP lock since it is permission related

	XATTR_NAME_SOM shouldn't be cached since it may change without a lock

	XATTR_NAME_SELINUX, XATTR_NAME_SMACK are cached in the kernel already since they shouldn't be modified for files after creation

The negative cached ll_xattr_entry could store "xe_value = ERR_PTR(-ENODATA)" (or presumably whatever other error was returned for the MDS_GETXATTR for that xattr name to indicate the xattr doesn't exist.

There is also a discussion in LU-10276 to store some xattrs under a different DLM lock, which would cause problems for using listxattr() for cached xattrs that are not actually in the client cache.  In such cases it would be possible to store "xe_value = ERR_PTR(-EREMOTE)" in the xattr cache, so that they still appear in the listxattr() output but the values are not actually stored in the cache.

It appears that the lack of some xattrs in the client cache is already a problem for listxattr() today, since security.selinux is not being listed on the client, even though it is stored on the inode:

  linkea: idx=0 parent=[0x208001:0x1c08b680:0x0] name='tmp'

For the security.selinux xattr this isn't a huge problem, since most applications will just request the xattr without first listing if it exists, but it should properly be listed when requested (e.g for backups and similar).

I’ve been running into something that feels very aligned with this ticket.

00000100:00100000:45.0:1770760290.599623:0:123532:0:(client.c:2215:ptlrpc_check_set()) Completed RPC req@ffff8ca1db48f080 pname:cluuid:pid:xid:nid:opc:job preprocessannot:138c256d-14c7-4617-b592-c29b3074f526:123532:1855645481035136:10.0.2.52@o2ib5:49:15468754

 

From what I can tell, these are checks for:

	system.posix_acl_access

	system.posix_acl_default

…on FIDs where no ACLs are set. The key issue seems to be: when those xattrs are absent, the clients don’t negative-cache that fact, so the same getxattr(...)=ENODATA misses keep generating RPCs. In our case it can spike to ~200K RPC/s, mostly hitting MDT0 (where the “base” directories live), and drives high load in the MDT rdpg service threads (since getxattr is handled there). We also see high inode_permission counts in MDT stats, which I assume is the kernel repeatedly re-checking perms during these path accesses (often executables being launched very frequently).

As an experiment, I set a dummy ACL + default ACL on those base directories. After doing that, the corresponding xattr values appear to get cached normally on the clients, and MDS load dropped significantly. Deeper in the tree we usually do have default ACLs, and we don’t see the same behavior there (presumably because those xattrs are present and cacheable).

So negative xattr caching (at least for these common “checked all the time” ACL xattrs) would be hugely helpful, and would avoid hacks like that.

This is on Lustre 2.15. Let me know if I’m misunderstanding what’s happening here, or if there’s a better workaround I should be looking at.

--- Comment (JIRAUSER19589, Wed, 1 Apr 2026 16:01:03 +0000) ---
The ticket mentions that security.selinux is not a problem for listxattr in general, but it is still a problem for exposure to deadlocks (LU-9193) due to making a second getxattr intent call before calling ll_lookup_finish_locks, when you have some clients with SELinux enabled and some with SELinux disabled. We observe that if a client with SELinux Permissive/Enforced looks up a file created by a client with SELinux Disabled, the prepack added by LU-9193 (and presumably by LU-18095) will not return anything as there is no such xattr, but we cannot cache that result due to lacking xattr negative cache. In this case, we are still exposed to the deadlock mentioned in LU-9193, which we have observed under heavy contention/LDLM load.

I imagine for this fix we will also need a way to signal that a prepack was attempted but the xattr was not found.

I am going to look into implementing this to prevent the issue - please let me know if anyone has specific thoughts. I'm a bit concerned by the statement "It appears that the lack of some xattrs in the client cache is already a problem for listxattr() today, since security.selinux is not being listed on the client, even though it is stored on the inode". It sounds like we might have to make sure security.selinux is being cached even in the case where it exists.
