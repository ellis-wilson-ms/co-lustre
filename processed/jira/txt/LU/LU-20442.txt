--- Comment (adilger, Tue, 21 Jul 2026 23:14:32 +0000) ---
jinshanx there are potentially already some tools that could be used here instead of adding new per-FID stats:

	the lljobstat(8) command is in all recent releases will generate "top-like" output for jobs generating RPCs on the local server to identify which jobs are creating a high load on the server (a distributed version is at https://github.com/DDNeu/global-lustre-jobstats as well).  This is usually enough to identify the problematic application, though it won't tell you which files/objects are being used.

	the ofd_access_log_reader (ALR) utility already exists to provide per-object IO information.  It uses a lockless kernel ring buffer (producer consumer model) that logs reads/writes to all OST objects with start/end offset, bytes, segment count, timestamp. it could be used to generate "heat" or "top" metrics for OST objects with aggregation, or potentially reformatted so that it can be streamed into other visualization tools.

I'm not against adding "heat" stats directly to the OFD and MDD, but this also adds potential issues with persistent memory usage, stats cleanup, etc.
