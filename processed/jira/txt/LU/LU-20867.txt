--- Comment (adilger, Fri, 2 Oct 2026 13:34:03 +0000) ---
Analysis of the hang (sessions 8082e408 and 83e643f3):

The client is not hung in the test itself but in the stat from "[[ -f $DIR/this_is_c0 ]]" after remounting with the c0 key: ll_getattr_dentry() -> cl_glimpse_lock() waits forever because the OSC import can never establish a GSS context.  lgss_keyring retries ctx init every few seconds and gets GSS_S_FAILURE (gss err d0000) from the OSS (and in 83e643f3 also from MDT0001/MDT0003 on MDS2).

On those servers lsvcgssd handles the SK ctx init, sees that the nodemap hash sent by the client (c0, gssonly_identification) differs from the nodemap inferred from the client NID, and calls nodemap_lookup_by_sha() (lustre/utils/gss/svcgssd_proc.c).  That sends OBD_IOC_NODEMAP/LCFG_NODEMAP_LOOKUP_SHA to data.ioc_dev = srv_ioc_dev, but the ioctl reaches the wrong obd device:

OSS:  ofd_iocontrol()) lustre-OST0000: iocontrol from 'lsvcgssd' cmd=c00866c5 _IOWR('f', 197, 8) unrecognized: rc = -25
OSS:  obd_iocontrol()) lustre-OST0006-osd: no obd_iocontrol operation
MDS2: obd_iocontrol()) lustre-MDT0003-osd: no obd_iocontrol operation

so the lookup fails, lsvcgssd rejects the context, and gss_svc_upcall_handle_init() reports "failed to get entry from rsi cache: rc = -43" for every attempt.

Cause: srv_ioc_dev is the obd index of the "OSS"/"MDS" device, resolved once by set_srv_ioc_dev() (at daemon start, or on the first lookup) and then cached for the lifetime of lsvcgssd.  But server_stop_servers() (lustre/target/tgt_mount.c) cleans up the OSS/MDS obd when the last OST/MDT on the node is unmounted, and the next mount creates it again, possibly at a different index that is then reused by an OST/OSD device.  lsvcgssd is not restarted across server remounts (pid 9815 on the OSS in 8082e408 is the instance started at boot; later "lsvcgssd" starts in test-framework exit via gssd_init_unique()), and sanity-sec test_70 and test_75b unmount and remount all OSTs before test_79.  Once any earlier test has made lsvcgssd resolve srv_ioc_dev, test_79's lookups go to a stale index.  The MGS node is not affected because it looks up the "MGS" device, which stays put.

The failure is intermittent because it needs both an earlier lookup that caches srv_ioc_dev on that server and the OSS/MDS obd coming back at a different index after the remount.

Possible fixes:

	in lsvcgssd, resolve the device by name (OBD_IOC_NAME2DEV) for each nodemap_lookup_by_sha() call instead of caching srv_ioc_dev, or re-resolve and retry once when the ioctl fails with ENOTTY/EINVAL; and/or

	make the OBD_IOC_NODEMAP lookup independent of a specific device index (e.g. accept it on any server target device, or address it by name).

The test itself should also not wait forever on a failed context negotiation; a bounded wait on the stat would turn this into a quick FAIL instead of a 90-minute session TIMEOUT.

--- Comment (adilger, Fri, 2 Oct 2026 17:59:35 +0000) ---
sebastien, could you please confirm the analysis above and comment on the proposed fixes?

Summary: this looks like a code defect in lsvcgssd rather than a test defect.  test_79 only exposes it:

	lsvcgssd caches the "OSS"/"MDS" obd index in srv_ioc_dev for the life of the daemon, but server_stop_servers() destroys that obd when the last target on the node is unmounted, and the next mount can recreate it at a different index.  lsvcgssd normally keeps running across target unmount/remount (failover, maintenance), so in production too, after such a remount every client needing nodemap_lookup_by_sha() (gssonly_identification, or an SSK key whose nodemap differs from the NID nodemap) would be refused on that server until lsvcgssd is restarted.

	The client cannot recover by itself: it already retries ctx negotiation every few seconds, but the server fails the same way each time because of the stale index.

Proposed fixes:

	lsvcgssd: resolve the device by name (OBD_IOC_NAME2DEV) for each nodemap_lookup_by_sha() call instead of caching srv_ioc_dev, or re-resolve and retry once if the ioctl fails.  The lookup only happens at context setup, so the extra ioctl is negligible.

	sanity-sec test_79: bound the wait after the remounts, so a failed context negotiation gives a quick FAIL instead of a 90-minute session TIMEOUT.

Does that match your understanding, and is there a reason srv_ioc_dev needs to be cached?

--- Comment (sebastien, Mon, 5 Oct 2026 06:29:21 +0000) ---
Yes, this analysis makes sense. But I still think it is better to cache srv_ioc_dev. Updating it in case of ioctl failure is not very expensive, but fetching it for every nodemap_lookup_by_sha() call is not exactly cheap. In some environments with lots of clients in constantly changing nodemaps, context setup can happen very frequently.
