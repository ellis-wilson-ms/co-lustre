--- Comment (adilger, Fri, 9 Oct 2026 10:22:49 +0000) ---
Some thoughts on how to implement this:

	each file should have a common suffix like .ltsh (Lustre Test Shell) so it can ignore helper scripts, editor backup files, etc. and if we start having .ltpy or .ltrs subtests they can also be identified

	useful information should be encoded in a comment at the start of each test fragment:
	
		minimum number of OSTs, MDTs, etc. needed

		minimum client or server version to run test (replaces monolithic lustre/tests/except/$TESTSUITE.ex files)

		minimum free filesystem blocks and inodes

		filesystem should be mounted or unmounted at start of subtest

		filesystem will be reformatted at start/end of subtest

	
	

IMHO, it should be possible to have multiple related subtests in a single file, for example because they need a common set of helper functions or test configuration that shouldn't be recreated by each subtest.

I think the best way to start using this is to add the infrastructure to test-framework.sh (or possibly another test-fragments.sh file?) that can load subtests from a $TESTSUITE.d/ directory (e.g. lustre/tests/sanity.d/) and then start adding new subtests there.  We can incrementally move existing subtests to be test fragments, but this would likely need to be done one/few per patch because of the two review-dne-subtest-change sessions running each subtest in a loop for 30m.  If we split all 1100 of the sanity.sh subtests into fragments in a single patch it would launch 2200 sessions and consume 45 days of runtime and probably not be able to pass since some subtests are not robust against running in a loop...
