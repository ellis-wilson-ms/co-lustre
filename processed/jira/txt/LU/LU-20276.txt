--- Comment (emoly.liu, Wed, 2 Sep 2026 09:16:14 +0000) ---
Here is some AI's analysis of this OOM crash issue:

test_70b and test_71c are NOT the actual trigger — they're just innocent bystanders. The real culprit is test_56b (which runs earlier in the same sanityn.sh suite). test_56b creates a (16TB × OSTCOUNT) sparse, 2000-overstriped file via llverdev, writing 4KB chunks every 1GB offset (partial mode). When this massive sparse file is destroyed at test exit via stack_trap "rm -f", the client sends destroy RPCs and moves on quickly, but on the OSS the destroy is processed inline on the ptlrpc service thread: osd_trans_stop() → osd_unlinked_list_emptify() → osd_unlinked_object_free() → dmu_free_long_range(). This dirties the entire indirect block tree for each OST object, generating massive unreclaimable slab allocations (dbuf_dirty_record_t, dmu_buf_impl_t, zio_buf_comb_*, zfs_btree_leaf_cache, etc.) that silently exhaust free memory on the ~4GB test VM.

A userspace process (NetworkManager) does an ordinary page fault, finds no free pages, and invokes the OOM killer after ZFS consumed it all.

Reducing llverdev size in test_56b for ZFS would prevent this OOM crash, but we still need a thorough fix.

--- Comment (behlendorf, Wed, 23 Sep 2026 00:32:59 +0000) ---
The OOM being caused by the previous large file free is very helpful.  There was work done in https://github.com/openzfs/zfs/pull/16722  to improve this, those changes are in the 2.4.x releases but they're not a complete fix.  Although, if you read the top comment of the PR there's a good explanation of what the memory consumers are and why.  Anyway, clearly that change is insufficient for the test VMs.

There are a few potentially easy workarounds I'd suggest trying first.

1. Add a "zpool wait -t free" to the large file freeing test case on the OSS.  At a minimum adding it to the end of the test will make sure any background freeing has completed before moving on the to the next test.  If the OOM is happening earlier, that of course won't help.

2. ZFS used to more aggressively throttle the frees, but that limit has been periodically relaxed in the name of performance (see https://github.com/openzfs/zfs/pull/10000 and https://github.com/openzfs/zfs/pull/13938).  The 10000 PR is old enough it wouldn't explain why you're seeing this now, introduced in the zfs-2.0 release, but the 13938 PR change first appears as of the zfs-2.2 release and maybe lines up a bit better.  It may be interesting to try setting "zfs_per_txg_dirty_frees_percent " back to it's previous default of 5 (it was increased to 30).  That will help throttle the frees.  To set it "echo 5 >/sys/module/zfs/parameters/zfs_per_txg_dirty_frees_percent".

3. If that isn't sufficient it may be because the blocks are being freed by a single "dmu_tx_hold_free".  Today there's no mechanism to throttle at a granularity less than a single hold, so if it's done with a single call you can go past the limit.  Breaking this up in to multiple holds in the OSD should allow the throttle to behave better and limit the memory usage if neither 1) of 2) above are sufficient.
