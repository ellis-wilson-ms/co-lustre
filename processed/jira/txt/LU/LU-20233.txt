--- Description ---
There are several reports hitting various assertions in ldlm_lock_put() which show that lock is either alive or not finished properly upon last put. This can be result of extra ldlm_lock_put() for example, also it looks like this can be also result of wrong handling of l_readers/l_writers which causes ldlm_lock_decref_internal() to skip blocking AST call for lock.

--- Comment (tappro, Fri, 8 May 2026 11:11:03 +0000) ---
One particular case goes always via the same path:

mdc_finish_intent_lock()>ldlm_lock_decref_and_cancel()>ldlm_lock_put()

which happens in that area:

if (ldlm_lock_match(NULL, LDLM_FL_BLOCK_GRANTED, NULL,
    LDLM_IBITS, &policy, LCK_NL, 0, &old_lock)) {
        ldlm_lock_decref_and_cancel(lockh, it->it_lock_mode);
...

it looks like call to ldlm_lock_match() leaves lock in non-appropriate state so consequent call to ldlm_lock_decref_and_cancel() ended up with assertions.

It seem there is problem with wrong lock mode which causes wrong counter for l_readers/l_writers counters, so they are not zeroed both at last put.

In ldlm_lock_match_with_skip():

ldlm_lock_match_with_skip(..., enum ldlm_mode mode, ...) {
    ### after queue_search we have lock found
    matched = lock ? mode : 0;
    ...
    
    ldlm_lock_decref_internal(lock, mode);
    ...
    return matched;
}

Note, that mode is parameter value passed from caller, not related to real mode of lock returned from queue_search().

It is not correct in two places: surprisingly it is correct because mode is updated via pointer from inside of queue_search()->lock_match()

	matched is set to mode from parameters which can be not the same as one of just found lock, so it returns wrong mode to caller.

	ldlm_lock_decref_internal() is using also mode from parameters but not real lock mode

Now look at the mode which is being used in that particular call from mdc_finish_intent_lock() - it is LCK_NL which means no sense to be used neither as matched to return, nor as mode for ldlm_lock_decref. Moreover this particular call is the unique one, it uses special API for ldlm_lock_match() call - with struct ldlm_namespace *ns = NULL

It is handled in specific way:

    if (ns == NULL) {
        data.lmd_old = ldlm_handle2lock(lockh);
        LASSERT(data.lmd_old != NULL);
        ns = ldlm_lock_to_ns(data.lmd_old);
        res_id = &data.lmd_old->l_resource->lr_name;
        type = data.lmd_old->l_resource->lr_type;
        *data.lmd_mode = data.lmd_old->l_req_mode;
    }

so real lock data is taken from lock itself, not from function parameters, including lock mode. Therefore if we pass write lock here then matched will be set to LCK_NL anyway, and ldlm_lock_decref() will decrement l_readers due to LCK_NL but not l_writers as it is needed.

P.S. my analysis above is not correct, because data.lmd_mode is a pointer and it points to mode in parameters, so mode is updated with correct value.
