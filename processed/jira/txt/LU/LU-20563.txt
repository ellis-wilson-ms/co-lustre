--- Description ---
Recently encountered this issue at a site - 

When client reaches IDLE state, a new rpc request triggers call to ptlrpc_reconnect_if_idle() and sets state as NEW and calls ptlrpc_connect_import_locked(). 

Most of the OST imports progresses fine from here but for some OST imports, in ptlrpc_connect_import_locked() , it goes in 3rd elseif condition and bails out from here with EALREADY and never recovers.

if (imp->imp_state == LUSTRE_IMP_CLOSED) {
        spin_unlock(&imp->imp_lock);
        CERROR("can't connect to a closed import\n");
        RETURN(-EINVAL);
    } else if (imp->imp_state == LUSTRE_IMP_FULL) {
        spin_unlock(&imp->imp_lock);
        CERROR("already connected\n");
        RETURN(0);
    } else if (imp->imp_state == LUSTRE_IMP_CONNECTING ||
           imp->imp_state == LUSTRE_IMP_EVICTED ||
           imp->imp_connected) {           imp_lock);
        CERROR("already connecting\n");
        RETURN(-EALREADY);
    } 

The investigation suggests it happens because for the problematic OST import, imp->imp_connected is set.

From code review, we see that it could happen because of an unsafe bit unset (without acquiring spinlock) of the imp_no_cached_data in another code path (introduced by this commit). But this unsafe unset can mess around with other bits of the flag too.

It is a generic race, but ARM64’s weaker ordering and different timing can make it easier to hit than x86.
