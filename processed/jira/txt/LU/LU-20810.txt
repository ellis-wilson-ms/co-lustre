--- Comment (JIRAUSER20209, Wed, 23 Sep 2026 08:33:37 +0000) ---
Analysis

Some concurrent call sites for peer discovery could still enqueue a peer into the `ln_dc_request` queue after `lnet_peer_discovery_stop()` has already drained and asserted the discovery queue is empty. This can cause the extra reference taken by `lnet_peer_queue_for_discovery()` to never be released, leading to an `lnet_peer` leak, and an attached `lnet_ping_buffer` leak as well when push data had already been received, ultimately being reported as "Portals memory leaked" when the module is unloaded.

The affected interfaces include:

	`lnet_peer_push_event`

	`lnet_push_update_to_peers`

	`lnet_peer_queue_message`

	`LNetPeerDiscovered`

Since the race window is very short, the probability of hitting this issue in normal testing is extremely low. By manually adding two gate points for `lnet_peer_push_event()` and `lnet_peer_discovery_stop()` to control the timing sequence, the memory leak can be reliably reproduced.

Fix Strategy

Add a synchronization mechanism: 

Re-check `ln_dc_state == LNET_DC_STATE_RUNNING` within the same `lnet_net_lock/EX` critical section where the actual insertion operation is performed.
