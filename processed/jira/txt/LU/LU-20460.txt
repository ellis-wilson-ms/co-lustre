--- Description ---
`lctl set_param -P .srpc.flavor.X=Y` returns success but does not register an sptlrpc rule. The parameter is errorneously put into the generic params log as an LCFG_SET_PARAM record instead of the per-filesystem -sptlrpc log as an LCFG_SPTLRPC_CONF record, so the MGS never enforces it or transmits it to clients.

The equivalent lctl conf_param works and is de-facto the expected way to configure persistent sptlrpc rules today.

This bug has been noticed multiple times in the past, it appears to have been originally reported in: LU-7183, which was closed as duplicate by LU-10937. However LU-10937 has a much broader intent, including a migration towards sysfs, while the original set_param -P gap remains unfixed still.

Example:

set_param -P

[root@server1 ~]# lctl set_param -P lustre.srpc.flavor.tcp103=null
[root@server1 ~]# lctl get_param mgs.MGS.live.lustre | grep tcp103 
# Nothing, rule is not applied
[root@server1 ~]# lctl llog_print lustre-sptlrpc | grep tcp103
# Nothing
[root@server1 ~]# lctl --device MGS llog_print params | grep tcp103
- { index: 54, event: set_param, device: general, parameter: lustre.srpc.flavor.tcp103, value: null }
# Entry placed into the params log mistakenly

conf_param

[root@server1 ~]# lctl conf_param lustre.srpc.flavor.tcp103=null
[root@server1 ~]# lctl get_param mgs.MGS.live.lustre | grep tcp103
lustre.srpc.flavor.tcp103=null
# Rule is active
[root@server1 ~]# lctl llog_print lustre-sptlrpc | grep tcp103
- { index: 360, event: security, device: lustre, parameter: srpc.flavor.tcp103=null }
# Rule place into -sptlrpc log
[root@server1 ~]# lctl --device MGS llog_print params | grep tcp103 
# params log empty as expected

It would be good to fix this behaviour so that we can fully deprecate conf_param for usage in this area.
