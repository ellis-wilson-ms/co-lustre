--- Comment (laisiyao, Tue, 24 Feb 2026 07:48:51 +0000) ---
Yes, this implementation is much lightweight, and it can also support standalone MGS0. BTW the MGS replica will be started on OST nodes as well.

The backup MGS won't take over MGS0 as primary, but wait for MGS0 to come back. If MGS0 node can not get back, the administrator has two options:

	if MGS0 is standalone, recreate MGS0 and copy configuration files from other nodes to this new MGS0

	specify one server node as MSG0, and restart all server nodes

--- Comment (adilger, Thu, 26 Feb 2026 00:59:38 +0000) ---
One of the future goals for FTM is that common infrastructure could be used to store databases for MDT0000 to make the filesystem more robust in case of failure and to allow MDT0000 removal from the filesystem for hardware replacement (LU-18823).  This covers information like quota limits (QMT), FLDB, flock, etc.  While those databases also do not change rapidly, they cannot be "offline" for a long time if a server has a hardware problem.  Do you have a proposal to handle replicating these databases without RAFT?

It would be possible to do this by e.g. expanding the FLDB replication to copy the full table to all nodes (it is relatively small, and most targets already have a good fraction of the table) and developing a mechanism for transfer of the master service, but it would need similar efforts for all of this functionality.

--- Comment (laisiyao, Thu, 26 Feb 2026 02:10:23 +0000) ---
IMHO FLDB and Quota still need RAFT to be fault tolerant, since it's the standard way to implement replicated services.  As for MGS, it's different from other services: the MGS is started before RAFT cluster is setup, and MDTs/OSTs mkfs with the MGS nid set, and they need the configuration from MGS to fully setup (possibly not if they have backup in local storage).  So even as we implement MGS upon RAFT, the MGS0 is still not fault-tolerant, the final result is the same as this implementation.

--- Comment (laisiyao, Thu, 26 Feb 2026 05:11:42 +0000) ---
One possible way to implement fault tolerant MGS0 is as below:

	start MGS0 and targets like before

	when RAFT cluster is up, and leader elected, MGS0 notify all targets to switch to RAFT leader as MGS

But even with this, it's better to sync the configuration files and IR data via MGC like this patch set because it's more lightweight.  And this involves a few changes:

	MGS0 needs to get the nids of RAFT leader

	MGC on targets need to be stopped and restart with RAFT leader nids as connection nids, and targets need to register again to ensure target configuration files are created

	the config change commands like 'lctl set_param -p' that run on mgs host need to be forwarded to RAFT leader

--- Comment (adilger, Thu, 26 Feb 2026 19:59:41 +0000) ---

That would only affect the initial target registration?  It should be enough that the targets specify multiple MGS NIDs on startup, so that at least one of them is running when they try to connect. --- Comment (adilger, Thu, 9 Apr 2026 19:16:57 +0000) ---
each target has the config for itself, but not configs for other targets.

It would be useful to extend the MGS code so that if the primary MGT does not have a config llog for a target, but the target has a copy of its config log, that the primary copy the config log to the primary MGT.  It would be enough to check this once at startup time, and would not be done if --writeconf was done and the config logs are being recreated.  That ensures the primary MGT always has a full set of the target config logs (in case they lose them for some reason).

The backup MGS won't take over MGS0 as primary, but wait for MGS0 to come back. If MGS0 node can not get back, the administrator ... specify one server node as MSG0, and restart all server nodes

After the "read only" replication is working, having some (manual) interface to declare which MGT replica is "primary" would allow this to be changed in case of emergency (e.g. MGT0 is lost and OSTs or MDTs need to be added to the filesystem).  The "primary" MGT would stay the same until it is changed again manually, and the primary could only be changed away from a running MGT if the new target had synced all logs from the current primary.  That is not quite "RAFT" yet, but allows handling things manually in an emergency.  Implementing "automatic" primary elections via some other mechanism could be done afterward.  We don't need to handle super complex/dynamic MGS configuration, so getting the MGS logs in sync and then transferring control should be relatively straight forward. 

However, I don't think it is OK to restart all servers to change the primary MGS.  There should be some way to handle this at runtime (e.g. command run on targets to update primary MGS NID).  I'm not very keen to have the new MGS automatically send an RPC to the targets to change the primary MGS NID, since that opens up the door to broken nodes fighting over control of the primary MGS if RAFT is not in use.

It would be useful to forward other config changes from the failover MGS to the primary MGS, so that the admin does not need to figure out which node is running the primary MGS.

One open question is how do clients learn about the running MGS replicas?  Would the clients list a dozen MGS NIDs on the command line or use DNS round-robin hostnames (LU-19412)?
