--- Description ---
Migrating a regular file with hard links does not reliably lock the parents of its other links before mdd_migrate() rewrites their entries. There are two gaps in mdt_migrate_links_lock():

1. The loop over the linkEA runs while ldata.ld_lee && !rc. mdt_migrate_link_lock() returns 1 when it takes a LOOKUP lock on a link parent on another MDT, so the loop stops after the first such parent and the remaining link parents are never locked. This dates from LU-4684 (commit 169738e30a7e "LU-4684 migrate: migrate striped directory").

2. The linkEA is read before the source object is locked. A link(), or a cross-directory file rename that does not take the BFL (same MDT since LU-17426, and cross-MDT with LU-20831), can add a link parent in that window. Migration never locks it, but mdd_migrate() rereads the linkEA under the source lock and updates that entry anyway. That parent is changed without its UPDATE lock, and a client's cached LOOKUP lock on the name can be left pointing at the destroyed source.

Both were found while reviewing LU-20831. Gap 2 was reproduced on a 4-MDT ldiskfs setup only with an injected delay after the linkEA read; neither has been seen in CI.

A candidate fix was in patchset 10 of https://review.whamcloud.com/c/fs/lustre-release/+/69203/10 (lock every link parent; once the source is locked, reread the linkEA and retry from the parent locks if it names an unlocked link parent). It was removed from that change because the issue predates it.
