--- Comment (hornc, Mon, 10 Aug 2026 22:06:37 +0000) ---
I think this is a dupe of LU-18041.

`lustre_start_mgc()` parses the NID correctly. There is no "Can't parse NID" message, and the first NID check at `obd_mount.c:322` passed. The failure is in the second loop, which counts only the NIDs that `class_add_uuid()` accepts:

 

rc = class_add_uuid(nidstr, &nid);
if (rc == 0) ++i;

 

`class_add_uuid()` rejects the NID silently:

 

if (strlen(uuid) > UUID_MAX - 1)
        return -EOVERFLOW;

 

`UUID_MAX` is 40, because `struct obd_uuid` is `char[40]`. So the limit is 39 characters. `LNET_NIDSTR_SIZE` is 64, which is why the string got this far.

 

	Address `fd33:3981:3213:f010:0:5254:1b:cfa4` = 34 characters.

	With `@tcp` the NID is 38 characters, so it fits. All other IPv6 mounts in that session passed.

	test_73e is the only test that uses `${NETTYPE}50`. `@tcp50` makes the NID exactly {}40{} characters, which is one over the limit.

 

The net number tips it over, not the address.
