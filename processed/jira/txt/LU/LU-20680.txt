--- Description ---
Problem

Two ARM64 GB300 clients running Lustre 2.15.90_OCI_v5 hit a SockLND scheduler LBUG while receiving delayed LNet PUT payloads:

LASSERT(conn->ksnc_rx_nkiov > 0)

At the failure, the connection was live and in SOCKNAL_RX_LNET_PAYLOAD. Subsequent kdump memory showed a valid receive vector with ksnc_rx_nkiov = 1, which rules out a malformed or zero-length payload.

Root cause

ksocknal_process_receive() calls lnet_parse(), which can defer the receive and invoke ksocknal_recv() asynchronously. The callback initializes the receive tuple (message, lengths, iov/kiov pointers, and nkiov), then writes ksnc_rx_state = SOCKNAL_RX_LNET_PAYLOAD while holding kss_lock.

The scheduler reads ksnc_rx_state without that lock. On weakly ordered ARM64, it can observe SOCKNAL_RX_LNET_PAYLOAD while still observing stale receive-tuple data, including ksnc_rx_nkiov = 0. It then reaches ksocknal_recv_kiov() and triggers the assertion.

Proposed fix

Publish SOCKNAL_RX_LNET_PAYLOAD with smp_store_release() after the receive tuple is initialized. In ksocknal_process_receive(), consume the state with smp_load_acquire() and use that acquired value for the state check. This guarantees that observing RX_LNET_PAYLOAD also makes the preceding tuple initialization visible.
