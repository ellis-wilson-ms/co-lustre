Two contended resources drive it:

*BFL global rename lock `[0x200000004:0x1:0x0]` (MDT0000):*

	held `EX` by *13831* (`mdt_reint_migrate`) — which is then off blocked in

  `osp_md_object_lock` acquiring the *remote parent* on the peer MDT;

	6524 / 6525 / 13860 queue behind it in `mdt_rename_lock`.

*Directory stripe object `[0x240000404:0xd3cf:0x0]` (a dir mastered on MDT0001):*

`crash` on the two namespaces for this FID:

	resource `d465d000`: `lr_granted` = *pid 14094, `LCK_EX`, writer* (the

  `setxattr`/`dir_layout_update` migration); `lr_waiting` = **the 8 getattr locks,

  `PR`**. → getattr readers are starved behind the migration's EX.

	resource `cc901600` (same FID, home-MDT side): one `lr_granted` = **`LCK_EX`,

  `l_export` set, `l_blocking_ast = tgt_blocking_ast`, readers=writers=0** (pid 13844,

  an idle `ll_ost_out00_00`). → a **cross-MDT EX lock exported to the peer MDT's OSP,

  cached and idle**, that nobody revokes.

`pid 13844` (the OUT thread that owns that exported EX) is back *idle* in

`ptlrpc_wait_event` — its op finished, the lock is just cached — so revoking it needs a

blocking AST to be serviced. But *every* MDT service thread — `mdt00_*`,

`mdt_io00_`, and the `mdt_out00_` OUT threads that process cross-MDT lock/OUT RPCs —

is already blocked in `ldlm_completion_ast`.

	
	
		Mechanism

	
	

A cross-MDT *lock-ordering + service-thread-starvation* deadlock:

1. `mdt_reint_migrate` (13831) takes the *BFL rename lock* and then blocks acquiring a

   *remote* parent/stripe lock via `osp_md_object_lock` (a lock request sent to the

   peer MDT's OUT service).

2. `mdt_reint_setxattr → mdt_dir_layout_update` migration (14094) holds a directory

   stripe *EX* lock and blocks acquiring *another* cross-MDT stripe lock; getattr

   readers pile up behind its EX → client `i_rwsem` pileup.

3. Granting/cancelling those cross-MDT locks requires the peer MDT's OUT/AST RPCs to be

   serviced — but all MDT service threads are already parked in `ldlm_completion_ast`

   waiting on cross-MDT locks. *No thread is left to break the cycle.* Nothing makes

   progress for the rest of the run.

4. The stuck distributed transaction eventually aborts and dies in

   `out_tx_index_delete_undo() … rc = -524` (*LU-18289*), LBUGing the MDS.

Note the two migration paths lock inconsistently: `mdt_reint_migrate` serializes under

the *BFL rename lock*, but the `mdt_reint_setxattr`/`mdt_dir_layout_update` layout

path does *not* take it — so two concurrent directory migrations (and a rename) can

interleave their cross-MDT object-lock acquisition and invert.

	
	
		Root of the inversion (in the source)

	
	

`mdt_reint_migrate()` and `mdt_reint_rename()` take the global rename (BFL) lock

(`mdt_rename_lock()` on `LUSTRE_BFL_FID`) before they take object/stripe locks. But

the layout-change path — `mdt_reint_setxattr() → mdt_dir_layout_update()` (and the

restripe thread via `mdt_restripe_layout_update()`) — calls

`mdt_object_stripes_lock(..., LCK_EX)` on the directory and its (cross-MDT) stripes

*without taking the BFL at all*. So a directory layout change and a concurrent

rename/migrate have *no common serialization point* and can acquire their cross-MDT

stripe locks in inverted order; the finite `mdt`/`mdt_out` service-thread pool then

starves in `ldlm_completion_ast` and nothing is left to service the OUT/AST RPCs that

would break the cycle.

	
	
		Proposed fix (RFC — branch `LU-17936-dir-layout-bfl`)

	
	

Give `mdt_dir_layout_update()` the same ordering as migrate/rename: take the BFL

(`mdt_rename_lock()`) first, before locking the directory and its stripes, and release

it on the way out. (Also exports `mdt_rename_lock()`/`mdt_rename_unlock()` from

`mdt_reint.c`.) With this, the layout change blocks at the BFL before grabbing any

stripe EX lock, so it can no longer hold the stripe locks that a BFL-holding

migrate — and the getattr readers — are waiting behind, and this exact cycle cannot

form. Both `mdt_dir_layout_update()` callers reach it without the BFL (or any

persistent object lock) already held, so there is no self-nesting.

    lustre/mdt/mdt_xattr.c    | +BFL lock/unlock around the stripe locking

    lustre/mdt/mdt_reint.c    | un-static mdt_rename_lock()/mdt_rename_unlock()

    lustre/mdt/mdt_internal.h | prototypes

Trade-off: this serialises cross-MDT directory layout changes against renames/migrates

(a BFL-EX per layout change). Acceptable for correctness; a trylock/two-phase variant

(cf. LU-17427) could reclaim parallelism later. An orthogonal, complementary direction

is to stop the getattr/statahead path from holding an MDT service thread blocked behind

a migration EX (non-blocking enqueue + restart, cf. LU-15562), which would relieve the

thread-starvation half of the wedge.

	
	
		Regression test — none shipped (deliberately)

	
	

I could not build a test that reliably fails without the fix, so none is included

(a test that passes both ways is worse than none):

	The failure is *multi-party* — a cross-MDT lock inversion plus MDT

  service-thread starvation — not a clean 2-lock A↔B, so a single `fail_loc` can't

  force it.

	A racer-style stress version (tried: striped dir + concurrent layout-change /

  cross-MDT rename / getattr storm, MDS thread pools shrunk, 60s and 300s) **passed

  on the unfixed build** on a 2-MDT rocky10 VM — racer is racy and this deadlock is

  intermittent.

	A BFL-hold timing probe can't isolate this path either: `lfs migrate` on a

  directory takes the BFL via `mdt_reint_migrate()` regardless of the fix, so it

  blocks on a held BFL with or without the `mdt_dir_layout_update()` change.

It is exercised (intermittently) by the existing *racer* suite on DNE.

	
	
		Validation status — HONEST

	
	

	*Builds clean* against the rocky10 kernel 6.12-rhel10.1 (`ltvm build lustre

  rocky10`, no warnings/errors on the touched files).

	*Runtime safety checked — no regression.* On a 2-MDT rocky10 VM, the fixed

  modules behave *identically to unfixed master* on the path the fix touches:

  files-only dir shrink (`lfs migrate -c1`) works (count 2→1, entries intact);

  cross-MDT subdir migrate works; a dir-with-subdirs shrink shows the same

  pre-existing "migration was interrupted, run lfs migrate again to finish"

  multi-pass behaviour on *both* builds (not caused by the fix). Concurrent

  restripe+rename+ls stayed responsive.

	*Deadlock fix itself is NOT runtime-proven* — the deadlock did not reproduce in

  bounded stress runs, so there is no "hangs unfixed → passes fixed" demonstration.

  The fix rests on the crash-dump lock evidence + the existing migrate/rename BFL

  pattern, and needs DNE-expert review and autotest soak (`testlist=racer`).

(ltvm note: the rocky10 kernel build rejects every module via BTF validation

— `failed to validate module BTF: -22`, a pahole/toolchain mismatch, not lustre —

worked around by stripping the `.BTF` section from the modules before load.)

	
	
		Fix direction

	
	

This is a design-level DNE locking fix; the RFC above is the minimal targeted form.

	
	
		Related

	
	

	*LU-18289* — `out_tx_index_delete_undo() … rc = -524`: the LBUG this deadlock aborts

  into (same run, same server dump). Should be fixed/tracked together.

	LU-15491 (local rename fid ordering) and LU-16958 (client layout-mutex) are already in

  this build and do *not* cover this cross-MDT/service-thread case.
