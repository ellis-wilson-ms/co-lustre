--- Comment (JIRAUSER19464, Fri, 14 Aug 2026 00:07:58 +0000) ---
adilger  the real reason for this failure is that

"The real reason for the failure is that in test-5, OBD_FAIL_FID_IGIF only suppressed LinkEA and FID-in-dirent, but still wrote the Normal FID into trusted.lma. Consequently, when LFSCK ran after the backup/restore reformat, it detected the existing trusted.lma and reconstructed the LinkEA and dirent using the Normal FID instead of upgrading the file to an IGIF FID. Because the file remained a Normal FID object and the MDT was started without OI scrub, the OI table lacked an entry for this Normal FID, causing subsequent FID-to-path lookups (lfs fid2path) to fail."

 

(The test occasionally passed previously because if the inode mapping happened to remain in OSD's in-memory OI cache (oti_cache), it bypassed the on-disk OI table check; once evicted from cache, subsequent lfs fid2path lookups failed with error 13).

So the patch suppress writing the FID to trusted.lma as well.  But after this fix, it failed with

The root cause in lfsck_prep 1 1 1 (analyze by gemini, and looks correct to me)

	When createmany -d $DIR/$tdir/d 1 creates directory d0, osd_create() creates the backend inode on disk without trusted.lma. However, the MDT still replies to the client with the Normal FID allocated for the mkdir RPC. The client VFS instantiates and caches the dentry "d0" bound to this Normal FID.

	Immediately on the next step, createmany -m $DIR/$tdir/d0/f 1 tries to create file f0 inside d0.

	The client VFS path walk traverses into d0 and issues an IT_LOOKUP "d0" RPC to the MDT.

	When the MDT looks up d0 on disk, it finds no trusted.lma, so osd_iget_fid() dynamically constructs an IGIF FID [0x0:ino_d0:gen_d0] and returns it in the lookup reply.

	The client receives the IGIF FID from the MDT, which collides with the cached dentry in client dcache (already bound to the Normal FID inode). This dentry alias mismatch causes the lookup to fail with -ENOENT (rc = -2).

To make MDT reply igif FID with this fail_loc will need some efforts.  So I wonder do we still support IGIF now? otherwise can we skip this test? It seems not worth the efforts.
