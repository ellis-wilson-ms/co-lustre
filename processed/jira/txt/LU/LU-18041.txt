--- Comment (simmonsja, Fri, 22 May 2026 19:59:24 +0000) ---
Mikhail wanted a nice summary of the problem and the purposed solutions so it can be discussed.

The main reason for this work is that we have a unique node identifier to NID list mapping. Currently this mapping uses for the node identifier the primary NID. This approach has two problems. One is that the primary NID can overflow obd_uuid and second in environments that have rolling IP addresses means that the primary NID is not a permanent node identifier.  We could use the target UUID. FInally we can use the mgc UUID.

1) primary NID as unique node identifier

    pro: consistent even across reboots in some environment

    con: Other environments the primary NID is not even consistent during uptime. No guaranteed it same after a reboot as well in such a case.

2) Use the target UUID  (MDTxxxx/OSTxxxx : [nidlist] )

    pro: always consistent server side. Also we have some elements of this behavior in the code already.

    cons: many mappings are duplicates if targets shares the same node

               For clients we don't have consistent target UUIDs.  Maybe if we have a export connect flag and cache on the MGS the first UUIDs it received for a                     client.  Then if it exist send the MGS cached UUID back to the client for its use.

3) Using the mgc UUID

    pro: consistent during the uptime of the node

    con: can change if the node reboots

            Now we can resolve the UUID issue for server nodes by transmitting to the MGS the mgc UUID on first mount. The clients has the same issue as using a target UUID case so the same possible solution.

--- Comment (adilger, Sat, 23 May 2026 01:14:13 +0000) ---
The client UUID reported to the servers MUST be unique across unmount/remount and between different mounts on the same client node.  Otherwise the servers will become confused if a client mounts the same filesystem twice (this happens a LOT today with containers). 

Clients already use a unique randomly-generated "real" UUID when they are connecting to servers, this has nothing to do with the client NID:

client# lctl dl | grep MDT
  3 UP mdc myth-MDT0000-mdc-ffff8cec414bb000 2dd451a5-bb30-4f53-9eb3-e31e45bb7fce 5
  9 UP mdc myth-MDT0001-mdc-ffff8cec414bb000 2dd451a5-bb30-4f53-9eb3-e31e45bb7fce 5
client# lctl get_param llite.*.uuid
llite.myth-ffff8cec414bb000.uuid=2dd451a5-bb30-4f53-9eb3-e31e45bb7fce
mds# lctl get_param mdt.*.exports.*.uuid
mdt.myth-MDT0000.exports.192.168.20.163@tcp.uuid=2dd451a5-bb30-4f53-9eb3-e31e45bb7fce

The client->target UUID is the same for all MDC/OSC device connections for a single filesystem instance since a client may be connected to multiple different filesystems or the same filesystem multiple times, but it is different than the MGC UUID since there is only one client->MGC connection for each MGS.

client# lctl dl | grep MGC
  0 UP mgc MGC192.168.20.1@tcp 81addc57-0086-42a2-a013-5b721a581b5f 5 

As you can see, the MGC also has a proper UUID to identify its connection to the MGS.  I don't think anything needs to be done to change or "fix" this.

Serguei's patch is fixing a different issue, which is the client's OBD device name that is used to identify the MGC locally.  We can't use the MGS "target" name like is used for FSNAME-MDTxxxx and FSNAME-OSTxxxx devices, since the MGS target name is always just MGS (it does not contain the FSNAME because there may be multiple FSNAMEs configured there) and "MGS" by itself would not be unique if a client mounts filesystems from MGSes on different storage clusters (that also happens commonly today).

Adding the MGS server NID into the device name was done to make the MGC device name unique for multi-MGS connections, and is useful for admins to identify which MGC belongs to each cluster (in the absence of an "FSNAME" identifier).  Serguei's current patch is only changing the NID formatting slightly so that the IPv6 NID fits into the OBD device name field.

I don't think it is unreasonable to use the primary MGS NID as the OBD device name, since if the client can't find the MGS by that NID then it can't mount the filesystem.  Since this OBD device name is used only local to the client and for the duration of the mount to identify the MGC device, then there is no need for this to be permanent or consistent across mounts.  Even if the MGS gets new NIDs during the mount lifetime, those NIDs will be stored internally and do not really affect the operation.

If the MGS NID changes without warning (e.g. MGS was using DHCP) then the clients would have no way to be notified of this since their connection to the old MGS NID would be lost, so this could not be a valid mode of operation.  That isn't the case if MDSes or OSSes were using dynamic NIDs because the MGS IR notification would tell the clients the new server NID(s).  Maybe we could allow MGS NIDs to change in the future (e.g. with Fault Tolerant MGS, as long as one client->MGS connection was preserved) or in-kernel DNS lookup, but that isn't the problem that is being solved today.
