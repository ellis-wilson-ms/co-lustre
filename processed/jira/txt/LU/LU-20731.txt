--- Description ---
A failed policy restart with a new argument leaves the NRS head of a multi-partition service in a mixed state. After that, a read of the nrs_policies file returns -EINVAL until the next successful start.

Sequence in lustre/ptlrpc/nrs.c:

1. nrs_policy_start_locked() receives a start for a policy that is already STARTED with a different argument. It calls nrs_policy_stop_locked() first. __nrs_policy_stop() clears pol_arg.

2. op_policy_start() fails, for example because the argument is invalid for the policy. nrs_policy_start_locked() sets the policy STOPPED and returns the error. pol_arg stays empty.

3. ptlrpc_nrs_policy_control() stops the partition walk at the first error. The partitions after it keep the old policy STARTED with the old pol_arg.

ptlrpc_lprocfs_nrs_policies_seq_show() in lustre/ptlrpc/lproc_ptlrpc.c compares pi_arg across the partitions and returns -EINVAL when two partitions disagree:

LustreError: ll_ost_io: failed to check pi_arg: rc = -22

The file stays unreadable until a start succeeds on every partition. The policy state is mixed too. Partition 0 runs the fallback policy. The other partitions still run the old primary policy with the old argument.

We saw this on an 8 partition OSS during a sanityn test_77tc run against the LU-20090 series. The test starts TBF with one argument and then starts it again with an argument that the policy rejects. The three code paths above are unchanged on master at dd48e6b096, so the defect is in master and not in the series. The reproducer on stock master is not yet run.

Reproducer shape on a server with more than one CPU partition:

lctl set_param ost.OSS.ost_io.nrs_policies="tbf nid"
lctl set_param ost.OSS.ost_io.nrs_policies="tbf "
lctl get_param ost.OSS.ost_io.nrs_policies

Two candidate fixes. The start path can restart the policy with the old argument when the new start fails. A failed restart then leaves every partition as it was. Or ptlrpc_nrs_policy_control() can roll the partitions already changed back to the old policy and argument on error. The seq_show check itself is correct. It reports a real inconsistency.
