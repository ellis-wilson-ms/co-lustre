--- Description ---
Summary

lov: lov_attr_get_dom() NULL dereference of lo_loi during DOM composite layout initialization causes kernel panic

Environment

	Cluster topology: MGS×1, MDT×3, OST×5, multi-node

	DOM stripe: lfs setstripe -E 1 MB -L mdt -E EOF -c 1

	Reproducer: append_flood_fd   — 128 concurrent O_APPEND writers

Description
Background

The first 1 MB lives on the MDT. When a file grows past 1 MB, the Lustre client triggers a composite layout transition that runs lov_init_composite() to allocate and initialize the OST component. This transition is where the race occurs.

Crash

A kernel panic occurs when many threads concurrently perform O_APPEND writes on a DOM file that is about to cross the 1 MB boundary. The crash is a NULL pointer dereference inside lov_attr_get_dom() at offset 0x48, which is the byte offset of loi_lvb.lvb_blocks inside struct lov_oinfo.

Root Cause — Two Race Windows

lov_init_composite() (lustre/lov/lov_object.c) initializes a composite layout in two separate loops with no memory ordering guarantee between them.

LOOP1 — marks all layout entries valid :

for (i = 0; i lo_nr; i++)
    lle->lle_valid = !(lle->lle_lsme->lsme_flags & LCME_FL_STALE);

LOOP2 — calls per-type initialization, which for DOM calls lov_init_dom() :

result = lle->lle_comp_ops->lco_init(env, dev, lov, index, conf, lle);

lov_init_dom() allocates struct lov_oinfo and assigns it to lo_loi after all lo_dom_r0 fields have been written:

lle->lle_dom.lo_dom_r0.lo_nr  = 1;
lle->lle_dom.lo_dom_r0.lo_sub = &lle->lle_dom.lo_dom;
lle->lle_dom.lo_mdt_idx       = idx;
lle->lle_dom.lo_loi           = loi;   /* plain store — no barrier */

Race Window A — between LOOP1 and LOOP2:

Thread A (lov_init_composite)             Thread B (concurrent O_APPEND write)
=====================================     ====================================
LOOP1: lle->lle_valid = 1;
       ...

                                            -> ll_merge_attr()
                                              -> lov_attr_get_composite()
                                                lle_valid == 1  * (enters DOM)
                                                -> lov_attr_get_dom()
                                                    loi = dom->lo_loi   lo_loi = loi         loi->loi_lvb.lvb_blocks  

Race Window B — inside lov_init_dom() itself:

Even after LOOP2 has started, lo_dom_r0 fields are written first and lo_loi is written last with a plain store. On architectures with weak memory models (ARM, POWER), a concurrent reader may observe a non-NULL lo_loi while lo_dom_r0 stores are not yet globally visible — resulting in stale attribute data being returned.

Crash path in origin code

/* lustre/lov/lov_object.c — lov_attr_get_dom() */
static int lov_attr_get_dom(const struct lu_env *env,
                            struct lov_layout_entry *lle, ...)
{
    struct lov_layout_dom *dom = &lle->lle_dom;
    struct lov_oinfo *loi = dom->lo_loi;   /* (1) plain load — can be NULL during Window A/B */
    struct cl_attr *attr  = &dom->lo_dom_r0.lo_attr;

    if (dom->lo_dom_r0.lo_attr_valid) {    /* (2) fast-path cache hit */
        *lov_attr = attr;
        return 0;
    }
    /* lo_attr_valid == 0: not yet populated by lov_init_dom */
    /* falls through to slow path — loi is NULL here during the race */

    if (OST_LVB_IS_ERR(loi->loi_lvb.lvb_blocks))  /* (3) NULL deref at offset 0x48 */
        ...
}

The crash occurs at step (3) because:

	lo_attr_valid == 0 during Window A/B — lov_init_dom() has not yet populated it

	loi was loaded at step (1) before lov_init_dom() stored the pointer

	Fault address 0x48 == offsetof(struct lov_oinfo, loi_lvb.lvb_blocks)

Reproduction

Reproducer: append_flood_fd  

Spawns N threads, each opening the file with O_APPEND | O_WRONLY and writing 4 KB in a tight loop. O_APPEND requires knowing the current file size (ll_merge_attr → lov_attr_get_dom). Prefilling to 1 MB − 4 KB ensures the very first write by one thread crosses the DOM threshold, triggering lov_init_composite(). While that initialization runs, all other threads race into lov_attr_get_dom() before lo_loi is published.

# Create DOM-layout file and prefill to 1 MB − 4 KB
lfs setstripe -E 1 MB -L mdt -E EOF -c 1 /mnt/clstvol/dom_repro/test_dom
dd if=/dev/zero of=/mnt/clstvol/dom_repro/test_dom bs=4096 count=255

# Fire 128 concurrent O_APPEND writers; first write crosses the 1 MB DOM boundary
./append_flood_fd /mnt/clstvol/dom_repro/test_dom 128

# compile: gcc -O2 -pthread -o append_flood_fd append_flood_fd.c

Reproduction rate: crash confirmed within ~80 iterations on a 3-MDT/5-OST o2ib cluster (Lustre 2.17.55_dirty (master branch), Rocky Linux 8.10).

How to Fix
Fix 1 — Defer lo_loi load and add NULL guard in lov_attr_get_dom() (reader side)

Original code loaded dom->lo_loi unconditionally at function entry, before even checking the fast path. The patched code defers the load to after the fast path check, uses smp_load_acquire() for ordering, and adds an explicit NULL guard.

This also removes a redundant memory load from the fast path (lo_attr_valid == 1, the common case in steady state), making the hot path slightly cheaper than the original.

Fix 2 — Use smp_store_release() to publish lo_loi in lov_init_dom() (writer side)

Original code used a plain C store to assign lo_loi after writing the lo_dom_r0 fields. On x86 the TSO model prevents store reordering, but on ARM and POWER a concurrent reader can observe lo_loi as non-NULL while lo_dom_r0 stores are still in flight. smp_store_release() prevents this by guaranteeing all preceding stores are globally visible before the lo_loi assignment becomes visible.

Why smp_wmb() + plain store is insufficient: smp_wmb() orders stores on the writer side, but a reader using only READ_ONCE() can still speculate the lo_dom_r0 loads before seeing the acquire fence from lo_loi. The smp_store_release() / smp_load_acquire() pair is the standard Linux kernel "publish pointer" pattern and provides the correct two-sided ordering guarantee on all architectures.

Fix 3 — NULL guard in fiemap path

A second dereference site in the FIEMAP ioctl path calls lov_oinfo_is_dummy(dom->lo_loi) without checking for NULL first. Reachable via the same Window A/B race through the fiemap codepath.

Completeness: grep -n "lo_loi" lustre/lov/lov_object.c confirms exactly two dereference sites — lov_attr_get_dom() (Fix 1) and this fiemap path (Fix 3). All other occurrences are pointer assignments or address-of operations, not dereferences. Both sites are now guarded.

Fix 4 — Early lo_preferred_mirror initialization for non-FLR layouts

In lov_init_composite(), lo_preferred_mirror is initialized to -1 and then set to 0 at the end of the mirror-selection loop. For non-FLR (plain DOM) files there is only one mirror and the selection loop always produces 0, but between LOOP1 and the end of LOOP2 the field remains -1. If a concurrent lov_io_mirror_init() reads lo_preferred_mirror == -1 and passes it to lov_mirror_entry(), the LASSERT only checks i  but not i >= 0, allowing lo_mirrors[-1] array access.

Fix 5 — Prevent i_size=0 corruption in ll_merge_attr_nolock() (secondary consequence)

When Fix 1 returns 0 during Window A/B, lov_attr_get_composite() omits the DOM component from the attribute merge, leaving cat_size == 0 in the result. The original ll_merge_attr_nolock() then calls i_size_write(inode, 0), corrupting the VFS inode size. Concurrent O_APPEND threads read i_size == 0 as the append position and overwrite file data from offset 0, causing silent data corruption even without a kernel panic.

(1) a race window producing cat_size=0 with inode i_size > 0 — blocked by this guard;

(2) a legitimate truncate-to-zero, which goes through vvp_do_vmtruncate() → i_size_write(inode, 0) directly under ll_inode_size_lock and never reaches ll_merge_attr_nolock() — unaffected;

(3) a normal attribute update with cat_size > 0 — unaffected since the condition short-circuits.

Internal validation — race occurrence confirmed via kernel counter

During internal analysis, a fix1_null_loi_cnt kernel counter was added to lov_attr_get_dom() to count actual race occurrences — i.e., times the function encountered lo_loi == NULL and returned 0 instead of crashing. This distinguishes "the race never happened" from "the race happened and was handled safely."

Results across 3500 total iterations spanning four I/O scenarios:

	O_APPEND flood baseline — 2000 iterations, 68 race hits, 0 crashes

	Concurrent stat() + write flood — 500 iterations, 21 race hits, 0 crashes

	ftruncate(0) interleave + write flood — 500 iterations, 19 race hits, 0 crashes

	fallocate boundary crossing (single-thread) — 500 iterations, 0 race hits (race window too narrow for single-thread caller), 0 crashes

Total: 3500 iterations, 108 confirmed race hits, 0 crashes. fix1_null_loi_cnt > 0 is direct evidence that the race condition fired during testing and was safely handled by the patch.

Performance impact

The fast path (lo_attr_valid == 1, the common case in steady state) has zero overhead — the new code is positioned after the fast-path early return and is never executed. The vanilla code unconditionally loaded dom->lo_loi on every call regardless of the fast path, so the patched fast path is marginally cheaper.

On the slow path (first attribute access after layout init), smp_load_acquire() compiles to a plain load on x86 (TSO) and a single ldar instruction on ARM. smp_store_release() in lov_init_dom() compiles to a compiler barrier on x86 and a single stlr on ARM. Both are called at most once per layout init event, not on the I/O hot path.

Known Limitation — FLR+DOM lo_preferred_mirror race

FLR+DOM files (File Level Redundancy combined with DOM) have a pre-existing race where lo_preferred_mirror == -1 can reach lov_io_mirror_init() during Window A:

/* lustre/lov/lov_io.c — lov_io_mirror_init() FLR path */
index = lio->lis_mirror_index = comp->lo_preferred_mirror;  /* -1 during race */
...
lre = lov_mirror_entry(obj, (-1 + i) % comp->lo_mirror_count);
/* (-1 + 0) % N evaluates to -1 on signed integer division */

/* lustre/lov/lov_cl_internal.h — lov_mirror_entry() */
LASSERTF(i u.composite.lo_mirror_count, ...);
/* No i >= 0 check — i = -1 passes the assert */
return &lov->u.composite.lo_mirrors[-1];   /* out-of-bounds access */

This race is pre-existing (present before this patch). Fix 1 removes the earlier NULL dereference crash that previously prevented reaching this code path. Fix 4 handles the non-FLR case (LCM_FL_NONE) by setting lo_preferred_mirror = 0 before LOOP1. The FLR+DOM variant is a pre-existing issue exposed by this fix and is not addressed in this patch.
