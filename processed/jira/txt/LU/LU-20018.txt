--- Comment (hongchao.zhang, Wed, 27 May 2026 09:10:10 +0000) ---
Hi,

In "htable_lookup" (lu_object.c), if there is an existing object and the object is not in use, it will drop the object from the hash immediately and retry the insertion of the new object, and it will wait the shadow object to be "inited" or "dying" if the shadow

object is still in use.

        if (atomic_inc_not_zero(&h->loh_ref)) {
                rcu_read_unlock();
                return lu_object_top(h);
        }

        spin_lock(&bkt->lsb_waitq.lock);
        if (lu_object_is_dying(h) ||
            test_bit(LU_OBJECT_UNHASHED, &h->loh_flags)) {
                spin_unlock(&bkt->lsb_waitq.lock);
                rcu_read_unlock();
                if (new) {
                        /*
                         * Old object might have already been removed, or will
                         * be soon.  We need to insert our new object, so
                         * remove the old one just in case it is still there.
                         */
                        rhashtable_remove_fast(&s->ls_obj_hash, &h->loh_hash,
                                               obj_hash_params);
                        goto try_again;
                }
                lprocfs_counter_incr(s->ls_stats, LU_SS_CACHE_MISS);
                return ERR_PTR(-ENOENT);
        }

If the existing lu_object is dropped from the hash by lu_site_purge before it calls the "lu_object_free" to free the lu_object, and the "lu_object_find_at" won't know there is another lu_object to be deleted by lu_site_purge, then it will destroy the OSD object after creating the new lu_object, which could race with it and lead to this issue.

Yes, the "nlink == 0" causes the inode to be put on the orphan list by "ldiskfs_truncate", which trigger the LASSERTION.

There is LLOG object to be used during mount, and it could be same issue, but will look it more detailedly for other casuses.

Thanks
