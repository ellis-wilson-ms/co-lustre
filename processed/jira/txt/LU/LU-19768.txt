--- Description ---
The Lustre stats collection via Netlink/YAML is incomplete.  It is not currently possible to access statistics from non-"stat" files, such as md_stats, jobstats, brw_stats.

These (and other) statistics need to be accessible via Netlink in order to provide a comprehensive monitoring interface for Lustre without having to scrape and parse text output via lctl.

--- Comment (adilger, Tue, 6 Oct 2026 08:04:58 +0000) ---
[Claude] Comparison of the two netlink framework approaches: 68047 ("LU-19768 obdclass: Create new framework for obd_device based Netlink") + 69416 ("LU-19768 mdd: add Netlink support for changelog_users") versus 65199 ("LU-19768 obdclass: table-driven netlink framework") + 65204 ("LU-19768 mdd: add MDD/changelog genetlink family"), focused on the base framework's compactness, runtime efficiency, maintainability, and suitability for exporting all Lustre statistics.

Summary

Recommend 65199 as the base, after three fixes (below) and adopting two ideas from 68047. 68047 is not materially smaller in practice, its cumulative min_dump_alloc sizing does not scale, and it has cursor/locking bugs that also affect every consumer built on it so far.

Like-for-like port: LDLM family on 68047

To compare the APIs directly, 65203 ("LU-19768 ldlm: add LDLM genetlink family") was ported onto 68047 (local branch only, builds cleanly on rocky9/aarch64; not runtime tested since neither series has a userspace consumer for that family yet).

collect/dump_one/release + static const descriptor
5 mandatory callbacks in a per-request stack struct

none
+80 lines: 68047 has no reusable counter/dataset packer, so an equivalent of 65199's lustre_nl_put_dataset() had to be added

Message sizing
not needed
setup_keys() walking every entry, plus a guessed key-table size

The "much simpler API" claim for 68047 does not show up in the consumer code size; it ends up about the same, plus hand-maintained size accounting.

Runtime efficiency

	68047 sums the size of every entry into cb->min_dump_alloc, so the entire dump must fit in one skb and netlink paging is never used. With thousands of OSTs, job_stats, or per-export stats this becomes a very large skb allocation per request. On RHEL8 (4.18) min_dump_alloc is a u16, so totals above 64KB silently wrap. The per-entry constants are hand-measured (144 + 36 + 28 + 28) and 69416 uses 1024 /* FIXME */; any key-table change silently invalidates them.

	68047 does a separate allocation per entry, stored in an xarray, takes/drops xa_lock around each entry in the dump, and re-looks up the obd by minor number for every entry.

	65199 stores fixed-size entries in a genradix (no per-entry allocation), takes no locks during the dump, and uses normal netlink multi-skb continuation.

68047 issues

	xas_for_each() resumes after the entry the cursor was last on, so an entry cancelled with -EMSGSIZE is skipped on the next dumpit call (data loss when output spans skbs).

	lustre_obd_genl_dump() returns -EMSGSIZE from the nla_nest_start() failure path while still holding xa_lock.

	start_cb is called under obd_device_lock() (= xa_lock(&obd_devs), a spinlock); lustre_targets_start_cb() can call xas_nomem(GFP_KERNEL) there, i.e. sleep in atomic context under memory pressure.

	lustre_targets_find_obd() dereferences obd->obd_minor without a NULL check, but obd_device_find() (xa_find) can return NULL.

	The patch mixes the configure rename (the comment says 6.5, but genl_info.family and genl_info_dump() arrived in 6.6), the stats refactor, and the framework. The stats path still has its own start/dump, so it only partly uses the framework.

65199 issues

	lustre_obd_nl_dump() returns -EMSGSIZE when the skb fills. Before kernel v6.9 (commit b5a899154aa9 "netlink: handle EMSGSIZE errors in the core") that terminates the dump with an error, so any dump larger than one skb fails on RHEL8/9. Fix: return (rc == -EMSGSIZE && msg->len) ? msg->len : rc; as lustre_stats_dump() in the same patch already does.

	The context "subclass" via lno_list_offset uses kernel-internal _genradix_ptr/idx_to_offset/_genradix_free. A framework-owned genradix with a fixed entry size (or an array of pointers) would avoid depending on genradix internals.

	Only a single filter glob is supported (the last one wins); 68047 handles a list of type.name sources. The per-command forwarding wrappers in 65203 are unnecessary; .dumpit = lustre_obd_nl_dump works directly.

Shared design flaw: collection under a spinlock

Both frameworks call the per-device collect callback under the obd_devs spinlock, so a collector can never sleep. The changelog patches show the result:

	65204 bypasses the 65199 framework entirely (despite its commit message) and walks class_num2obd() without the lock or an obd reference, which races with device cleanup.

	69416 uses the 68047 framework, so it calls lu_env_init() and llog_cat_process() (disk I/O) under the spinlock: a guaranteed sleep-in-atomic bug.

Whichever framework is chosen should take class_incref() on matching obds under the lock, drop the lock, and then call the collector in a context that may sleep.

MDD changelog patches

	69416 is still work in progress: leftover pr_info("here 1"), user_attr nest ended twice, cne leaked on all error paths and when there is no llog context, fixed 1024-byte sizing (fails with more than about 15 changelog users), no reference or minor check in get_source, changelog_type2str(mask  should use i, magic event.type == 10, and in-place "MDD"→"MDT" string editing in userspace. Its strength is the lctl get_param path, with output that matches the existing changelog_users parameter.

	65204 has the more correct kernel side (allowed to sleep), but no userspace consumer, and its key names ("changelog", "index", "id") do not match the existing parameter.

Long-term maintenance and coverage of all stats

The 65199 series already covers recovery, obd parameters, brw_stats, job_stats, exports, LDLM, quota and health, and it adds reusable pieces (lustre_nl_put_dataset(), ldebugfs_stats_register()). 68047 has the only userspace (liblustreapi) wiring and a model for one-obd-to-many-items cases like pools.

Suggested path:

	Land 65199 with the -EMSGSIZE return fix, collection moved out of the spinlock, and the genradix internals replaced.

	Adopt from 68047: the multi-source type.name filter and emitting the HDR/SOURCE attributes from the framework.

	Rebase the MDD changelog patch on that, using 65204's kernel collection with 69416's userspace code.
