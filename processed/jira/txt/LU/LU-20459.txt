--- Comment (JIRAUSER22000, Wed, 8 Jul 2026 08:34:32 +0000) ---
It seems the cpu hotplug states was wrongly freed because of lustre_rmmod. 

And when /sys/devices/system/cpu/hotplug/states was accessed after lustre_rmmod, it will trigger a crash.

There are very few places in lustre code, where cpu hotplug states are touched.  In master/b_es7_0, it's lnet/lnet/lib-cpt.c and in b_es6_0, it's libcfs/libcfs/lib_cpu.c.

In these files, the cpuhp_setup_state_nocalls() function with CPUHP_BP_PREPARE_DYN dynamically allocates a state ID within the prepare stage range and returns the actual allocated state, not the input constant.

The original code discarded the return value from the "dead" callback registration and later used CPUHP_BP_PREPARE_DYN directly in cpuhp_remove_state_nocalls(), which may cause incorrect cleanup if multiple modules use the same dynamic range, or if some Linux release version (e.g., Ubuntu 26.04) changed the behaviour of the function.  Thus crash the kernel.

So it is reasonable to add a static variable lustre_cpu_dead to save the actual state ID returned by cpuhp_setup_state_nocalls(), ensuring the correct state is removed during cleanup.
