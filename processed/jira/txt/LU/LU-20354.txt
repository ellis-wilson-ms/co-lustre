--- Description ---
The "lfs quota" operations are blocked when an OST is offline.  I see this regularly with my home Lustre system where the OSTs are on HDDs that have spun down to save energy.  The "lfs quota" operation fetches the quota usage information from each MDT and OST directly upon request, and the command does not return until the HDDs are spun up, which means there is no cache of the usage information on the QMT.

Having offline OSTs is expected to be a more common occurrence with FLR-ECRO deployments, and to the largest extent possible the filesystem operations should not block in this case.

For proper operation when an OST is (temporarily) offline, it would be useful for QMT0000 to maintain a (lazy) cache of the quota usage of each target.  This has two benefits:

	it maintains filesystem accessibility for "lfs quota" commands when an OST is undergoing failover or is permanently offline.

	it allows estimating how much quota usage was on that OST before it went offline for purposes of future quota grants (i.e. the OST's quota usage is not just "lost" when it is inaccessible).

In most cases the OST quota usage does not need to be totally uptodate, since the quota enforcement is itself not exact.  If the OST is online, then the QMT and client should prefer quota usage from the actual target.  If the OST is offline, then the cached quota usage should be "good enough", since the space used by that OST cannot change while it is offline (excluding OST reformat or e2fsck correcting errors).

This means that having a cache of the OST usage that is asynchronously written to the QMT0000 for each ID should be enough.  It does not need to be synchronous or recovered in case of failure, since it can be updated the next time the OST is online, or if the OST is permanently removed from the filesystem.

--- Comment (JIRAUSER19404, Wed, 17 Jun 2026 13:06:17 +0000) ---
Hi, following is the procedure of `lfs quota`,

1. RPC to MDS/QMT: Fetches global quota limits and grace time.

2. Iterate OSTs: Issues Q_GETOQUOTA to collect individual block usage, aggregating them into dqb_curspace on the client side.

3. Iterate MDTs: Issues Q_GETOQUOTA to collect and aggregate inode usage on the client side.

To cope with EC-RDONLY OST offline issue, we could just add another step

4. Consult QMT for Offline OSTs's granted space. Just as scherementsev "phase 1" suggested.

To further refine the accuracy of the offline OST's usage (since granted space can be much larger than actual usage), we could implement a heuristic optimization: calculate the average Usage-to-Grant ratio sampling from some currently online OSTs, and apply this ratio to the offline OST's granted space to extrapolate a more realistic estimate.

I am not a fan of maintaining a persistent usage cache directly on the QMT by piggybacking qb_usage on all quota requests (QUOTA_DQACQ_FL_REPORT, ACQ, and RELEASE) and serializing it into struct lquota_slv_rec.

Aside from the fact that this usage data is not up-to-date, this approach introduces additional architectural complexity: modifying lquota_slv_rec alters the on-disk layout, which demands rigorous  backward compatibility handling.

Given that our primary goal under FLR-ECRO is simply to provide a "good enough" estimate to prevent lfs quota from blocking or returning incomplete data, adding Step 4 offers a much simpler, low-risk, and cost-effective alternative.

Hi Keguang, I think in the case of not-yet-inactive OSTs that have just failed, we want to make sure that the GETQUOTA RPCs do not hang for a long time. As such, these RPCs should be allowed to time out but not retry these RPCs. 

I'm not exactly sure of the quota implementation details, but my thought would be to have the fallback to the quota grant usage to happen immediately after the OST RPC fails/times out. That localizes the error handling, and does not require storing some extra state about which OSTs to retry. However, that is just a high-level opinion and maybe does not match the way the code is implemented. 

On the one hand, it may not be ideal to store a persistent record of the quota usage on QMT0000 since it could become stale, however it might also have some advantages. This cache on QMT0000 would allow the client to avoid potentially hundreds of extra RPCs for statfs() calls when project quota is enabled on a directory tree (which is basically always for multi-tenant systems that are increasingly common today. In some cases, applications are calling statfs() frequently, and while we have a client-side per-ID cache, it still means GETQUOTA calls to all MDTs and OSTs every few seconds from every client calling statfs(). If the quota master cached the aggregated quota usage per ID then the clients only need to do a single GETQUOTA call to get the full limits, reducing the RPC count by a factor of hundreds.

--- Comment (JIRAUSER19404, Wed, 24 Jun 2026 05:39:16 +0000) ---
Hi adilger  scherementsev  hongchao.zhang, a simple HLD about the cache,

TL;DR: Add quota-usage cache (not serialize to disk) in QMT where clients consult for quota usage, cache itself needs warmup and may face cache-miss; in that case, QMT proxies RPCs to OSTs to fetch usage and populate the cache on behalf of clients.

PRE: we already have a workable mechnism to fulfill the lfs quota command as mentioned above.

Startup: At startup, QMT will read all index files into Cache, {qid, osts[grants, usage(missing at startup)], mdts[...]}. During this phase, query from clients are rejected and redirect to the legacy mech (to keep the design simple and consistent, we do not perform proxy RPCs at this stage). (should we continue serving ACQ/REL at this stage?).

Warmup: QSD piggybacks the usage field in their ACQ/REL/REPORT, which helps to warmup the cache.

Serve clients: On each query with UID/GID, QMT return the corresponding OSTs/MDTs like { osts:[grants, usage], mdts:[...] }. If usage is missing at this stage, QMT proxies RPCs to OSTs to retrieve quota usage on behalf of the clients, the populated cache avoids repeat RPCs for subsequent callers. Based on prior experience with stats(), the extra RPC load on MDS0 is acceptable here.

With this cache, we could significantly reduce quota queries to OSTs/MDTs and improve client query performance as suggested in the description of this ticket.

 

Open: about Cache, there's already a global Cache in QMT. It's indexed through ID. We may reuse it with a new field like 'ost_maps'  under each lqe.

--- Comment (JIRAUSER19404, Thu, 25 Jun 2026 01:42:02 +0000) ---
Rather than ignore requests before the cache is populated, it would be possible for QMT to do proxy RPCs to the other targets to populate its cache and return that to the client. That is the same RPC count, but will populate the cache for the next caller.

In terms of the same RPC count, yes, it helps. However, this is a bit tricky: should we shift the burden from clients to QMT on MDS0, given that MDS0 already has heavy duties?

During startup, QMT does not yet have the full mapping relationship between quota IDs and OSTs. In that case, a quota query may fan out to all OSTs, which could mean thousands of RPCs in a large cluster.

After startup, when the system is in steady state, the fanout should be controllable in most cases. At that point, we may use proxy RPCs. Still, we probably need a threshold: if the number of missing quota entries is below this threshold, QMT should do the proxy RPCs on behalf of clients; otherwise, clients should still take the responsibility for querying the OSTs. (In the latter case, maybe we could maintain a specific thread on QMT, recording the missing ones and fetching them in the backgroud asynchonously).
