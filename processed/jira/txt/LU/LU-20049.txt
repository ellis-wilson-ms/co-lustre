--- Comment (eaujames, Fri, 18 Sep 2026 08:20:02 +0000) ---
Here is the upstream answer:

Re: [PATCH 2/4] libext2fs: add quota to libext2fs
From: Theodore Tso 

On Fri, May 29, 2026 at 01:57:14PM -0500, eaujames@ddn.com wrote:
> add quota related interface to libext2fs and install the
> relevant headers.

The reason why the quota functions are in the libsupport library as
opposed to the libext2fs directory is that the quota functions weren't
ready to be moved into libext2fs.  The libext2fs library is published
as a shared library, so the function ABI's must be stable.  This
requirement does not exist for libsupport.a (which is only statically
linked, so function stability is not a requirement).  The functions in
libsupport also in some cases try to write to the standard out, which
is not allowed for libext2fs.

As a result of this, the quota and ea_inode feature is not directly
supported by libext2fs, and hence, not by programs like fuse2fs.

So to address the problem you are trying to solve in this patch series
--- which is to allow e2fsck to correctly handle processing processing
an orphaned file which has an extended attribute value stored in an
inode and quota tracking enabled --- we have two choices

* Clean up the quota handling functions so we can move safely move
  them from lib/support to lib/ext2fs.  This is the long-term plan /
  goal, since it would also allow us to add support for ea_inode and
  quota into programs like fuse2fs.

* Don't add the functionality to lib/ext2fs, but just arrange to have
  release_orphan_inode() in e2fsck/super.c call the functions in
  lib/support as necessary.  (This is how we handle quota support in
  e2fsck today.  We just didn't deal with the combination of ea_inode
  | quota correctly.)

						- Ted

I believe the first option is the correct one. Otherwise, we’d end up duplicating functions in e2fsck, which would hurt maintainability. However, I don’t currently have the time to address this, and I’m also unsure about the exact requirements for libext2fs functions.

adilger what do you feel about this?

--- Comment (adilger, Fri, 18 Sep 2026 21:34:41 +0000) ---
eaujames, while I agree that the first option is the right long-term answer, it would definitely be a lot of work.  I suspect that no matter how this is done that Ted will have his own ideas about what the permanent API should be.  We had a similar issue with the xattr handling APIs that we originally added to libext2fs, and then he didn't like them and totally rewrote the implementation in a different way.  There have been similar disagreements about other changes to e2fsck (e.g. inode badness) that we just have to move on from.

As such, I think that the second option is the best way to move forward today.  I don't necessarily think that we need to duplicate the code in e2fsck, but rather we are free to use and change the code in lib/support (which is private to e2fsprogs) so that libext2fs and e2fsck can use it, and then call them directly instead of exporting them as ext2fs_* functions.  That would allow debugfs and e2fsck to be fixed without making them public interfaces forever into the future.  Ted has maintained e2fsprogs for almost 30 years (first commit 1997-04-26) so I trust his judgement in terms of maintaining the API in a supportable manner, even if that makes it harder to do in the short term.
