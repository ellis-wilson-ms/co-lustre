--- Description ---
Dear Whamcloud team,

We would like to report a bug in Lustre 2.17.0. It appears that collecting Lustre stats as a non-root user using lctl get_param might trigger an out-of-bounds (OOB) memory write, which can lead to a kernel crash. Example affected commands are as follows:

lctl get_param "mdt.*MDT*.exports.*@*.stats"
lctl get_param obdfilter.*OST*.exports.*@*.stats 

While crashes are frequently observed on MDS VMs, we have not yet observed any OSS VMs crash with this OOB. To reproduce the crash:

	Create a clean VM running the Lustre server kernel 5.14.0-611.13.1_lustre.el9.x86_64. (single Lustre server deployment)

	Download and install Lustre 2.17.0 （https://downloads.whamcloud.com/public/lustre/lustre-2.17.0/el9.7/server/）

	Format the MDT with the following flags:

Filesystem features:      has_journal ext_attr resize_inode dir_index filetype needs_recovery extent mmp flex_bg ea_inode dirdata large_dir sparse_super large_file huge_file uninit_bg dir_nlink quota project
Filesystem flags:         signed_directory_hash track_trim

       4. Format the OST with the following flags:

Filesystem features:      has_journal ext_attr dir_index filetype needs_recovery meta_bg extent 64bit mmp flex_bg large_dir sparse_super large_file huge_file uninit_bg dir_nlink quota project
Filesystem flags:         signed_directory_hash track_trim

       5. Mount the MGT/MDT/OST

       6. Use a non-root user to execute the vulnerable command as follows:

[root@lustre-mdsvm1 ~]# sudo -u testuser bash -c '  
     for i in $(seq 1 200); do

To the best of our knowledge, the issue is limited to Lustre stats collection. Any application that collects Lustre stats with the affected commands as a non-root user may be affected. In contrast, running the above affected commands as root does not cause any crashes.

 

Kernel Crash and Out-of-Bounds Memory Access.  The page fault at 0x80003 appears to be a downstream effect of this issue. Using KASAN, we identified its source as an out-of-bounds write to a buffer in lustre_stats_dump() (lustre/obdclass/kernelcomm.c, v2_17_0), allocated at line 891 and freed at line 923.

The error was captured on the same Lustre version with a debug build of the same kernel (5.14.0-611.13.1_lustre.el9.x86_64), rebuilt with the RHEL debug configuration and KASAN enabled (CONFIG_KASAN=y, CONFIG_KASAN_GENERIC=y, CONFIG_KASAN_INLINE=y, CONFIG_KASAN_VMALLOC=y). The resulting kernel reports itself as 5.14.0-611.13.1.kasan.el9.x86_64+debug. It was booted with kasan.fault=panic so that the first KASAN report triggers a panic and is preserved in the vmcore by kdump. The KASAN report extracted from the vmcore is as follows:

	The same task (3087) then wrote 16 bytes just after the end of this buffer. The buffer is [ff110006918d0800 , ff110006918d09f8), and the write starts at ff110006918d09f8, causing OOB memory access.

To understand how and why OOB occurs, we explain our understanding regarding how Lustre 2.17.0 prepares the vulnerable start buffer. The following code prepares the start pointer in Lustre 2.17.0:

/* In lustre-release/lnet/include/uapi/linux/lnet/lnet-nl.h at b2_17 */
...
struct ln_key_props {              
  char                                   *lkp_value;              __u16                                lkp_key_format;              __u16                                lkp_data_type;
};
struct ln_key_list {              
__u16                                lkl_maxattr;              
struct ln_key_props            lkl_list[];
}; 

/* In lustre-release/lustre/obdclass/kernelcomm.c at b2_17 */
size_t len = sizeof(struct ln_key_list);
...
struct ln_key_list *start;
...
count = LUSTRE_STATS_ATTR_MAX + stats->ls_num - 1;
len += sizeof(struct ln_key_props) * count;
OBD_ALLOC(start, len);

The size of the region allocated for start is len, computed as:

len = sizeof(struct ln_key_list) + sizeof(struct ln_key_props) * count 

Without memory padding, the struct sizes would be:

	struct ln_key_props: 12 bytes (8 bytes for the char *lkp_value pointer, 2 bytes for _u16 __ lkp_key_format,{_} and 2 bytes __ for __ _u16 lkp_data_type).

	struct ln_key_list: 2 bytes (the __u16 lkl_maxattr }}field). The flexible array member {{lkl_list[] adds no size, but it does impose the 8-byte alignment of its element type.

This would give len = 2 + 12 * count. However, pahole shows the actual layouts include padding:

[root@lustre-mdsvm1 ~]# pahole -C ln_key_props $(modinfo -n obdclass)
struct ln_key_props {
        char *                     lkp_value;            /*     0     8 */
        __u16                      lkp_key_format;       /*     8     2 */
        __u16                      lkp_data_type;        /*    10     2 */
        /* size: 16, cachelines: 1, members: 3 */
        /* padding: 4 */
        /* last cacheline: 16 bytes */
};
[root@lustre-mdsvm1 ~]# pahole -C ln_key_list $(modinfo -n obdclass)
struct ln_key_list {
        __u16                      lkl_maxattr;          /*     0     2 */
        /* XXX 6 bytes hole, try to pack */
        struct ln_key_props        lkl_list[];           /*     8     0 */
        /* size: 8, cachelines: 1, members: 2 */
        /* sum members: 2, holes: 1, sum holes: 6 */
        /* last cacheline: 8 bytes */
}; 

struct ln_key_list is padded from 2 to 8 bytes (6 bytes after lkl_maxattr), and struct ln_key_props is padded from 12 to 16 bytes (4 bytes of tail padding). The effective size is therefore len = 8 + 16 * count. Conversely, count = (len − 8) / 16. For the 504-byte buffer in the KASAN report, this gives count = (504 − 8) / 16 = 31. Key findings:

	len is 504, so, as derived above, start->lkl_list holds count = 31 elements, with valid indices 0 through 30.

	At the time of the crash, the loop index i is 31, and the code writes to start->lkl_list[31].

	Index 31 is one past the end of the array. This 16-byte write is the out-of-bounds write.

Triggering the Vulnerable Path as a Non-Root User. Analyzing the runtime call graph leading to lustre_stats_dump() reveals the execution path that produces the out-of-bounds write. When a non-root user queries Lustre statistics with the affected command:

sudo -u testuser lctl get_param mdt.*MDT*.exports.*@*.stats 

Lustre chooses how to read the data based on the requesting user's privileges. It first tries to open the file path with the user's privileges. If the user is not root and the parameter files are not found (-ENOENT), Lustre falls back to llapi_param_display_value():

# Code in lustre/utils/lustre_param.c{...
# Try to open file as current user privilege
  rc2 = do_param_op(&popt, path, NULL, GET_PARAM, NULL);
  if (rc2 if (rc == 0)
    rc = rc2;

   if (rc2 == -ENOENT && getuid() != 0)
# if user is not root and cannot read the file, use this function
    rc2 = llapi_param_display_value(path, version, flags, stdout);
   continue;
  }
 }

Because root can read the file path directly, it never takes this fallback path, which explains why the crash does not occur when the affected commands are run as root.

Our analysis indicates that statistics collection for OSTs and MDTs shares the same execution path. Although we have not observed crashes on OSS VMs running the standard kernel, KASAN reports the same out-of-bounds write on OSS VMs, so we believe OSS nodes are also affected.
