LU-17240 tests: mount targets in parallel

setupall() mounts every MDT and every OST one at a time, even when
they are on different nodes, and conf-sanity and other scripts do
this many times per run.

Mount MDT0001 and later MDTs in parallel after MDT0000 (and a
combined MGS) is started, then mount all OSTs in parallel, using
parallel_start() and parallel_wait() from formatall().  MDTs are
still all started before the OSTs.  start() and mount_facet() set
per-target variables such as <facet>_dev for dm-flakey and
<facet>_svc, which would be lost in a background subshell, so
parallel_start() now saves the exported <facet>_* variables of each
background command and parallel_wait() imports them into the parent.

mountmds() and mountoss() now return an error if any target failed
to start, and setupall() and replay-single test_135 fail if they do,
so a failed background mount is not ignored.  They and mountmgs()
skip targets that are already mounted, since setupall() is also used
to remount only the client.  Also pass the MDT index to
switch_identity() from mountmds(), instead of an unset or stale
variable, and have it use <facet>_svc for the MDT name, since the
client is not mounted yet.

Also attach loop devices in setup_loop_device() with "losetup -f
$file", instead of picking a free name and racing another attach for
it, which concurrent mounts of loop-file targets would hit.

Also make sanity test_818 set fail_val=1 so that only the OSP for
OST0000, where its file is, hits the one-shot
OBD_FAIL_OSP_CANT_PROCESS_LLOG, using cfs_fail_index() so fail_val
can also select a single OST or a bitmap of OSTs.  The test assumed
that OST0000's OSP sync thread starts first, but with parallel OST
mounts the OSTs register with the MGS in any order, and the test
then failed every time in CI.

Parallel mount is on by default and controlled by:
- PARALLEL_MOUNT: mount targets concurrently ($PARALLEL_OPS)
- PARALLEL_MOUNT_TARGETS: target types mounted concurrently
  ("mdt ost")

First mount of 6 OSTs after formatall(), on one 4-CPU VM, 3 runs:

             serial  parallel
  mountoss()  6.9s     1.4s    (-80%)

Remounting existing targets gains less, since each mount is fast and
setupall() time is mostly waiting for the client mount.
