LU-20290 lnet: add NUMA-node discovery-view group source

Add a numa group source alongside the per-ni source. It buckets a
node's participating NIs by NUMA node -- ni->ni_dev_cpt, the same
locality the send-path affinity steering keys on -- so the NUMA-local
NICs of one target form one group and a client coalesces them into
one multi-rail peer. Grouping is a local rule, not an enumerated NID
list, so the same configuration applies to every server regardless of
its NIDs.

The source is selected by a new lnet_group_numa_nets module param,
mutually exclusive with lnet_self_nets (both feed the same
participating-net list and differ only in the source). It is correct
iff a node's targets map one-to-one to NUMA nodes and the CPT table is
NUMA-aligned -- the same assumption the affinity path already makes; a
custom partition table that collapses NUMA nodes over-merges groups,
an accepted deployment precondition. The list and its helpers now back
both params, so they no longer carry the "self" name.

An NI whose LND left ni_dev_cpt at CFS_CPT_ANY has no NUMA node to
bucket by, which is the common case on virtual hardware. Give it a
group of its own. One shared unknown bucket would merge exactly the
NIDs this source keeps apart. A node where only some NIs report no
NUMA node is an asymmetry the admin can act on, so log it; all unknown
is a steady state that degenerates to per-ni, so do not.

The collect mirrors the per-ni discipline of no allocation under the
net lock: walk the NIs once into an off-lock (nid, key) scratch, drop
the lock, then build the variable-size groups. The same global
lnet_interfaces_max cap bounds total members; every numa view is a
subset of the full view, so its pi_nnis cannot exceed the limit the
full view already satisfies. The cap is writable through sysfs at any
time, so read it once per collect: the alloc, the bound and the free
have to agree on it.

A locally-initiated Push has no ingress NI to key on. per-ni keeps the
plain net test, but a numa net can carry members of more than one
group, so a net does not single one out and the numa case claims no
peer at all.

Add an optional dvp_fallback_peer policy test. It names the groups
which can stand in for the missing view, and the Push selector picks
among them. The node sends each Push from a NID of the selected group,
so the peer learns only that group, and later Pushes send the other
groups. The merged full view is not an acceptable stand-in, because it
names all of the local NIDs at the same time, and this is what lets
the peer coalesce the groups.

A numa group can span nets, so the NID the Push is sent from must be
the group member on the destination's net. The view's primary NID is
the first NID it advertises and can be on another net, which makes the
Push a routed send that fails unless a route is configured. Source
from an up view NID on the destination's net, and keep the primary
only for a destination no view NID shares a net with. The stand-in
test asks the same question of the view, so a group is eligible only
if it can supply that source. A view carries a down NI with its status
DOWN rather than dropping it, so status is what says whether a NID can
be sent from.

A destination behind a router is on no net of ours, so no group has a
member on it and the question becomes which group can reach it. Take
an up view NID that a live route reaches the destination from, and let
the stand-in test ask the same. Without this no group stands in for a
routed peer: the peer gets the merged full view and coalesces the
groups, where a directly reachable peer keeps them apart. The view's
primary NID stays the last resort.

The pick is keyed on the peer and on the local ping seqno rather than
on a global cursor. Peers are pushed in a stable order by one thread,
so a global cursor repeats its offset whenever the peer count is a
multiple of the group count, which pins every peer to one group for
good.

A peer which reached us on a local NI keeps that ingress NID as the
authority, so no group stands in for it. If one did, a Push to a peer
which arrived on a net that does not participate would be re-sourced
onto a net the peer never reached us on.

A test-only fault injection overrides the bucket key with a synthetic
per-NI value, so the grouping can be exercised on a host whose NICs
report no device NUMA node. That is the common case on virtual
hardware: every NI reads CFS_CPT_ANY, which takes a group of its own,
so neither distinct groups nor one shared group is otherwise
reachable. The override is inert unless armed and never writes
ni_dev_cpt.

Add sanity-lnet coverage for the numa group source and for a Push to
a routed peer. The router setup helper can now give module options to
the local node alone, so that node can run a grouping the routers and
the remote peer do not.

Add lnet.lnet_group_numa_nets.4 man page.
