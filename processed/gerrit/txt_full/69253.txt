LU-20808 mdt: read batch flag from session in intent policy

mdt_intent_policy() decides whether it is handling a batch sub-request
from mdt_thread_info::mti_batch_env. mdt_batch() sets that flag, but
nothing clears it when the batch request finishes: it is only reset
by mdt_thread_info_init(), which has not run yet at that point in
mdt_intent_policy(). A thread that handled a batch request earlier
therefore still looks like it is in one, and

  LASSERT(pill == &info->mti_sub_pill)

fires on the next intent that thread handles.

tgt_session_info::tsi_batch_env carries the same state, but it lives
in the request's own session. ptlrpc_server_handle_req_in() sets up a
fresh rq_session for every request, whose tgt_session_info starts out
zeroed, and tgt_ses_key_exit() clears the flag again when the request
is done. So it describes the request in hand. Read that instead. The
later uses in this function are already correct, because the
non-batch path reassigns info through tsi2mdt_info(), which
initialises the thread info and clears the flag.

Also clear mti_batch_env when mdt_batch() is done, so that the thread
info no longer carries the flag into the requests that thread handles
next. mdt_intent_policy() keeps reading the session all the same: its
flag describes the request in hand by construction, whatever an
earlier request left in the thread info.

This has been reachable since batch RPCs landed, but becomes easy to
hit once MDT-to-MDT lock enqueues carry an intent, because those
arrive on the OUT service, whose handlers never initialise
mdt_thread_info at all:

  LustreError: (mdt_handler.c:6097:mdt_intent_policy())
  ASSERTION( pill == &info->mti_sub_pill ) failed
  Comm: mdt_out00_001
   mdt_intent_policy+0x45d/0x4f0 [mdt]
   ldlm_lock_enqueue+0x3ba/0x920 [ptlrpc]
   ldlm_handle_enqueue+0x393/0x1840 [ptlrpc]
   tgt_enqueue+0x65/0x280 [ptlrpc]
