LU-20887 lfu: an OST object's owner in the Object Stream

An OST object records the MDT file it belongs to: the parent
FID in its trusted.fid, or in the LMA on an OST whose inodes
have no room for a second xattr (LMAC_STRIPE_INFO). A device
scan of a stopped OST already reads it and answers
LLAPI_SCAN_OWNER. The Object Stream of an OST in service did
not carry it, so a scan there could list the objects but not
the files they belong to.

That is the scan a drain of an OST needs. The OST stays
mounted while its files are migrated away, and the files
with objects on it are found from the OST itself instead of
from a scan of every MDT.

dt_otable_lfu_rec() now asks DORA_XATTR for trusted.fid on
an object whose LMA says LMAC_FID_ON_OST, or that has no LMA
at all, and takes the parent from the LMA when
LMAC_STRIPE_INFO says it is there. On an MDT the question is
not asked, except for the few objects with no LMA.

The FID goes in the record's tail, after the link, as struct
lfu_owner, and LFU_REC_HAVE_OWNER says it is there. The
header keeps its size and LFU_WIRE_VERSION is not bumped: a
reader that does not know the bit skips the bytes with
lr_reclen, and a reader that does finds no bit from an older
server. That matters for the stream a client reads over
OBD_IDX_READ, which has no size to negotiate. The tail as a
whole stays within LFU_LINK_MAX, so no buffer grows; an OST
object has no link, so the owner is all its tail holds.

In userspace scan_lfu_rec_to_obj() hands the owner to the
scanner as the head of a trusted.fid, which is all
scan_owner() reads of one. So the kernel backend answers
LLAPI_SCAN_OWNER, and lfind --fid2path names the objects of
a mounted OST by their files. scan_lfu_rec_ok() refuses a
record whose owner would lie outside it.

An object that was created and never written has no parent
FID on the OST and is still reported without an owner.

conf-sanity test_305 scans a mounted ldiskfs OST through
lfu.ko and checks that every written file is named and the
empty one is not. It skips where the module is not there.
