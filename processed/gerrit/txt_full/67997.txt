LU-20590 tests: inject layout lock reclaim during an IO

The client reclaims the layout lock of a file from the LRU.  An IO on
that file which is in flight then restarts.  Add a fault injection
which drops the unused locks of the MDC namespace inside the window
the IO uses.  The restart then needs no memory pressure and no racing
lru_size=clear.  The injection goes through the LRU cancel path, not
a direct invalidation of the object.  The condition under test is
therefore the real one.  The injection fires only after the layout
refresh succeeds.  A drop of the namespace LRU on the way out of a
failed refresh does no good.

The reclaim is best effort.  ldlm_cancel_lru() queues nothing while
another thread already drains the namespace.  A lock which somebody
holds a mode reference on is no candidate either.  The injection can
therefore miss, and the IO then completes with no restart at all.
The count of locks queued goes to the debug log.  The test skips
instead of fails when that log holds no restart.  A test which did
not run must not report a failure.

Add sanity test_251c.  The test checks that such an IO completes.
The test also checks that the pin held the layout lock out of the
LRU.

ldlm_cancel_lru() moves to a public header, and llite is a module of
its own, so the patch exports the symbol.  A test change which widens
the module ABI is unusual, so this message calls it out.
