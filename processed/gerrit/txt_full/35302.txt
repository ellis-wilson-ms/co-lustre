LU-13428 llite: correct cl_sync_file_range() arguments

OBD_OBJECT_EOF is a 64 bit unsigned value, but loff_t used
for fsync is a signed value, so LLONG_MAX is actually the
maximum allowed size for fsync/cl_sync_file_range.

Several callers passed OBD_OBJECT_EOF as the end of a
whole-file sync, which is -1 once stored in the signed
loff_t of cl_fsync_io.  It has done no harm, because every
consumer either special-cases the sentinel or truncates it
back to an all-ones page index.  (The range does not reach
the OST disk sync in any case: ofd_sync_hdl() takes it from
the zeroed reply body rather than the request.  That is a
separate, pre-existing bug and is not fixed here.)

Correct all cl_sync_file_range() callers to use LLONG_MAX
instead of OBD_OBJECT_EOF, reject a negative start or
end with an error message so a caller cannot silently
reintroduce the same mistake, trace the requested range
and mode on entry, and drop the OBD_OBJECT_EOF mapping
in osc_io_fsync_start(), which nothing can reach any more.

ll_writepages()'s writeback_index reset compared end
to OBD_OBJECT_EOF, already dead code since both range
setups above it produced OBD_OBJECT_EOF whenever it
ran. That comparison has to move to LLONG_MAX with the
rest: left matching OBD_OBJECT_EOF, the branch goes live
instead and computes an index that overflows loff_t on
the next range_cyclic pass. Collapse the reset to a plain
mapping->writeback_index = 0.
Correct the cl_sync_file_range() comment on which fsync
modes actually send OST_SYNC.

Yeah, agreed difference between OBD_OBJECT_EOF/__u64 and LLONG_MAX/loff_t could cause a lot of tricky problems, e.g. the comparison of singed/unsigned values, and the two different ways of determination of EOF. And these problems could hide there forever until an unlucky user hit it in a corner case.

I am wondering whether the following cleanup can fix the potential problems once for all:

1) Replace loff_t to __u64 in all Lustre internal codes. For example, do not allow any structure defined in Lustre use loff_t, unless it is an API. It might be possible to add a rule in the code check script to prevent this usage?

2) Only use loff_t in defintions of APIs (functions, structures) and the interaction with Linux/ZFS/Ldiskfs.

3) If need to convert between loff_t and __u64, always use inline functions like:

static inline __u64 loff2ull(loff_t offset) {
	/* Assuming Linux/APIs never use negative offset value */
	LASSERT(offset >= 0);
	if (offset == LLONG_MAX)
		return OBD_OBJECT_EOF;
	return (__u64)offset;
}

static inline loff_t ull2loff(__u64 value) {
	loff_t offset;

	/* Assuming Linux/APIs never use negative offset value */
	if (value == OBD_OBJECT_EOF)
		return LLONG_MAX;

	offset = (loff_t)value;
	/* Assuming never use unsgined 64-bit offset larger than LLONG_MAX */
	LASSERT(value >= 0);
	return offset;
}

That would be many lines of codes, but would simplify the logic of using loff_t.
