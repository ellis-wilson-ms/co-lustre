LU-17957 mdd: POSIX interface for non-root immutable files

Allow a non-root file owner to make their own file immutable using
POSIX tools, without CAP_LINUX_IMMUTABLE or root: set the file's
atime to at least mdd.posix_immutable_min_atime_delta seconds in the
future, then remove all write permission (chmod a-w). When
mdd.posix_immutable is enabled (default off) and both conditions are
met, the MDS sets IMMUTABLE_FL automatically.

A new on-disk LMA flag, RETENTION_FL (LMAC_RETENTION), marks files
made immutable this way, as opposed to plain "chattr +i", whose
IMMUTABLE_FL never auto-clears. A file is "expired" once its atime
has passed. Expiry lazily clears IMMUTABLE_FL|RETENTION_FL on the
next operation that needs the file writable, so files that are never
touched again keep the flags as MDS-internal bookkeeping only.
RETENTION_FL is always stripped from client-visible replies, and
IMMUTABLE_FL is masked once a file is expired, so a client can never
observe or cache a stale immutable state.

mdd.posix_immutable_min_atime_delta (default 24h, minimum 30s)
bounds how far in the future the atime must be set, to keep the
window comfortably larger than the client's own re-check interval
and avoid confusing an incidental atime update with an intentional
retention request.

A caller with CAP_LINUX_IMMUTABLE (e.g. root, or an HSM restore) may
migrate an immutable file or swap its layout at any time, regardless
of retention/expiry. A caller without it (e.g. the owner) must wait
for expiry first. This requires relaxing a few MAY_WRITE checks
(layout swap, migration, HSM release) specifically for
CAP_LINUX_IMMUTABLE callers, since the standard VFS write-permission
check always rejects immutable files outright, even for root. The
capability check needs the request's ucred, which the standalone
swap_layouts RPC handler did not previously set up, so it now
initializes and releases ucred around the permission check.
lfs migrate retries its read-only source open after EPERM, since
copying a file only needs read access.

On the client, since IMMUTABLE_FL is time-based rather than fixed, a
cached dentry must not keep the VFS from reaching the MDS once atime
has passed: ll_revalidate_dentry() forces a fresh lookup whenever the
cached inode is IS_IMMUTABLE and its atime is already in the past, so
open/unlink/rename after expiry reach the MDS for the authoritative
check instead of being rejected locally on stale cached flags. It is
re-checked on the next operation that triggers a lookup or MDS round
trip (e.g. close and reopen, stat, unlink, or rename).
