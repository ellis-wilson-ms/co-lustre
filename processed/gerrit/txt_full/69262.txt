LU-20808 mdt: skip lockless lookup for a remote create parent

With the read intent in place, a remote-parent create looks the name
up twice: once locklessly before taking the parent locks, and once
under the lock, by the MDT owning the parent, which grants the lock
with the same reply.

The lockless one is not one round trip but two. lod_index_try() loads
the parent's LMV before delegating to the device below, because on a
striped directory the name lives in one shard and LOD has to know
which, so the lookup drags a trusted.lmv read along with it. Neither
can be folded into the intent: both happen before there is a lock
request to attach an intent to, and neither can be batched with the
other, since the lookup's target object is chosen from the LMV the
first read returns.

Skip it when the parent is remote and this is neither a replay nor a
restripe. Replay still looks first, to tell a name that already
existed from one this request inserted itself; so does restripe,
because finding an existing directory is how it decides to restripe
it.

Skipping it means creating a name that already exists takes and
releases the parent locks before returning -EEXIST, which is the lock
traffic LU-10235 set out to avoid. "mkdir -p" run over an existing
tree from many clients produces that in bulk, since the client skips
its own lookup for mkdir when it may write the parent (LU-4185), so
every one of those creates reaches the MDT.

So keep the lockless lookup where names turn out to exist. A create
that finds its name taken, whichever lookup finds it, stamps the
parent's in-memory object with the time (mot_create_eexist), and
creates under a parent stamped within MDT_CREATE_EEXIST_WINDOW (30
seconds) look first again. A parent that is only ever given new names
never pays for the lookup. The stamp lasts only as long as the object
stays cached, and needs no wire or on-disk change.

The stamp only helps the creates that arrive after it is set. Creates
of an existing name that all arrive before the first -EEXIST is
recorded each take the parent locks, one after another, and those
that find the name lock taken also lose the read intent and look the
name up under the lock. So "mkdir -p" over an existing tree from many
clients costs one lock round per create in that first wave, and none
after it until the window lapses. Each MDT keeps its own stamp.

For a remote-parent mkdir of a new name this takes the synchronous
reads to one, the attribute fetch osp_object_init() issues when the
parent object is first instantiated, which precedes any of this and
cannot be avoided here.
