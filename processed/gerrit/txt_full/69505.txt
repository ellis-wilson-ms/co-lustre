LU-20896 osc: encrypt direct IO pages at their own file index

A direct write larger than about 1MiB to an encrypted file with the
key loaded stores data that does not decrypt back to what was
written.  OSC encrypts a direct IO page by pointing its folio at the
file mapping and setting the folio index to the page's file index,
then computing the block number as the folio index plus the page's
offset within the folio.  When the user buffer is backed by a
transparent huge page, that offset is not zero, so the page is
encrypted as another page of the file, while a direct read decrypts
it at its own index.  The pages of one large folio can also be in
different RPCs that are prepared concurrently, which all change the
same folio index.

Pass the inode and file index of the page to
osc_encrypt_pagecache_blocks() instead, and leave the folio of a
direct IO page alone.  "lfs migrate" and "lfs mirror extend" with
the key loaded no longer corrupt the file.

The fact that pages can be prepared at the same time by different
threads also poses a lock contention issue. Each thread calls
folio_trylock() on the same folio before encrypting its page. When the
trylock fails, the folio is assumed to stay locked during encryption,
which only holds for a page cache folio locked by vvp_page_assume()
waiting for this RPC. For a direct IO folio, the other thread unlocks
it as soon as its own page is encrypted, so the WARN_ON_ONCE() in
osc_encrypt_pagecache_blocks() fires and osc_brw_prep_request() fails
the write with -EINVAL.

A direct IO folio is part of the user buffer, not of the page
cache of the file. It is only read to encrypt it into a bounce
folio, at the inode and file index given by the caller, so the
folio lock does not protect anything. With embedded llcrypt, skip
the folio_trylock() of a direct IO folio, and the lock check in
osc_encrypt_pagecache_blocks().

8MiB direct write with the key loaded, 4MiB buffer, 15 runs:

  transparent huge pages   always   never
  without the fix          15/15    0/15 corrupt
  with the fix              0/15    0/15 corrupt

Add sanity-sec test_66a to write and read an encrypted file with
direct IO from a huge page buffer. Also exercise locking concurrency
by running 4 parallel 32MiB direct writes to files overstriped twice
on each OST with 64KiB stripes.
