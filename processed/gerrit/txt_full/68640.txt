LU-20694 tests: exercise the LOD update llog failure paths

conf-sanity 166 opens the window lod_add_device() leaves between
publishing a new MDT target and creating that target's update llog,
and mounts a client into it.

MDT0000 only reaches that code with its own llogs already initialized
when a target is added after it is mounted, so the case starts from a
fresh config log and brings MDT0001 up afterwards: the config update
that adds MDT0001's OSP is what MDT0000 processes while it is already
answering connects.  OBD_FAIL_MDS_LOD_ADD_TGT_PAUSE holds it there for
fail_val seconds, and lod.*.mdt_obd - which walks the target list under
the same lock lod_obd_get_info() takes - is what tells the test the
window is open.  MDT0001's mount runs in the background: the config
update reaches MDT0000 on its own schedule and the rest of that mount
is not bounded by the pause, so waiting for it could step past the
window.  The case then reads mds1's log back to confirm the connect
really took the retry path rather than merely succeeding.

Without the fix the MDS panics on ASSERTION( ctxt != NULL ) in
lod_obd_get_info() as the client connects.

conf-sanity 167 covers the other end of the same path.
OBD_FAIL_MDS_LOD_INIT_LLOG fails lod_sub_init_llog() for a remote target
the way a local resource shortage would, and the case requires the MDT
mount to fail rather than come up unusable, then requires the next mount
without the failure to work.

It fakes the failure at the lu_env_init() call rather than on entry, so
llog_setup() has run and the out_llog unwind is what tears the context
back down - the path with nothing else to exercise it.
