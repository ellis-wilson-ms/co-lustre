LU-19566 lustre: add layout flags to lfsck

EC parity mirror components hold parity, not file data, so
LFSCK must restore them as parity components when it
rebuilds a layout from orphan OST objects. It restored each
component with only LCME_FL_INIT, losing the parity flag,
the EC geometry and the link between the data and parity
mirrors, so a rebuilt EC file could not use its parity.

For EC components, store the long-lived component flags
(prefer, nosync, parity, nocompr), the EC data and code
stripe counts and the mirror link id at the end of
filter_fid. The client sends them on writes and setattr in
the obdo fields that were o_uid_h and o_gid_h, never used,
flagged by the never-used 0x00200000 valid bit (formerly
OBD_MD_FLQOS), now OBD_MD_FLCOMPFLAGS, and the OST passes
them to the MDT in the orphan record, so LFSCK restores
them. The objects only get them from a write or setattr, so
a change of flags is stored once the file is next written. A
rebuilt parity component also gets the parity pattern, which
clients use to keep reads off it, and LFSCK accepts that
pattern when it adds further orphans to such a file. When
LFSCK adds a component to an EC file its parity is marked
stale, since the objects do not show whether the parity was
current, so it is only used again after a resync. LFSCK
scans still skip EC files: repairing a missing parity object
there would need the parity regenerated or marked stale.

STALE is not stored: resync writes an object while its
mirror is still stale, so a stored STALE is backward and can
rebuild a layout whose mirrors are all stale, which LBUGs
the MDS when it loads that layout.

Other components keep the 52-byte filter_fid, so that
servers before this change and older tools still read it,
and only EC files, which need the new servers anyway, get
the 60-byte form. Servers without this change do not handle
it: their LFSCK and MDT migration get -ERANGE reading it,
and an OST keeping the parent FID in LMA (256-byte inodes)
refuses to have it written, unless they have "lfsck: read a
filter_fid longer than ours", which this patch is based on.
An OST keeping the parent FID in LMA has no room for these
fields, and does not store them.

sanity-lfsck test_47 and test_48 cover mirrors after resync
and EC files; test_48 checks the rebuilt EC geometry and,
after a resync, reads the file with a data OST failing.
test_45 now waits for LFSCK to finish on every target, not
only on the OST it checks, so that the next test can start
LFSCK.

--- Message (Patrick Farrell, 2026-10-08 01:46:47.000000000) ---
Patch Set 16:

Open gap, to be resolved: LFSCK cannot yet rebuild a usable EC file from orphan OST objects.

https://review.whamcloud.com/62389 stores the component flags in filter_fid, so a rebuilt parity component now gets LCME_FL_PARITY and LOV_PATTERN_PARITY: clients no longer read it as file data, and the data mirror is intact. But three pieces of an EC component are not in filter_fid, and LFSCK leaves them zero:

- lcme_dstripe_count (k, data stripes)
- lcme_cstripe_count (p, parity stripes)
- lcme_mirror_link_id, which ties the parity mirror to the data mirror it protects

filter_fid's ost_layout holds only stripe size and count, the component extent and the component id. Without the link id the parity mirror is never used: lov_io.c looks up the data mirror by lsme_mirror_link_id and returns early when none matches. So after LFSCK rebuilds an EC file, its parity cannot be resynced, and it cannot reconstruct data if a data object is also lost. That is the case EC is for. (Read from the code; not yet tested on a rebuilt file.)

Ways to close it:
1. Store k, p and the link id in filter_fid too. They fit in one more 32-bit field (8+8+16 bits). Each growth of filter_fid has the same mixed-version problem as ff_comp_flags (older LFSCK and MDT migration get -ERANGE on the larger xattr, older 256-byte-inode OSTs refuse it), so if this is the route, it should go into the same format change as ff_comp_flags rather than a second one.
2. Derive them in LFSCK after the orphans are attached: p is the parity component's own stripe count, k the stripe count of the data component with the same extent, and the link id that data component's mirror id. This is unambiguous only when one data mirror covers that extent.
3. Option 2 as a fallback for objects written before option 1.

Option 1 has to be decided before 62389 lands, since it changes the on-disk format that patch introduces.

PS17:

- For EC components, filter_fid now also stores the EC data and code stripe counts (k and p) and the mirror link id, 60 bytes in all; every other component keeps the 52-byte filter_fid, so a mixed or downgraded system only meets the larger form on EC files, which need the new servers anyway. The client sends these on writes and setattr, the OST passes them up in the orphan record, and LFSCK writes them back into the rebuilt component, so the raidset split comes out as before even when the data stripe count is not a multiple of k. When LFSCK adds a component to an EC file its parity is marked stale, since the objects cannot show whether it was current, so it is used again only after a resync. sanity-lfsck test_48 rebuilds a 2+1 file, resyncs it, checks the layout matches the original, and reads it back with a data OST failing. Prefer, nosync and nocompr on non-EC mirrors are no longer kept.
