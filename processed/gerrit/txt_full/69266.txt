LU-20808 mdd: drop only the linkEA in mdd_parent_fid()

mdd_parent_fid() reads an object's linkEA without holding a lock on
it, so it must not leave what it read in the cache: a rename walks the
tree once before it takes the rename lock and again after, and the
second walk exists precisely to get a fresh answer.

But it invalidates the whole object cache to do it, and it read
nothing except that one xattr. Most of what else it discards was put
there by someone who did hold a lock - the object's attributes above
all - and the next reader has to fetch it again. For a remote object
each of those is a synchronous OUT_UPDATE RPC.

Not all of it, though: the attributes of an ancestor the walk itself
instantiates, and those of a rename's parents read by the walk before
they are locked, were read without a lock too. They now stay cached
until a lock on the object is granted, which drops them or replaces
them with what came back under it. For the rename parents that
happens straight after the walk.

In a cross-MDT rename onto an existing target the source parent is
walked twice, and each walk strands the attributes behind it: the
mdd_la_get() at the top of the following mdd_is_subdir(), and then
mdd_rename()'s own read of the same attributes, both go to the wire
for state that was already there and still covered by the parent lock.

Add dt_invalidate_xattr() to forget a single cached xattr and use it
here. It is optional, and only the OSP MDT objects implement it: when
an object's type does not provide it there is nothing to invalidate,
as on a local target, and dt_invalidate_xattr() returns 0.

The linkEA itself is still dropped, so the second walk reads it again
exactly as before.
