LU-20818 osc: spread RPC builds over the submitting node

An unbound workqueue runs work in the affinity pod of the CPU
it was queued on, and since Linux 6.6 the default pod is the
last level cache; RHEL 9 carries that change.  From 7.1 the
default is an 8 core shard of the cache instead.  Where the pod
is one CCD of 8 CPUs, every OSC's RPC build still runs in the
submitter's CCD, and a single thread's striped IO gains little
over the system workqueue.  A module cannot change a
workqueue's scope.

Queue each OSC's writeback work at a core of the submitting
thread's node, in bit reversed order of the device index, so
consecutive OSCs are far apart in the node's core order.  Only
the first thread of each core is used: SMT siblings share a
cache, so a second OSC landing on one would build in the
first's pod.  Core order is not pod order, so this spreads the
OSCs well rather than perfectly.

An unplug is queued on every extent release and RPC completion,
so the chosen CPU is kept on the client rather than walking the
node's CPU mask each time.  There is one slot, so an OSC whose
unplugs arrive from two nodes recomputes whenever the node
changes; it is the single node case that the walk cost hurts.
