LU-18511 gss: carry out negotiation again on empty ccache

lgss_keyring prepares the root credential in
lkrb5_prepare_root_cred(), which checks the credentials cache and
obtains a new TGT from the keytab if needed, serialised with the
other lgss_keyring processes by a semaphore. But the credential
itself is not held, and it does not help to hold one: an INITIATE
gss credential obtained from the default cache only keeps a
krb5_ccache handle, and krb5_gss_init_sec_context() reads the
tickets from that cache when it is called, through
krb5_get_credentials().

So emptying the cache in between makes gss_init_sec_context()
return GSS_S_NO_CRED. This happens when something runs kdestroy or
kinit, and also when another lgss_keyring renews the root TGT,
because lkrb5_get_root_tgt_keytab() empties the cache with
krb5_cc_initialize() before filling it again with
krb5_cc_store_cred().

Such a failure is transient, and always recoverable for root, whose
credential can be obtained from the keytab again. But it is treated
as fatal: gss_kt_update() turns it into -EACCES and sets
PTLRPC_CTX_ERROR_BIT, then sptlrpc_req_refresh_ctx() only looks for
an already existing context for root, finds none just after a
flush, and completes the request with -EPERM. The application ends
up with an error on an operation that should merely have waited for
a new context.

So when the negotiation of a root context fails with GSS_S_NO_CRED,
get a new credential and carry the negotiation out again. This time
ask for a private copy of the credentials cache, in memory, made
while still holding the semaphore so that no other lgss_keyring can
be emptying the shared cache. Nothing outside of this process can
empty that copy, so the negotiation cannot fail again for the same
reason and a single retry is enough. Only the retry pays for it, so
the usual path keeps sharing its service tickets with the other
lgss_keyring processes.

While here, release the negotiation data before retrying, which the
existing retry path forgot to do, leaking the service name and the
partial context.

Also make 'lfs flushctx -k' run kdestroy before the ioctl that
flushes the contexts, instead of after it. Running it afterwards
empties the credentials cache just as the gss upcalls triggered by
that very flush are starting, which is the easiest way to hit this
race.

Add sanity-krb5 test_91, which recreates that ordering explicitly,
under dbench load.
