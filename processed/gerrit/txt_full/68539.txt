LU-20668 ldlm: sample l_completion_ast under the resource lock

An MDT umount can LBUG with
ldlm_server_completion_ast()) ASSERTION( data != NULL ) failed.

cleanup_resource() decides to fake a blocking AST for a lock that
still carries local references, but it reads l_completion_ast only
after dropping the resource lock.  In that window an MDT service
thread finishing an intent enqueue can run mdt_intent_lock_replace(),
which drops those references and installs ldlm_server_completion_ast()
in their place - and that callback needs a ldlm_cb_set_arg, which the
cleanup path has none of.

Sample the callback together with the reference counts, while the
resource is still locked.

server_put_super() sets OBDF_FORCE unconditionally, so every MDT
umount takes this LDLM_FL_LOCAL_ONLY path, not just umount -f.

A lock handed over inside that window is not left behind: class_cleanup()
disconnects every export before obd_precleanup() gets to mdt_fini(), so
such an enqueue always finds rq_export->exp_disconnected and cancels the
lock it has just given away.

Add replay-single test_204 and the two pauses it needs: one parks an
MDT thread between the grant of a local intent lock and its handover
to the client, the other holds the namespace cleanup of a concurrent
umount inside the window it has just sampled.  The latter is limited
to server namespaces so that a combined MDS/client node does not stall
its mdc/osc/osp cleanups as well.

Fixes: 6b810c5a75e9 ("Instead of sending blocking and completion callbacks as separated requests, adding them to a set and sending in parallel.")
