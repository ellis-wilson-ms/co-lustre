LU-20703 llite: limit readahead window by the readahead budget

The per-file readahead window is capped by ra_max_pages_per_file,
independently of the global readahead budget ra_max_pages
(llite.*.max_read_ahead_mb).  When the budget is set below the
per-file window (e.g. sanity/101d sets max_read_ahead_mb=40 while
max_read_ahead_per_file_mb=64 on a 64K-page client), the readahead
window target exceeds the whole readahead budget, and then:

* the async readahead gate in kickoff_async_readahead() is never
  satisfied: the throttle defaults to ra_max_pages_per_file, so
  the gate only opens at the maximal window, but a cache miss
  runs ras_reset() and drops the window back to 0, and it takes
  ra_max_pages_per_file / ras_rpc_pages growth steps to climb
  back;
* every cache miss runs a synchronous readahead walk that reserves
  the whole remaining budget and holds it until its read RPCs
  complete;
* while the budget is in flight the reader catches up with the
  readahead frontier, and further misses can only reserve one page
  via the pages_min override, degenerating into a storm of one-page
  (64KB) read RPCs plus per-miss readahead state and lock-match
  overhead, making the readahead-enabled read slower than the
  readahead-disabled one: "readahead 22.8092s > no-readahead
  10.3606s (80M)".

Limit the effective per-file readahead window by the readahead
budget with a new helper ra_max_window_pages(), and use it where
the window growth is capped (ras_stride_increase_window(),
ras_increase_window()), where the whole-file-read window is
initialized (ll_ras_enter()) and in the async readahead gate
(kickoff_async_readahead()).  The stored tunables are unchanged,
so raising max_read_ahead_mb again restores the original behavior.

The window grows in ras_rpc_pages steps once it reaches one RPC
(ras_increase_window() aligns every step), so it tops out at
ra_max_window_pages() rounded down to the RPC size.  Round the
async readahead throttle down to the same granularity, otherwise
it can exceed every value the window can take and async readahead
never fires (e.g. brw_size=16 on a 64K-page client with
max_read_ahead_mb=40: window tops out at 512 pages, throttle is
640).  Throttles below one RPC are left unaligned, since such
windows are still reachable via the sub-RPC window in
ras_increase_window().

Also add opt-in (DEBUG_101D=1, or DEBUG_101D=trace to also capture
the D_READA trace) instrumentation to sanity/101d, which dumps the
readahead parameters, readahead stats and read RPC size histogram
around the measured reads, and restores the debug mask via
debugsave()/debugrestore() when tracing.
