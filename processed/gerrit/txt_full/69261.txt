LU-20808 mdt: read a remote create parent with its lock

When the parent of a create is remote, take its locks through
mdt_parent_lock_read(), which attaches an IT_MDT_TO_MDT_READ to the
name-hash lock enqueue. While it grants the lock, the MDT owning the
parent resolves the name and reads back what the create reads next:
the parent attributes and ACL for the permission checks and for SGID
and project inheritance, the default ACL, pin and default layouts the
child inherits, and the LMV that places the name. That state lands in
the OSP cache, and the name's resolution comes back to mdt_create().

mdt_create() then does not look the name up again under the lock. It
makes the search permission check that lookup would have made itself,
with mdt_dne_read_lookup(), from the cached parent state, and leaves
everything else to mdd_create() as before, which now finds what it
reads in the cache. The only other difference is that mdd_create()
does not repeat its sanity lookup for a remote parent, since the name
was resolved under the lock; it checks write permission on the parent
in its place, as it does for a local one.

A create under a local parent is left exactly as it was, since reading
a local parent costs no RPC. Nothing here changes create semantics. A
reply that does not come back - from an older MDT, for an intent that
could not be packed, or for a lock that was not free at once - or that
could not resolve the name leaves the ordinary lookup in place, with
the locks held. Replay always takes the ordinary path: it may have to
cope with a create that was only partially executed. A restripe
reaches the lock only as an ordinary create, since the lookup before
it has already restriped an existing directory, so it uses the intent
like any other create.

A permission error from mdt_dne_read_lookup() now fails the create at
once. The lookup it replaces fell through to mdd_create(), which
turned the same error back into a failure later.

The intent state is allocated on a thread's first remote-parent
operation and kept until the thread exits, rather than grown into
mdt_thread_info, which has to fit in a page.
