LU-20837 libcfs: add tracepoints for Lustre debug messages

The current Lustre FS debugging approach is robust, always ready,
and quite flexible. However, it is still not appropriate for
run-time dynamic analysis. Also, sometimes it has trouble capturing
a sufficient amount of continuous logs.

In addition to the original debug logging system, kernel tracepoints
have been added. They enable external tools to capture, filter,
and analyze debug messages with negligible overhead when disabled.
Such tools can be used for efficient log capturing, run-time
analysis, and more.

The approach is quite simple. Two tracepoints are added to
libcfs_debug_msg(): lustre_debug_location carries the file,
function, line, subsystem and mask of a message, and
lustre_debug_msg also carries its formatted text. Both fire for
every message that reaches libcfs_debug_msg(), i.e. that passes
the debug and subsystem_debug masks or is D_ERROR, D_EMERG,
D_WARNING or D_CONSOLE, even when it does not reach the debug
buffer (e.g. in IRQ context or when no trace page is available).

To illustrate how this works, a lustre_debug_msgs.py tool was
added. It allows capturing Lustre logs at runtime. It supports
filtering by subsystem (-s) and mask (-m) in the BPF program,
and by source file name (-f).

For example, execute this on a system with Lustre FS:
sudo python3 lustre_debug_msgs.py -s S_RPC -m D_ERROR
This will capture any errors that happened in the RPC subsystem.

sanity test_60k checks that "lctl mark" output reaches the
lustre_debug_msg tracepoint through a private tracefs instance.

There were timed 1M CDEBUG(D_INFO, "... %d %s\n") calls from a
small test module with ktime, in a 4-vCPU VM (Xeon E5-2650 v4,
6.12 kernel). 5 runs, median:

                         message passes mask   message masked
                         (debug=-1)            (debug=0)
without patch            361 ns                0.8 ns
patch, tracepoints off   368 ns (+2%, noise)   0.8 ns
patch, ftrace enabled    842 ns                0.8 ns
patch, bcc tool attached 839 ns                -

With the tracepoints off, the hook is a static-key branch, and
the difference is within noise. A masked-off CDEBUG never reaches
libcfs_debug_msg(), so it costs the same ~1 ns in every case.
With a consumer attached, each message that passes the mask costs
about 2.3x: it is formatted a second time and written to the
trace buffer.
