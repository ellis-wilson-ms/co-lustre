LU-20559 misc: keep updates out of assertion conditions

Four more places put a state change in the condition of a LASSERT(),
which expands to ((void)sizeof!!(cond)) with --disable-libcfs-assert
and takes the change with it.

dt_los_put() drops its reference there, so the one dt_los_find() took
is never released, local_oid_storage_fini() never sees the refcount
reach zero, and the los, its los_obj and the ls_device reference all
leak for the life of the mount.

obd_get_mod_rpc_slot() and obd_put_mod_rpc_slot() set and clear the
cl_mod_tag_bitmap bit there. With the set gone the bitmap stays empty,
so find_first_zero_bit() returns 0 for every caller and every modify
RPC in flight is issued with tag 1. The tag identifies the slot the
reply is reconstructed into, so they collide.

nrs_tbf_cli_fini() sets NRS_TBF_CLI_DEL_BIT there, so the client is
never marked deleted.

Do the update first and assert on its result, as the rest of this
series does for lut_client_bitmap. Assert-enabled builds are
unchanged.

In genops.c the range checks gate the set and the clear rather than
merely asserting on them, so the bound survives where the assertion
does not: cl_mod_tag_bitmap holds only OBD_MAX_RIF_MAX bits.

This is not the whole sweep: gnilnd_conn.c and gnilnd_cb.c have the
same shape on their bit arrays. They are left alone because that LND
is not built in the configuration this was tested in.

None of it is reachable through a test - the failure only appears in a
build configured with --disable-libcfs-assert - so this is by
inspection.
