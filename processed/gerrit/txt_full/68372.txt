LU-10026 tests: add sanity-compr test for compression

This patch adds a sanity-compr test to validate that
we get space usage reduction with compression.
The test uses ll_compression_scan tool to calculate
the compressed size of the source file and compares
it with the size of the Lustre CSDC compressed file.

tests: add sanity-compr test for dir compression

This patch adds a sanity-compr test to validate that
we get directory space usage reduction with compression.

DDN-bug-id: EX-9871
Was-Change-Id: I0dc3d44c300708f3a25bfce06b81993cdd30c418

tests: change source dir for sanity-compr/1008

While the source directory contains almost all small files,
sanity-compr test_1008 will hit the
"failed estimates > 50% of total estimates" failure on SLES15.

The patch fixes the issue by changing the source dir to
contain large files.

DDN-bug-id: EX-9125
Was-Change-Id: Iad661750cba7c9d2204f2306e73169deb012ddf4

utils: fix ll_compression_scan overflow

Fix the total size estimate calculation to avoid overflow for
large total sizes.  Otherwise, the intermediate register used
for the calculation will overflow and produce an invalid estimte.

DDN-bug-id: EX-9125
Was-Change-Id: I12099cea1268abede17c92e0422b6c1c25ac66d5

tests: sanity-compr/1008 CentOS 7.9 more margin

For sanity-compr test_1008 allow a higher margin of error for
CentOS 7.9 clients because they consistently show slightly
worse compression ratios and fail the test.  It isn't clear
if this is because of worse/partial RPC formation or because
the compression code in this kernel is less optimal.

These tests should still be run to ensure the code is working, but
not fail so much, because fixing these old clients is not critical.

DDN-bug-id: EX-9125
Was-Change-Id: I6c1c6044daf5d0706cfb661b4f0f051769174ff9

tests: get stats_compr param in sanity-compr/1007

This patch adds getting stats_compr param in sanity-compr
test 1007 and 1008 to track data compression statistics.

systems.

Patch Set 2:

test_1008 fails on a stock EL9 OSS, and I believe it is waiting on 62408 rather than on anything in this patch.

From the run:

    gzip, level 1, chunk 64K: estimated 17225 KiB, CSDC 17456 KiB   ok
    gzip, level 6, chunk 64K: estimated 16456 KiB, CSDC 17456 KiB   6% > 5% margin

The two CSDC sizes are identical to the byte.  ll_compression_scan -l 6
uses userspace gzip, which honours the level; the server maps -Z gzip to
the kernel's deflate, which ignores the level entirely.  So the sweep
compares a level-honouring estimate against a fixed-level result, and the
gap grows with the level.  The lgzip module in 62408 is what makes the
level real.

The same holds for zstd until 66001 lands: on this OSS, -Z zstd:1 and
-Z zstd:19 over the same data produce byte-identical output.

Two ways out: gate the level sweep on the l* modules actually being
loaded (test-framework's load_compression_modules() already reports when
they are not), or leave it and let it pass once 62408 and 66001 land.  As
it stands the EX-7795 ignore fires but the subtest still reports FAIL.

Minor, separate: the "'lz4' not found" / "'lzop' not found" lines from the
utility probe are harmless but read like errors in the log.
