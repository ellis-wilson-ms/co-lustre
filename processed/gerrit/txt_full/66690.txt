LU-20400 o2iblnd: fix descriptor leak on FastReg map error

kiblnd_fmr_pool_map() removes a fast registration descriptor from
fpo->fast_reg.fpo_pool_list and bumps fpo->fpo_map_count before
calling ib_map_mr_sg(). When ib_map_mr_sg() short-maps the
scatterlist (n != rd->rd_nfrags), the function returns the error
without returning the descriptor to the pool and without dropping
the map count. It also leaves fmr->fmr_frd and fmr->fmr_pool NULL,
so the caller's kiblnd_fmr_pool_unmap() is a no-op and cannot
recover them.

Each short-map therefore leaks one descriptor and one pool
reference. Because fpo_map_count never returns to zero,
kiblnd_fmr_pool_is_idle() never reports the pool idle, so it is
never reaped. Under a workload that produces gapped transfers
(which fail ib_map_mr_sg() repeatedly) the FMR pool grows without
bound.

On the error path, reacquire fps_lock, return the descriptor to
fpo_pool_list, mark it not posted, and decrement fpo_map_count, the
same cleanup kiblnd_fmr_pool_unmap() performs. fmr_frd and fmr_pool
are intentionally left NULL.

Add a fault-injection point, CFS_FAIL_O2IBLND_FMR_MAP_SHORT,
that forces a short-map result so the cleanup path can be
exercised deterministically without a real gapped layout. With the
leak present, fpo_map_count never returns to zero and
kiblnd_destroy_fmr_pool()'s LASSERT(fpo_map_count == 0) fires on
module unload; with the fix, unload is clean.

Small cleanup in kiblnd_setup_rd_kiov() is also included. The code
that checks for gaps includes a "+ offset" where offset is always 0.
Remove it.

The fix itself looks correct: the error path re-takes fps_lock and returns the descriptor to fpo_pool_list, clears frd_posted, and drops fpo_map_count, mirroring kiblnd_fmr_pool_unmap(); fmr_frd/fmr_pool stay NULL so the caller's unmap is a safe no-op. Two points below.
