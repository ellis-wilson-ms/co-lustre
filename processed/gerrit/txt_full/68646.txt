LU-19878 tests: report a give-up in force_new_seq_ost()

force_new_seq_ost() polls prealloc_last_id/prealloc_next_id until the
OST has precreated objects on the new sequence.  If precreation never
becomes ready the loop simply falls out silently, and the suite that
fails later has nothing in its log saying why.  Echo the give-up with
the ids it was polling.  A return code would not reach the main
caller: force_new_seq() runs the helper as a background job and
collects it with a bare "wait", which discards per-job status.

Say what the loop waits for as well: prealloc_next_id is the next
object to hand out and prealloc_last_id the last one precreated,
so the number of free objects is last - next + 1 and the bound asks
for a new batch with objects to spare.  Correct the comment on the
wait too - each iteration sleeps on top of two remote lctl calls, so
a full wait takes well more than qos_maxage seconds.

The helper is shared, so none of this is specific to conf-sanity/155:
sanity/test_27Cd and several sanity-pfl subtests call
force_new_seq_all() directly, runtests and replay-single-lmv call it
at setup, the other replay-* suites and recovery-small call it at
setup on an MDS older than 2.15.61.226, and run_rr_alloc() calls
force_new_seq_ost() itself.

conf-sanity test_155 keeps its own guards, because the wait only makes
OST0000 available again: "lfs setstripe -i 0" is a preference, and
lod_ost_alloc_specific() still walks on to another OST when
lod_statfs_and_check() rejects the requested one.  Write those guards
in the suite's usual "positive condition || action" form and name the
OST index the object landed on, so the skip says what happened.  The
"$" inside (( )) has to go with it: when getstripe prints no l_ost_idx
line, "(( $idx != 0 ))" is a bash arithmetic syntax error, so default
the index instead and let the empty case skip with the index printed.
