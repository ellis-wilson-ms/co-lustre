LU-10026 csdc: set compress component for file

Introduce per-component compression support for composite LOV layouts.
A new LCME_FL_COMPRESS component flag marks entries that carry
compress fields; the flag is set when the user supplies a compression
type via 'lfs setstripe -Z' and is propagated through the LOD and LOV
layers so that compressed components are distinguished from plain
ones.

LOD layer:
- lod_parse_striping(): read lcme_compr_type/lvl/chunk_lum_bits from
  the user-supplied lov_comp_md_v1 when LOV_PATTERN_COMPRESS is set.
- lod_use_defined_striping(): likewise for pre-defined layouts.
- lod_get_default_lov_striping(): carry compress fields into the LOD
  component when inheriting a default layout that includes
  compression.
- lod_generate_lovea(): serialise llc_compr_* fields into the on-wire
  lcm entry when LOV_PATTERN_COMPRESS is set.
- lod_adjust_compr_chunk_size(): new helper that rounds down the
  requested chunk-size exponent so the chunk fits evenly within one
  stripe and within one RPC (clamped to COMPR_CHUNK_MAX_BITS in the
  following changes).

API / utils layer:
- 'lfs setstripe' gains --compress|-Z <type>[:<level>] and
  --compress-chunk=<size> options to set the compression type, level,
  and chunk size on a new component.  Like -S and -c, -Z is inherited
  by subsequent -E components unless overridden by another -Z.

  Example:
	$ lfs setstripe -Eeof -Z lz4:5 --compress-chunk=512 <file>

- 'lfs getstripe' gains --compress-type, --compress-level, and
  --compress-chunk options to print individual compress parameters:

  Example:
	$ lfs getstripe <file>
    lcme_compr_type:     lz4
    lcme_compr_lvl:      5
    lcme_compr_chunk_kb: 512
      lmm_pattern:       raid0,compress

- llapi_layout_merge(): copy compress fields when merging layouts.
- Two new man3 pages: llapi_layout_compress_set.3 and
  llapi_parse_compress_type.3.

Misc:
- dump_lsm() in lov_ea.c prints compress fields for debugging.
- compr_name_from_type() helper added in lov_internal.h and wired up
  in dump_lsm() to print compression type names in debug output.

sanity-compr test_1000d fails because lfs getstripe shows no compression attributes for a directory's default layout.  --compr-type, --compr-level, --compr-chunk and --compress-chunk all come back empty on a directory, though they work on a file.

test_1000d does:

    local dchunk=$($LFS getstripe --compress-chunk $DIR)

and then compares every inherited value against $dchunk, so it is comparing against an empty string and fails on the first file it checks.

The values are on disk.  Decoding the directory's lustre.lov EA after
"lfs setstripe -Z lz4 --compress-level=9 --compress-chunk=128 $DIR":

    lcme_compr_type = 5 (lz4)
    lcme_compr_lvl = 8 (mapped back to 9)
    lcme_compr_chunk_lum_bits = 1 (128K)
    lcme_flags = 0x0
    lmm_pattern = 0x801  (LOV_PATTERN_COMPRESS set)

lov_dump_comp_v1_entry() gates the whole compression block on
LCME_FL_COMPRESS.  The MDT sets that when it packs a file layout
(lod_lov.c, under "if (lod_comp->llc_pattern & LOV_PATTERN_COMPRESS)")
and llapi never sets it when building a layout, so a directory's
default layout never has it.  The pattern is the signal, and
llapi_layout's own parsing path already uses
"v1->lmm_pattern & LOV_PATTERN_COMPRESS" rather than the flag.

What I tested, in lov_dump_comp_v1_entry():

    -       if (entry->lcme_flags & LCME_FL_COMPRESS) {
    +       /*
    +        * A directory's default layout never gets LCME_FL_COMPRESS: the MDT
    +        * sets that when it packs a file layout, so only the pattern says
    +        * whether the component is compressed.
    +        */
    +       if (entry->lcme_flags & LCME_FL_COMPRESS ||
    +           (entry->lcme_size >= sizeof(struct lov_user_md_v1) &&
    +            ((struct lov_user_md_v1 *)((char *)comp_v1 +
    +               entry->lcme_offset))->lmm_pattern & LOV_PATTERN_COMPRESS)) {

test_1000d passes with that.  Setting LCME_FL_COMPRESS on the directory
default layout instead would also work for new directories, but the
display path has to cope with existing ones either way.

Happy to push this as its own patch if you would rather not carry it here.
