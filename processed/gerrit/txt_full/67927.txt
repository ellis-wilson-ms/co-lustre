LU-20580 o2iblnd: don't sleep in atomic in kiblnd_startup()

kiblnd_startup() queried the net device inside the
kib_global_lock write section. lnet_get_link_status() takes
rtnl_lock(), which is a mutex and can sleep. The query therefore
ran with preemption disabled and interrupts off.

On a kernel without CONFIG_DEBUG_ATOMIC_SLEEP, the uncontended
mutex fast path does not schedule and reports nothing. With that
option set, might_sleep() reports every call. When another task
holds rtnl_mutex,
__mutex_lock_slowpath() calls schedule_preempt_disabled() and
the kernel reports "BUG: scheduling while atomic". The system
reaches this path at boot, when the network subsystem holds
rtnl_mutex while LNet starts. The node then does not boot.

schedule_debug() then calls preempt_count_set(PREEMPT_DISABLED),
which leaves the count unbalanced.

Drop kib_global_lock before the query, and hold rtnl_lock()
across the query and the update instead. The net is on ibd_nets
before the query. The netdev notifier walks that list, and also
runs under rtnl_lock(). The notifier therefore cannot make the
query result stale before the update applies it.
kiblnd_set_ni_fatal_on() walks ibd_nets, so it still takes
kib_global_lock. The lock order is rtnl_lock() first.

The query now calls __dev_get_by_name() and
lnet_get_link_status_locked(). These functions expect the caller
to hold rtnl_lock(). __dev_get_by_name() takes no reference, so
the code no longer calls dev_put(). The old
code called dev_put() even when the lookup returned NULL. Before
v5.17, dev_put() has no NULL check and faults.

kiblnd_dev_failover() clears the fatal flag from the same query.
There, rtnl_lock() covered only lnet_get_link_status(), so the
lock did not span the update. The flag also changed without
kib_global_lock. That branch takes the same two locks now, in
the same order.

Both call sites also hold netdev_lock_ops() across the query.
lnet_get_link_status() takes that lock with rtnl_lock().
ethtool_op_get_link() calls __linkwatch_sync_dev(). That function
asserts the instance lock on a device which needs it. These two
sites call lnet_get_link_status_locked() directly. They must
therefore take the lock themselves. netdev_lock_ops() is a no-op
on a kernel without HAVE_NETDEV_LOCK_OPS.

Before the Fixes commit, the query was already inside the lock.
That commit added rtnl_lock() to lnet_get_link_status(), which
made the query sleep. A later commit removed the RCU read
section that once wrapped the query. The sleep stayed in place.
