LU-20559 tests: cover the OST mount error path

Add conf-sanity 165 for the two leaks the preceding patches fix. It
fails an OST mount with OBD_FAIL_MDS_FS_SETUP, which ofd_fs_setup()
has carried for years, and then mounts the target again.

The second mount is what the lustre_sb_info leak prevents: without
that fix it returns -EALREADY, because the <target>-osd device the
failed mount left behind is still registered. The case therefore tells
a patched OST from an unpatched one.

It also leaves the node able to unload its modules, which the export
leak prevents - though only in a build with --disable-libcfs-assert,
where the assertions that would have caught the state are compiled
out. The case does not assert on that, since a passing conf-sanity run
says nothing about it either way.

Beyond the remount it checks that every client recovers, not just one:
the MDT's osp connection counts as a client here, so a "> 0" test is
satisfied even when the mounted client was evicted. And it compares
the file back byte for byte against a pattern written before the
failure - dd exits 0 on a short read, so reading into /dev/null would
pass with the object gone.

The case also sets OBD_FAIL_TGT_CLIENT_DEL around the stop, which is
what leaves the client's last_rcvd slot in place - without it the
failed mount has no recovery exports to strand and neither leak
appears.

No new fail_loc is needed: 0x135 already sits inside ofd_fs_setup()
and leaves through its own out_seqs label, so what it unwinds matches
what a real failure there unwinds. The two existing users, 5h and 26,
set it on the MDS.
