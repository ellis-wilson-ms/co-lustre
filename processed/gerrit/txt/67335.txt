LU-19862 osd: keep a_ops in sync with the inode journal mode

osd_ldiskfs_write()/osd_ldiskfs_write_fast() put llog inodes into
data=journal mode by setting LDISKFS_INODE_JOURNAL_DATA directly on
ei->i_flags.  ldiskfs picks inode->i_mapping->a_ops in ldiskfs_iget(),
via ldiskfs_set_aops(), from ldiskfs_inode_journal_mode() - i.e. before
that flag is set.  Since osd mounts with nodelalloc, the inode ends up
with ldiskfs_should_journal_data() == 1 but a_ops still == ldiskfs_aops
rather than ldiskfs_journalled_aops.

That inconsistency bites in ldiskfs_dirty_journalled_data(), which does
folio_mark_dirty() before handing the buffer to jbd2:

	if (S_ISREG(inode->i_mode))
		folio_mark_dirty(folio);
	return ldiskfs_handle_dirty_metadata(handle, NULL, bh);

With ldiskfs_journalled_aops, ->dirty_folio is filemap_dirty_folio(),
which leaves the buffers alone.  With ldiskfs_aops it is
block_dirty_folio(), which sets BH_Dirty on every buffer of the folio.
jbd2_journal_dirty_metadata() then files a plain-dirty buffer as
journalled metadata and complains:

	JBD2: Spotted dirty metadata buffer (dev = dm-0, blocknr = 57266).

A journalled metadata buffer carrying BH_Dirty later trips

	J_ASSERT_BH(bh, !buffer_dirty(bh))

in jbd2_journal_commit_transaction()'s BJ_Forget loop, panicking the MDS
on umount:

	kernel BUG at fs/jbd2/commit.c:1022!

The only caller reaching ldiskfs_dirty_journalled_data() for these inodes
is ldiskfs_block_truncate_page(), which zeroes the tail of the last
partial block.  osd_drop_preallocated_space() calls ldiskfs_truncate()
from osd_object_delete() to give back the blocks preallocated by the
batch allocator, so every eviction of a partially-filled llog object hits
it - and at umount the whole LU object cache is purged at once, which is
why the warnings arrive in a burst just before the panic.

Call ldiskfs_set_aops() when the flag is first set, so a_ops matches the
journal mode, exactly as ldiskfs does for an inode read in with the flag
already on disk.

Note the blocks freed by the truncate are not the problem: they are
forgotten correctly.  The offending block is the one the truncate keeps.

Add the jbd2 warning to check_dmesg_for_errors() so this is caught by
every suite rather than only when it escalates to the assertion.  The
message warns of on-disk corruption and should never appear.  Without the
osd fix sanity-scrub test_22 now fails in 9s ("Error in dmesg detected")
instead of relying on the much rarer panic.
