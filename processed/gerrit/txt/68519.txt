--- Commit Message ---
LU-17000 ofd: do not use a list iterator after the loop

ofd_intent_cb() decides "found it" from the list_for_each_entry()
iterator after the loop.  When the loop runs to completion the iterator
holds a pointer computed from the list head, which is not NULL, so the
later test succeeds and the code works on a bogus object.

The OBD_FAIL_OST_GL_WORK_ALLOC injection deliberately skips the
allocation and relies on gl_work still being NULL, but the preceding
loop has already overwritten it, so the simulated ENOMEM path is never
taken.  A real allocation failure assigns NULL and is unaffected.

gl_list sits at offset 8 of struct ldlm_glimpse_work and is the first
member of struct ofd_intent_args, so the stale iterator resolves to
(char *)&arg - 8 in ofd_intent_policy()'s frame.  The gl_lock store
lands 8 bytes below arg, outside the object, and list_add_tail() then
links arg.gl_list to itself, leaving the list empty, so the cleanup
loop in ofd_intent_policy() never runs and the ldlm_lock_get()
reference is leaked.  The gl_desc and gl_flags stores that follow would
overwrite arg.no_glimpse_ast, arg.error and arg.size; on a
CONFIG_BUG_ON_DATA_CORRUPTION kernel the list_add_tail() kills the
thread first, and without CONFIG_DEBUG_LIST none of it is caught at
all.

Walk the list with a separate variable so the result only ever holds a
real list entry.

Reproduced on an OSS with fail_loc=0x240: without this patch the node
panics 20us later with "list_add double add: new=X, prev=X, next=X" at
lib/list_debug.c:29, in ofd_intent_cb().  With it the injection returns
-ENOMEM as intended and the OSS stays up.
