LU-20055 llite: bump i_version on lock loss

NFS uses it to determine if the file has changed in addition to
timestamps (and we don't have nanosecond timestamps, so
any sub-second update is at risk).

cl_object_attr_update() works on the osc/mdc sub-object only walks that sub-object's own layer list (lovsub, osc/mdc) and never reaches vvp_attr_update(), so 882b41365a4e never actually bumped i_version, so the fix here is a second update issued against cl_object_top() to reach the vvp layer.

Fixes: 882b41365a4e ("LU-19237 llite: Update i_version when losing osc/dom lock")

Experimental feature testing in progress, please pay attention to the comments

Looks correct. The sub-object cl_object_attr_update() only walks the osc/lovsub slices (osc_attr_update sets loi_kms), so it never reaches vvp_attr_update() where CAT_KMS bumps i_version; hitting cl_object_top() adds the vvp/lov slices, and since lov_attr_update() is a no-op the only visible effect is inode_inc_iversion(), so there's no risk of overwriting the top-level size with a per-stripe kms. One thought: this fixes an NFS-visible cache-coherency bug with no accompanying test. A reexport/i_version regression test is admittedly awkward to write, but worth considering if one is feasible.

Mostly good, comments inline. This does fix a real no-op: the CAT_KMS branch that 882b41365a4e added to vvp_attr_update() was unreachable, because nothing in the tree ever passed CAT_KMS to a top object.

One question on the approach: ldlm_cancel_callback() runs the CANCELING blocking AST for every cancel, including purely local ldlm_cancel_lru() trims where no remote node touched the file. On a re-export server that changes the NFSv4 change attribute and makes NFS clients drop their caches for no reason. Is it worth limiting the bump to cancels driven by a conflicting lock?

Nothing exercises the new behavior either; a parallel-scale-nfs style case showing a second NFS client picking up the update would make this much easier to keep working.
