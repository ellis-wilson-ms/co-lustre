LU-20157 llite: clear PageUptodate only on reclaim

vvp_page_delete() cleared PageUptodate on every cl_page teardown.
This violates the kernel invariant, relied upon since v5.13
79e3094c53c5 ("mm/filemap: drop check for truncated page after I/O"),
that invalidation leaves PG_uptodate intact.  A buffered read racing
a DLM blocking AST could therefore find a !uptodate folio and return
-EIO (LU-16651) instead of retrying.

The flag is only needed where page removal can fail after the cl_page
is already gone.  That is the reclaim path alone: do_release_page()
commits cl_page_delete() before __remove_mapping() decides whether
folio_ref_freeze() succeeds, so an extra vmpage reference can leave a
folio in the mapping with no cl_page.  Such a folio is invisible to
osc_page_gang_lookup(), which walks osc->oo_tree rather than
mapping->i_pages, and would be served stale forever.  Every other
caller removes the folio unconditionally: cl_page_discard() via
generic_error_remove_folio() on the AST path, and
ll_invalidate_folio() via filemap_remove_folio() on truncate.

Move the clear into do_release_page(), inside the !cl_page_in_use()
branch so it fires only when the cl_page is actually destroyed.  The
lli_page_inv_lock seqlock is retained; its only writer is now the
reclaim path named in LU-16160.

With the AST path no longer clearing PG_uptodate, it no longer needs
to exclude page cache filling, so drop ci_invalidate_page_cache and
the filemap_invalidate_lock() pair added by LU-16651. This also
removes the AST-vs-IO deadlock of LU-19427, whose fix was reverted.
The HAVE_INVALIDATE_LOCK configure check has no remaining users and is
removed.

The reclaim refcount race itself is deliberately left alone, and
PG_uptodate is still cleared to mask it.  Gating the teardown on a
page_ref_freeze() of the vmpage was tried and rejected: where the
freeze succeeds the folio is freed and PG_uptodate is never observed,
so skipping the clear gains nothing, while a removal that still fails
in the residual window between the unfreeze and __remove_mapping()
would leave an orphan with PG_uptodate set.  Aborting the release on a
failed freeze does prevent orphans, but changes ->release_folio
semantics for every caller and regressed sanity 255b and 398a.
Closing the window properly requires deferred teardown from
->free_folio.
