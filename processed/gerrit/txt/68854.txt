--- Commit Message ---
LU-17296 nrs: order BRW RPCs by offset inside an mClock class

The queue of an mClock class bucket is FIFO. A fair shared HDD OST
loses the seek order that the ORR policy gives.

Add a "locality=" key to the mClock policy start command. Each class
bucket then also sorts its BRW RPCs by the offset of the first
fragment. Equal offsets keep the arrival order. A class can hold many
objects, so the key helps most with one large object for each class.
TBF returns -EINVAL for the key.

The YAML rule dump adds an offset_insert counter. The mClock
D_RPCTRACE dequeue line shows the BRW offset. The mClock request grows
to 64 bytes.

Add sanityn/test_77xe.

Some concerns. The design objection from the patchset 1 thread is still open on this revision: ordering a bucket purely by logical offset, with no object identity and no bounded per-object batch, was questioned as counter-productive for backend block allocation and as a way to starve an already-queued request. Patchset 2 answers it by documenting the limitation in the commit message and the man page, but the comparison itself is unchanged, so the request for bucket/object selection followed by a size-bounded offset-ordered batch has not been answered in code and the thread is unresolved. Since the key is opt-in and off by default, nothing here demands an immediate re-spin, but that thread looks like it should close before this lands. The inline items are optional nits to pick up on the next refresh.
