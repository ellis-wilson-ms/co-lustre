LU-19699 quota: release grant via DQACQ on qunit shrink

qsd_id_glimpse_ast() returns the surplus space in the glimpse
reply and drops it from lqe_granted right away, but the slave
QSD never learns if the master fails to apply that release in
qmt_lvbo_update(), then the master keeps more grant accounted
than the slave owns, and the leak eventually causes a bogus
-EDQUOT. OBD_FAIL_QUOTA_PREACQ (fail_loc=0xa06) triggers this
and cause test_80 in sanity-quota.sh to fail intermittently.

Only report the surplus in lvb_id_may_rel and let the regular
DQACQ release path return it, then it will be transactional
and retried on failure, so the two sides cannot diverge.

The master still handles lvb_id_rel in qmt_lvbo_update() so
that older slaves keep working during a rolling upgrade. In
the other direction, a patched slave with an unpatched master
still releases via DQACQ, but the old master only waits the old
QMT_REBA_TIMEOUT of 2s from "lqe_revoke_time" before setting
edquot, so a transient -EDQUOT is still possible in that mixed
version window.

qmt_adjust_edquot() is now the only thing holding edquot off
until the DQACQ arrives: anchor its grace period to the reply
that claimed the release (lqe_may_rel_time) rather than to
"lqe_revoke_time", which may be much older, and also raise
"QMT_REBA_TIMEOUT" to 10s to cover the extra round trip and
the QSD update thread scheduling, otherwise the master sets
edquot first and clients see a transient -EDQUOT.

That hold-off has to cover the pool lqes too, not only the
global one: record lqe_may_rel/lqe_may_rel_time on every lqe of
qti_lqes in qmt_lvbo_update(), so that a pool lqe marked edquot
by qmt_set_revoke() in the same call is held off as well. Ending
the hold-off as soon as the quota space comes back: subtract the
released count from lqe_may_rel in qmt_dqacq0(), so the timeout
only acts as a ceiling for a slow or lost DQACQ instead of always
delaying edquot by the full 10s.
