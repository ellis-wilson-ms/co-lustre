LU-20613 llapi: add a ZFS backend to llapi_scan_device()

Add scan_osd_zfs.so, the ZFS half of llapi_scan_device(), which reads
objects out of a pool through libzpool the way zdb does, behind the
same llapi_scan_sink the ldiskfs backend is behind.

A pool that is still imported answers EBUSY rather than being read
underneath its server: reading an imported pool from outside is not
supported, so the pool has to be exported first, and its snapshots
then become readable too. lfsp_search names the directories to look in
for a pool's vdevs, since a pool on file vdevs is invisible to a scan
of /dev. The scan loads no /etc/zfs/zpool.cache: a pool listed there
would be opened directly, before those checks, and a pool the kernel
holds would answer EREMOTEIO instead of EBUSY. ZFS 2.4 also falls back
to /boot/zfs/zpool.cache, so the scan drops every pool that
kernel_init() loaded before it opens its own.

Like zdb, the scan caps the ARC at 256 MB, because it reads each
block once. It also sets zfs_arc_min to 32 MB: in libzpool the
minimum starts at half the maximum, and a cap below the minimum is
ignored. On an MDT with 1.2 million objects this lowered peak memory
from about 450 MB to about 345 MB, with no measurable change in scan
time. There is no spa_export() call: under SPA_MODE_READ it returns
EROFS, and the import ends at kernel_fini() when the last scan closes.

A directory's size is the length of its ZAP, as osd_attr_get()
reports it to a client. The SA size of a directory is not kept up to
date on osd-zfs.

osd-zfs keeps an xattr that does not fit in the SA in a directory of
its own, one object for each value. These objects hold the xattrs of
another object, like an ldiskfs ea_inode, so they are neither reported
nor counted. They have no ZPL_MODE, so otherwise they would be counted
in ss_skipped, and lfs find --device would report damage that is not
there.

A dataset that holds no ZPL objects -- a zvol, or a snapshot of one --
answers EMEDIUMTYPE, which is this backend refusing this dataset and
not the ENOTSUP the library returns when it has no backend to ask at
all.  The ldiskfs backend separates the same two with ENOPKG; a caller
that skips its work where a build cannot scan must not also skip it
where the build can and the target was misnamed.

conf-sanity 300 is extended to cover it rather than left
ldiskfs-only: its gate becomes ldiskfs-or-zfs, and so does the OST
half's, which asks about ost1_FSTYPE for itself rather than about
whether it matches the MDT's.  MDSFSTYPE and OSTFSTYPE are set
separately -- facet_fstype() reads the facet's own first -- so an
ldiskfs OST under a ZFS MDT is a real combination, and keying off
the match would leave it unscanned by a backend that can read it.
Both facets grow an export_zpool and import_zpool pair around the
scan, because a pool still imported by its server answers EBUSY.
-p and --search are passed so a pool on file vdevs is found.

lfs find gains --search DIRS, which sets lfsp_search, and --device
takes a pool/dataset name for a ZFS target; lfs-find.1 says when such
a pool answers EBUSY.  scan_device_target(), which llapi_find_device()
reads a target's label with, takes the search path too and selects its
backend the way llapi_scan_device() does.  The ldiskfs half of
conf-sanity 300 still errors where the backend will not load, an
ldiskfs build being unable to configure without libext2fs; only a ZFS
target skips on ENOTSUP, and only when the build has no ZFS backend:
every dlopen() tried found no scan_osd_zfs.so. The loader now names
each attempt's error, so a plugin that is there but does not load
fails the test instead. While mds1 is still up, the test also checks
that --target on a ZFS MDT is refused as in use.

The backend goes into the programs that scan, not into liblustreapi,
which is what mkfs.lustre already does with -lzfs -lnvpair -lzpool.
libzpool is the DMU built for userspace and it arrives with libspl and
libnvpair behind it.  In the no-plugins build those are linked into
the library, so they reach every program that links it -- lfs, lctl,
and every helper under lustre/tests -- and not only the ones that
scan.  sanity 131d shows this: it reads errno through rwv, which
links liblustreapi and never scans anything.  libext2fs is one
ordinary library and does not carry that, so the ldiskfs backend stays
where it is.

So liblustreapi keeps -DHAVE_ZFS_SCAN and declares the five entry
points weak, and libscan_zfs_in.la is linked into
llapi_scan_device_test, the scanner conf-sanity 300 drives, and not
into lfs, which clients install.  A program without it links and
leaves the slot NULL, which is the -ENOTSUP llapi_scan_device.3
already describes -- the same answer as a build whose configure found
no libzpool headers at all, so no caller and no test learns a new
outcome.  lfs find --device therefore reads a ZFS target in a packaged
build, which dlopens scan_osd_zfs.so, and answers ENOTSUP for one in a
build without plugins; conf-sanity 300 skips its lfs find half on
exactly that, for a ZFS target only.

The weak reference is not on its own enough to link the backend in,
and the failure is silent.  libtool hands a convenience library to the
link as a plain .a, and an undefined *weak* symbol is not a reason for
the linker to extract an archive member -- so the five stay NULL, the
scanner answers -ENOTSUP on a build that has the backend, and nothing
says why: nm reads "w scan_zfs_open" and the binary holds no
libzpool symbol at all.  So the program names one symbol undefined
up front, -Wl,-u,scan_zfs_open,
which extracts the member that defines it and brings the other four
with it.

Its own autotest reaches the ZFS half only where configure finds the
headers; the Test-Parameters line below asks for the ZFS session that
can say something, and the default testing already runs sanity 157c.

Neither exercises the weak slot, and that is not an omission.
PLUGINS is enable_shared, so the weak references, libscan_zfs_in.la
and the -u exist only in a --disable-shared build; the autotest
sessions are built from the spec, which is %bcond_without shared, and
take the dlopen() path.  The build that does carry them is the
janitor's, which configures --disable-shared and runs the whole of
sanity on every change.
Asking for ONLY=131d here would run it against the shared build,
where the condition cannot arise.

lustre.spec.in changes with it: %files osd-zfs-mount becomes a
generated lustre-osd-zfs-mount.files, carrying its %dir and zed.d
entries over, because the plugin is built only when configure found
libzpool and a static file list cannot say that.

A name that begins with '/' is a device path. scan_device_exists()
stats it and returns -ENOENT, -ENOTDIR, -ELOOP or -EACCES before a
backend is chosen, so a mistyped path gets the real error even on a
build without ZFS. scan_backend_kind() also takes such a name as
ldiskfs before its own stat(), so a mount point or another directory
is never sent to the ZFS backend. A relative name is ldiskfs only if
it is a block device or a regular file; any other relative name,
including one that does not exist, is taken as a dataset. -ENOTSUP
keeps the meaning that llapi_scan_device.3 gives it, and that
conf-sanity 300 uses for its skip: this build has no backend for the
target.

SCAN_CHUNKS_MAX is derived from DN_MAX_OBJECT in <sys/dnode.h>, the
bound the walk needs, so a ZFS that widens the object id carries
this along with it.

A pool this kernel holds is told from one that is merely named like
a kstat by asking for a directory.  /proc/spl/kstat/zfs holds about
twenty global kstats -- zil, fm, dbufs, arcstats and the rest -- as
regular files in the same directory pools appear in, so a stat() that
only asks "does the name exist" would answer -EBUSY for an exported
pool called fm.  Only a directory there is a pool.

-EBUSY names both of the things that raise it: a pool another mount
holds, and a dataset already owned within this process, which is a
second scan of the same target.  dmu_objset_own() answers the same
errno through dsl_dataset_tryown() for the second, where the pool is
exported and there is nothing to export.  llapi_scan_device.3 says
the same.
