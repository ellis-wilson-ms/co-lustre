LU-17364 osc: discard un-flushable pages when cancelling a lock

When a lock is cancelled -- a blocking AST, or the local cancel done while
invalidating the import (client eviction, force umount) -- its dirty pages
must go, since nothing covers them once the lock is gone. osc_lock_flush()
writes them back first (osc_cache_writeback_range() with discard=0 when the
lock does not carry LDLM_FL_DISCARD_DATA) and then discards whatever is left
via osc_lock_discard_pages().

If that write-back fails -- the client was evicted, or an OST returned an
I/O error -- the pages can never be written now and are left in a cached
(OES_CACHE) extent. osc_lock_discard_pages() -> cl_page_discard() ->
osc_page_delete() then finds the page still pending in a non-OES_TRUNC
extent, osc_teardown_async_page() returns -EBUSY, and it trips:

  (osc_page.c:182:osc_page_delete()) Trying to teardown failed: -16
  (osc_page.c:183:osc_page_delete()) ASSERTION( 0 ) failed
  (osc_page.c:183:osc_page_delete()) LBUG

This is the lock-cancel sibling of commit f7c84e94af66 ("LU-17364 llite:
discard un-flushable pages on evicted inode teardown"), which covers the
ll_delete_inode() inode-teardown path; this one covers the force-umount /
blocking-AST path (ll_umount_begin -> ldlm_namespace_cleanup ->
osc_ldlm_blocking_ast -> osc_lock_flush), which that patch does not reach.

The lock is being cancelled regardless, so once the write-back fails
discarding the pages locally is the only option. Retry
osc_cache_writeback_range() with discard=1 -- which completes cached extents
without an RPC -- so osc_lock_discard_pages() finds nothing to LBUG on.

sanity test_913 exercises this via a force umount, reusing
OBD_FAIL_OSC_NO_FLUSH. Without this fix it LBUGs in osc_page_delete() even
with the llite sibling applied; with it the force umount completes cleanly.
