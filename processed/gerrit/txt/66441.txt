LU-20099 nrs: add zero reserved and unlimited rates for mClock

A reserved rate of 0 reserves nothing. A limit rate of "unlimit" or
"max" sets no ceiling. An mClock rule that names no rate key now gets
no reservation and no ceiling, not the default rate. The default rule
keeps nrs_class_def_rate. Thus traffic that matches no rule keeps a
ceiling, or a reservation on a reserve-only policy.

A TBF rule with no ceiling returns -EINVAL. An mClock rule that uses
no dimension of its policy also returns -EINVAL. The service logs an
error line for that rule. On a policy with no weight dimension, a
rule that names no rate key is such a rule. A change command with two
rate keys returns -EINVAL. A change of the reserved rate to 0 returns
-EOPNOTSUPP. A limit rate of 0 now returns -EINVAL, not -ERANGE, for
a TBF rule and for an mClock rule.

Add the short rule keys R=, L= and W= for resvd_rate=, limit_rate=
and weight=. The new nrs_rule_dims_report() logs each rule key that
names a dimension the policy does not have. The log line also names
the start key that turns the dimension on.

nrs_mclock_class_deadline_min() takes the current time. A bucket in
the weight tree is ready now, so the arrival path arms the throttle
timer for it.

One command starts a rule on the two heads of a service. The function
nrs_rule_command() saves and restores rs_rcfg, rs_lcfg and rs_weight.
Thus the second head does not read the writes of the first head.

The rule dump prints the rate as a range: "R-max", "0-L" or "rate
0-max". Add the man page nrs_policies.4.

Extend sanityn/test_77ve with a rate change of a running rule. Add
sanityn/test_77v{k,l,o,p,q,s}.

Some concerns, see inline comments. The new "unlimit"/"max" and zero-rate values are accepted by the generic rule parser, but only the mClock scheduler was taught to handle them; a TBF rule with rate=max ends up with rcfg_nsecs_per_rpc == 0 and trips an assertion, and an mClock head started with only the reserve dimension can accept R=0 and then never dequeue that class. Both look worth gating in nrs_cmd_rule_check() so the invalid combinations are rejected at configuration time rather than at RPC time. It would also help to extend 77vk to cover the reserve-only head and a TBF rule, since the current cases all use "reserve=1 limit=1" under mclock.
