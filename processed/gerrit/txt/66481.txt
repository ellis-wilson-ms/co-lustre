LU-12669 ec: fix EC recovery read for encrypted files

The parity of an encrypted file is computed from its data as stored
on the OSTs, but an EC recovery read rebuilds a stripe from data
pages that OSC has already decrypted, together with the parity as
stored, and returns garbage.

Rebuild the stripe from the data as stored instead: have OSC leave
the data pages read for the recovery encrypted, rebuild the missing
pages from them and the parity, then decrypt the pages read and
rebuilt, leaving an all-zero block (a hole) as OSC does.  A data
page already in the page cache holds the plaintext, so read the
stripe again from the OST for the positions being rebuilt, rather
than encrypting the plaintext, which cannot recreate the stored
data of a hole.  Without the key, leave the pages encrypted, as a
normal read does.

Add sanity-ec test_56a to recover an encrypted file with a hole in
a surviving stripe, both from the OSTs and with that stripe cached.

Experimental feature testing in progress, please pay attention to the comments

Problematic, see inline comments. Dropping the all_vmpages[] array looks like it breaks EC reconstruction itself, not just the encrypted case: lov_ec_read_stripe_pages() NULLs out_pages[j] for every successfully read page, so all_pages[idx]->cp_vmpage is no longer reachable for EC_DPG_READ (and for EC_DPG_ERROR pages coming from the submit-failure path), and lov_ec_decrypt_recovered_pages() ends up a no-op for the same reason. That array removal and the rewritten page-release logic in out_err/rg_cleanup/out are a sizeable refactor of the parent patch that is independent of the encryption fix; splitting it out (or folding it back into the parent) would make both halves reviewable. sanity-ec.sh currently has no encryption coverage at all, so this fix looks untested - consider adding a sanity-ec case that writes an encrypted EC file, resyncs the parity with O_CIPHERTEXT, takes an OST down and verifies the recovered read matches the plaintext.

(4 comments)

Beyond the inline comments, there is no test for any of this, so there is no way to know how much of this code works. It needs a sanity-ec test that creates an EC file in an encrypted directory (test_dummy_encryption is enough), resyncs it, stops a data OST and compares checksums: a cold read, a read with surviving stripe pages already cached, and a sparse file with a hole in a surviving stripe.

A simpler and more robust design: do the reconstruction entirely in ciphertext, as the parity was computed. Set cp_skip_decrypt on every data page the EC read submits (as this patch already does for parity), so the OSC leaves the OST's ciphertext in those pages; they are owned, locked and not yet uptodate, so no reader can see them. Rebuild the missing stripes from that data and the parity, then decrypt every page the EC read filled or rebuilt in place (leaving all-zero blocks alone, as osc_brw_fini_request() does) before marking it uptodate. A surviving page already in cache is read again from the OST into a transient page, like the parity pages, rather than re-encrypted. That removes cp_bounce_page, cp_bounce_filled, the OSC copy, the in-place encryption and its rollback, and the encrypt/replace helpers.
