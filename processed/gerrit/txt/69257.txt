LU-20808 osp: seed the object cache from a lock intent reply

The state an IT_MDT_TO_MDT_READ brings back - attributes and xattrs,
read by the owning MDT under the lock it grants with the reply - is
exactly what the layers above read next. Rather than handing it to
each consumer, put it in the OSP object cache that osp_attr_get() and
osp_xattr_get() already keep. That places the same bytes where a read
would have placed them, with no new window in which they can go stale:
like a read made under the lock, it is dropped when the lock is
released. And it serves MDD and LOD alike, without either knowing that
the intent exists.

An xattr the owning MDT looked for and did not find, or found
unsupported, is cached as absent, which spares the next reader a round
trip to learn the same thing. One that came back is cached with its
value. One too large for the room left comes back as its size alone,
and is cached by its size: that answers the size query a reader such
as LOD makes before it reads a value, so that reading a large default
layout takes one read instead of three (-ERANGE, size, read).
osp_xattr_get() fetches such a value itself. An xattr whose read
failed is not cached at all.

osp_intent_fill_cache() stands in for the invalidation that follows a
remote lock grant, so it is as strong: it takes opo_invalidate_sem and
bumps opo_invalidate_seq, or a read issued before the lock was granted
could complete afterwards and put back what it saw beforehand. When it
installs attributes it clears opo_stale and marks the object as
existing, with its type, as a successful read of them would; when it
has none to install, it leaves the object stale, as osp_invalidate()
does.
