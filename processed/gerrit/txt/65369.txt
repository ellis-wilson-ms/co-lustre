(8 comments)

Patch 1/5 of LU-20090. Clean refactor that swaps the variable-length tc_key[] flex array for a fixed struct nrs_tbf_key, in preparation for later patches that compose bucket keys from heterogeneous fields. Looks good overall: the new struct is 72 bytes with no internal padding (verified: flags@0, nid@4 packed-lnet_nid, opcode@24, id@28, jobid@40), so the rhashtable's default jhash over (key_offset, key_len=sizeof(struct nrs_tbf_key)) is well-defined; both producers of a lookup key zero the buffer first (__GFP_ZERO in OBD_CPT_ALLOC_GFP, explicit memset in nrs_tbf_cli_find) so there are no uninitialized-padding hash-input bugs. Removal of tbf_id::ti_type and the corresponding idtype-mask filter in nrs_tbf_id_list_match is safe because each expression's id_list is homogeneous by construction (nrs_tbf_id_list_parse only ever populates ti_uid OR ti_gid OR ti_projid). Backwards compatibility for existing nid/jobid/uid/gid/projid/opcode rules is preserved because tk_flags is constant within a scheduler instance (always head->th_type_flag) and unused fields stay zero on both insert and lookup sides.

A few things worth tightening before landing:

1. Commit message is too terse for a foundation patch in a 5-part series. Please explain *why* a fixed-size key is needed (so later patches can compose heterogeneous per-rule keys without per-type-key plumbing) and call out the unrelated cleanups bundled in (__NRS_TBF_FIELD_MAX -> NRS_TBF_FIELD_MAX, __NRS_TBF_FLAG_END -> NRS_TBF_FLAG_END, dropping tbf_id::ti_type, slight memory-footprint increase for narrow keys). Per https://wiki.lustre.org/Commit_Comments the body should answer 'why', not just restate the subject.

2. Memory footprint regression worth mentioning: a nid-only TBF scheduler previously allocated ~20 bytes of key per client; it now always allocates 72. Combined with the rhashtable min_size of 256 and the LRU of cached clients this can be material on busy servers. Not a blocker, but please acknowledge in the commit message and confirm it's an accepted tradeoff for the upcoming composition work.

3. Minor stylistic nits inline.

With the commit message expanded and the small inline items addressed I'd be happy to +1 this. Marking Code-Review +1 because the change itself is correct and the issues are documentation/polish.
