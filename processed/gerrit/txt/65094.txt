LU-19895 clio: enable multi-order folios for BIO writes

Handle multi-order folios from user pages (DIO) tracking one
PAGE_SIZE chunk per cl_page.

Prepare for multi-order folios allocation tracking each folio
and number of pages though osc_extent to brw_ext.

This enables allocation of large folios on buffered write path

Large folio supported is available with Linux kernels 6.12 and later

Enable large folio support via mount and get/set param:
   lctl get_param llite.*.large_folios
   lctl set_param llite.*.large_folios=[0|1]

Default is enabled.

Adjust folio order max:
   lctl get_param llite.*.folio_order_max
   lctl set_param llite.*.folio_order_max=[0-MAX], default is MAX

View folio order min:
   lctl get_param llite.*.folio_order_min

Maximum order equates to a 1M folio, explicitly (20 - PAGE_SHIFT)
which is 8 on 4k page platforms and 4 on 64k page platforms.

Adjusted sanity/277 to write in 4k chunks and added a delay
so max_cached_mb has time to see the used_mb.

Exposed current client dirty_pages:
   lctl get_param dirty_pages
which allows more insight into the lustre cache and grants
in use by a client.

PCC now limits the folio order maximum on the Lustre inode to
not exceed the PCC backing inode folio order maximum.

Linux commit v5.15-rc3-86-g9dd3d069406ce
  mm/filemap: Add filemap_add_folio()
Linux commit v5.19-rc3-341-g2bb876b58d593 followed by
  filemap: Remove add_to_page_cache() and add_to_page_cache_locked()

Switch to require using the folio API to migrate folios between
Lustre and PCC.

Fix queued value osc_dio_submit() where osc_queue_dio_pages() could
fail with -ENOMEM.

Patch Set 30:

AI review of PS30 (Claude). Two issues found while reviewing a DIO change built on top of this patchset. Both look pre-existing rather than introduced here, so reporting rather than fixing.

1. lov_page_init_empty() (lustre/lov/lov_page.c:191) zeroes only PAGE_SIZE of what may now be a multi-page folio, then marks it uptodate:

        addr = cl_kmap_local(cl_page);
        memset(addr, 0, PAGE_SIZE);
        kunmap_local(addr);
        folio_mark_uptodate(cl_page->cp_folio);

cl_kmap_local() is kmap_local_folio(cp_folio, cl_page_pgno << PAGE_SHIFT), which maps the single page at that offset, so for a CPT_CACHEABLE cl_page spanning a large folio (cp_len == folio_size) only the first 4KiB is cleared. The remaining pages keep whatever they held and the folio is then marked uptodate, so a buffered read of a hole or of an uninstantiated PFL component on a large folio would return stale kernel memory to userspace. The line itself is unchanged, but this patchset is what makes cached cl_pages span whole folios, so the reachability is new. A per-page loop over cp_npgs would fix it; a wider memset would not, since kmap_local_folio only guarantees the one page.

2. osc_dio_submit() (lustre/osc/osc_io.c:340): if osc_queue_dio_pages() fails mid-loop, the code breaks with queued > 0 and a list that the failed call has already emptied. The trailing 'if (queued > 0)' then calls osc_queue_dio_pages() again on that empty list, where the oe_dio branch does list_first_entry() and dereferences the list head as an osc_async_page. Entries after the failure point are also never completed while the function returns 0, which would leave the sync anchor waiting.

Neither has been reproduced at runtime -- item 1 in particular is a code-reading result and worth confirming before acting on it.

Shaun, a heads-up on code overlap with 69505 (LU-20896 osc: encrypt direct IO pages at their own file index), which fixes corruption of encrypted direct IO from THP-backed user buffers.  69505 passes the inode and file index to osc_encrypt_pagecache_blocks() and no longer sets ->mapping/->index on the user folio, since the pages of one large folio are in RPCs that are prepared concurrently.  This patch rewrites the same loop in osc_brw_prep_request() and keeps the map_orig/index_orig swap on origin_folio, so it will need to be rebased onto 69505.

With multi-order page-cache folios, the folio_trylock() in that loop also races for buffered writes: another RPC with pages of the same folio can unlock it before the folio_test_locked() check in osc_encrypt_pagecache_blocks(), which then returns -EINVAL (WARN at osc_request.c:1428, "prep_req failed: rc = -22").  The direct IO side of that fix is planned for 69505, and Sebastien is working on the page-cache side so that it also works with in-kernel fscrypt.
