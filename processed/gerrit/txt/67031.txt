LU-20435 build: fix dmu_offset_next detection

This is a duplicate of https://review.whamcloud.com/48056 and is not
supposed to be landed. It is used so the following patches can
progress as 48056 is based on master.

lustre-build-zfs.m4 checks that the line "EXPORT(dmu_offset_next)"
exists in "$zfssrc/module/zfs/dmu.c". However, dmu.c is not available
because the build points to "kmod-zfs-devel", and so "dmu_offset_next"
was never detected and available.

Use LB_CHECK_COMPILE() to detect if the dmu_offset_next() function
has been exported by ZFS. This is consistent with the rest of the
checks and more reliable than checking the source which is normally
unavailable at build time.

Additionally, skip sanity/430a for ZFS. ZFS reports SEEK_HOLE/DATA at
whole-block granularity, so byte-precise offsets used in 430a only
work for ldiskfs. Instead of modifying 430a accordingly but break
history, add test sanity/430aa which is similar to 430a but keeps data
and hole boundary block aligned. It is therefore compatible with both
ZFS and ldiskfs.

Test-Parameters: fortestonly
Test-Parameters: testlist=sanity env=ONLY=430 fstype=zfs
Test-Parameters: testlist=sanity-ec fstype=zfs
