LU-19895 clio: cap DIO folio extents at pages-per-RPC

A DIO folio extent cannot be split across RPCs, so when an
extent is larger than a target's max_pages_per_rpc the client
silently sends larger RPCs than configured.  Extents reach
1MiB, so any target tuned below that is affected.

Cap the extent at the smallest max_pages_per_rpc among the
targets an io spans, DoM included: osc_io_publish_dio_maxes()
keeps that minimum in new ci_dio_rd_max/ci_dio_wr_max fields,
and cdp_max_ext_pgs carries it into the extent build.

sanity 119w covers it: with max_pages_per_rpc tuned to half of
CDP_EXT_MAX_PAGES, an unaligned DIO write sends 256-page RPCs
without this patch and none above the tunable with it.  It also
checks the pool for that extent size was used, so it cannot
pass by coalescing not having happened at all, and reads the
file back so the read arm is covered too.

cl_object.h:2092 (reuse ci_rd_max): they are not interchangeable.
ci_rd_max and ci_wr_max are last-writer-wins -- osc_io_init() assigns

over every target the io touches, which is what an extent that cannot
be split across RPCs needs.  Switching ci_rd_max to min semantics
would change a field the buffered path also sets, to remove one dead
field; the dead field is worth its own cleanup rather than a semantic
change smuggled into this one.

ll_write_begin() can size a folio against another stripe's target.  As
noted it is pre-existing and comes in with the parent change, so it is

Folded into the patches it was fixing, so it no longer stands alone.

This capped a DIO folio extent at the target's max_pages_per_rpc.
The problem is that 68541 is what makes extents wider than a page,
so between 68541 and this change the client silently sent RPCs
larger than the tunable allows.  Measured on an 8 OST VM with
max_pages_per_rpc=16 and a THP backed DIO write:

  65094 (parent)        16 page RPCs, tunable honoured
  68541 alone          256 page RPCs, 16x over
  68541 + this cap      16 page RPCs

That is a three commit bisect window where a tuned down
max_pages_per_rpc is ignored, so the cap belongs with the change
that needs it rather than on top of it.

Split by which path it covers:

  68541  the cdp_max_ext_pgs plumbing, osc_io_publish_dio_maxes()
         and the ll_get_iov_memory() clamp -- the aligned path,
         where the regression was
  68620  the ll_allocate_dio_buffer() entry order clamp and
         sanity 119w -- the unaligned buffer only exists there

The tip of the series is byte for byte what it was with this
change on top; all that moved is which commit each hunk lands in.
Both patches will carry it on their next push.
