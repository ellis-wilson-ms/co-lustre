LU-20508 llite: avoid blocking thread deadlock during cross-MDT recovery

When an MDT reboots in a DNE configuration, blocking ASTs are sent to
other MDTs internal clients asking them to release cross-MDT locks.
The blocking thread calls ll_lock_cancel_bits() which invokes
truncate_inode_pages() for directory inodes. This function waits on
pages locked by in-flight RPCs to the recovering MDT, creating a
circular dependency that exhausts the entire LDLM blocking thread pool.

The deadlock occurs because:
1. readdir RPCs holding PG_locked pages are on imp_delayed_list
   (import not in FULL state during recovery)
2. Delayed RPCs have no timeout (rq_waiting=1 skips expiry checks)
3. The import cannot reach FULL because recovery needs blocking
   threads for lock replay/cancel operations
4. All blocking threads are stuck in truncate_inode_pages()

Replace truncate_inode_pages() with invalidate_mapping_pages() when
called from a blocking AST context (ldlm_is_bl_ast). This is safe
because directory pages are read-only cache of readdir results and
the lock being canceled guarantees future access will re-fetch.
invalidate_mapping_pages() skips locked pages without blocking, and
skipped pages self-heal when their RPCs eventually time out.

Experimental feature testing in progress, please pay attention to the comments

Some concerns, see inline comments. The main one is that invalidate_mapping_pages() is best-effort, so this drops the invariant that a directory's page cache is empty once its UPDATE lock is gone, and nothing on the readdir cache-hit path re-validates. It would also help to have a regression/coverage case for the deadlock itself (a recovery-small or replay-* subtest with a delayed MDS_READPAGE during MDT recovery), so the fix does not have to be justified only by a field stack trace.
