LU-18456 tcu: move regular files into trash upon last unlink

"last unlink" moving into trash can will create a directory named
after the parent FID in the trash dir for the corresponding MDT.
Then, if/when the parent directory is also removed, the FID-named
directory in trash will rename to use its original file name (and
also inherit the actual FID or other xattrs like crypt, selinux,
etc) from the now-deleted parent.

This can avoid having to move all of the deleted files over to the
"real" deleted parent.

This patch implements the part of moving regular files into trash
upon last unlink.

Add sanityn/test_117b to verfiy it works as expected.

Patch Set 4:

This should create and use a per-UID directory in the Trash directory to isolate user files.  The UID should be the UID of the file/directory being deleted, not the euid of the process deleting the file. This functionality should always be enabled, since it is a security feature, since some files/dirs in a user's subdirectories may not have proper permissions to restrict access. 

For clients in a nodemap, there should be a top-level directory with the nodemap name above the UID directory, with UID=mapped root UID, but 1777 permission (sticky directory, like /tmp, so that only users can delete their own files). The UID directory *name* should be the unmapped tenant UID (since this is what clients will see), and the *owner* should be the mapped UID from the nodemap (which is what will control file access). 

The nodemap handling could be in a separate patch, but I think the UID handling needs to be in this patch, since it will affect the on-disk location of all deleted files.

I am afraid this may downgrade the performance of unlink operations.
It needs two extra lookup or creation in the unlink transactions. (one for "UID", another for "pFID", or even the already existed "pFID" for the deleting directory).

We would better to have a better mechanism to accelerate these extra lookup, I think.
