LU-20730 llapi: llapi_scan_mount(), a scan from a client

The transport landed with no way to reach it but an ioctl, so the 30x
was real and unavailable.  This is the entry point: every MDT of a
mounted filesystem scanned by the server that holds it, records
streamed back, one callback per object.

It is a fourth scan backend rather than a fourth thing that looks like
one.  The unit of work is an MDT instead of a slice of a target, so
tt_chunks is the MDT count and a chunk index selects one; the scan
core already shards chunks across workers, so N MDTs are scanned in
parallel with nothing added for it.  Only the record knows which MDT
answered -- one llapi_scan_tgt covers many -- so llapi_scan_obj gains
so_mdt_index and the core prefers it to the target's when set.

The record becomes an object in one place now.  libscan_kernel.c had
that translation and libscan_client.c needs the same one; with plugins
the kernel backend is dlopen'ed and cannot call back into
liblustreapi, so the choice was one inline in a header or two copies
that drift.  lustreapi_lfu_rec.h holds it, and the kernel backend was
moved onto it.

Enumerating the MDTs is not llapi_get_obd_count().  That answers the
size of the descriptor array -- 64 on a filesystem with one MDT -- so
chunks 1 through 63 asked for targets that do not exist and the scan
delivered every record and then returned -ENODEV.  lmv.*.target_obd
lists the indices themselves, which is also what makes a sparse
filesystem work: MDT0000 and MDT0003 with nothing between is a real
configuration, and a count cannot express it.  A target that is not
ACTIVE is refused at open rather than scanned around, because a scan
that skipped one would return a short answer that reads exactly like a
complete one.

Measured against a scan of the target itself, on the 88k filesystem:

                    llapi_scan_mount   the ring   diff
  visible                     87961      87961      0
  --internal                  88051      88051      0

and from a client that is not the server, 87961 = 87961, diff 0, with
87957 of those records carrying a name and parent FID rebuilt from the
linkea that crossed the ring and then the wire.

What this is not: it scans the whole filesystem whatever directory
names it, since a target has no subtree, so it is for a filesystem
sweep and not for looking through one directory.  The manual page says
so, and choosing between this and llapi_scan_namespace() by that rule
is design-llapi-scan.md's business, not this change's.
