LU-20542 gss: retry callback RPC when reverse ctx is stale

A server cannot renegotiate a reverse GSS context; one is only
installed when the peer negotiates a new context. So when the peer
drops its contexts, the next callback is answered with
GSS_S_NO_CONTEXT, sptlrpc_req_replace_dead_ctx() returns
-ECONNREFUSED, and ldlm_handle_ast_error() evicts a client that was
only mid-refresh.
This is the sanity-sec test_27d/27e failure.

Resend the callback instead, marked with rq_gss_rvs_resend so it skips
the context refresh in ptlrpc_check_set() and reaches the peer over
the same dead context. Every other resend still refreshes, so a
reverse context that goes stale on its own is still detected and
replaced. The resend also keeps its reply match bits: the peer sends
its GSS error reply before it unpacks the request, so that reply uses
the request XID and would be dropped otherwise. Retry for about one
ping interval, which is how long an otherwise idle peer can take to
send a forward RPC and so negotiate a new context. Blocking ASTs, and
completion ASTs sent with LDLM_FL_AST_SENT, stay bounded by
rq_no_resend or the lock callback timeout. Other completion ASTs and
glimpse ASTs set neither, so the retry window is their bound.

After a renegotiation the old reverse context stays listed with a
short expiry, and the replacement can pick it. It dies on the next
refresh, so the retry never ran. Treat an expired replacement as a
failed one.

While a callback waits to retry, the client may have no reverse
context listed. A new BL or CP AST then fails to pack with
-ECONNREFUSED and is dropped. Nothing resends it: a BL AST for an
AST_SENT lock has no timer, and a lost CP AST leaves the client
waiting for the grant (forever for flock). Evict the client in that
case, as a failed callback does.

--- Message (Patrick Farrell, 2026-10-11 16:06:05.000000000) ---
Patch Set 7: Code-Review-1

This doesn't fix the test_27d failure.

In that failure the client has already renegotiated and holds a valid new context. The problem is on the server: the client's idle DISCONNECT failed during the nodemap key switch, so the OSS kept the export, and when the client reconnected from IDLE the OSS never installed the new reverse context. Resending the callback over the stale reverse context can't succeed, and the client has no reason to negotiate again.

A reproducer that forces that sequence fails with PS7 on the first iteration: the OSS resent the BL AST 4 times over 6 s on the stale handle and then evicted the client. test_27d also failed on PS5 and PS6 in review-dne-selinux-ssk-part-2.

https://review.whamcloud.com/c/69581 installs the reverse context from the connect request when an existing export reconnects. It passes that reproducer 10/10, where master and this patch fail.

This patch also makes changes beyond the retry: it treats an expired replacement context as failed, and evicts the client when a new BL/CP AST fails to pack. Those change behaviour on their own and would need a separate change and justification if they are wanted.
