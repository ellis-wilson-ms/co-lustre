LU-20698 osd: lock the os_has_ml_file scrub bit

osd_iit_iget() sets os_has_ml_file without ->os_lock, and it runs on
the otable iterator thread as well as the OI scrub thread.  That bit
shares a byte with os_full_scrub, which osd_scrub_oi_insert() sets
from another thread under ->os_lock; both compile to a plain byte
read-modify-write (orb $0x2 / orb $0x1 on the same address), so
either update can be lost.  A dropped os_has_ml_file skips
osd_scan_ml_file_main(), leaving multiply-linked OST objects
unhandled for that pass; a dropped os_full_scrub skips the escalation
to a full scrub.

Take ->os_lock, as lustre_scrub.h already requires for every bit in
that word.  The osd-zfs store cannot lose an update today, because it
and the only other write to its byte -- scrub_thread_prep() clearing
os_full_scrub -- both run on the scrub thread.  That is a property of
the current bit layout rather than of the threading: osd-zfs does have
cross-thread writers to this word, os_paused and os_waiting, which
merely land in the other byte.  Lock it too so the rule holds by
construction.
