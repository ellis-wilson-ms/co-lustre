LU-20493 ptlrpc: wait for PM-QoS work at connection fini

ptlrpc_latency_req_fini() used cancel_delayed_work() to stop the
per-CPU cpu_latency_work() before freeing the cpu_latency_qos array
and the dev_pm_qos_request it references.  cancel_delayed_work() only
removes a not-yet-started work item; it does not wait for one that has
already been dispatched to a worker.  If a cpu_latency_work() instance
is running (or queued for execution) when the connection is finalized,
the array and request are freed out from under it and the module is
unloaded, so the work then dereferences freed/poisoned memory:

  general protection fault, probably for non-canonical address
  0xdead000000000387
  Workqueue: events cpu_latency_work [ptlrpc]
  RIP: __dev_pm_qos_remove_request+0x16/0x210
  Call Trace:
   dev_pm_qos_remove_request+0x2d/0x50
   process_one_work+0x2c8/0x700
  Modules linked in: ... [last unloaded: ptlrpc]

Commit 80708743dc ("LU-18788 ptlrpc: cancel PM-QoS delayed work")
addressed the same "work runs after the module is unloaded" failure,
but cancel_delayed_work() is insufficient once the work has already
been dispatched.

Use cancel_delayed_work_sync() so finalization waits for any in-flight
(or self-rescheduling) cpu_latency_work() to complete before freeing.
It must be called without holding lq->lock, which cpu_latency_work()
also acquires.
