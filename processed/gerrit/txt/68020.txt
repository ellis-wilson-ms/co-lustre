LU-20591 target: select iterated objects by size and time

A walk of a target reports every object it holds, which is far more
than a caller that is after, say, the large files nobody has touched
for a month has any use for. Reading all of that out and sifting
through it in user space is work both sides can be spared.

Let the walk be restricted to the objects whose size or timestamps
fall within given ranges. The ranges reach the target in a struct
lustre_scrub_iter_filter alongside the request, and the target applies
them where it already reads the attributes to fill in an item, so an
object that does not match is never copied out at all.

Ranges, rather than a value and a comparison, are what the target is
given: the 'newer than', 'older than' and 'exactly N units ago' of
find(1) all turn into one, so the target has a single rule to apply
and user space alone decides what a unit means. A filter field that
the target does not know about is refused with -EOPNOTSUPP rather than
ignored, because ignoring it would quietly widen the result.

The same struct selects on the ownership of an object, which costs
nothing more: it comes out of the read the size and the times already
need. A field the target does not know about is refused rather than
ignored, because ignoring it would quietly widen the result, and the
struct keeps room in reserve so that the next field to select on does
not have to break that rule.

'lctl iterate_objects' grows --size, --atime, --btime, --ctime,
--mtime, --uid, --gid and --projid, which take find(1) arguments and
follow its rules, as 'lfs find' does: a bare number counts 512 byte
blocks or days, '+N' and '-N' are more and less than N, and a value
with no sign has to fall inside the unit it names, so '--size 1M' is
everything above zero up to 1 MiB. The owner takes no sign at all,
just as find(1) takes none for -uid and -gid.

The times are the ones the target holds, which are not always the ones
a client sees: an OST does not maintain the access time of its
objects, and the objects it has precreated but not handed out yet
carry no time at all, so they come out older than anything. Both are
documented rather than papered over.

Add test_31 in sanity-scrub.sh to verify. It checks the size filters
against the sizes the device itself reports, so no expected result is
a hardcoded count, and it moves the timestamps of a file into the past
to check both directions of the comparison.
