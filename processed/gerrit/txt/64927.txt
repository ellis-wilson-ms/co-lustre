LU-20016 utils: add an EC computation benchmark

Note that in the ISA-L library, computing parities and recovering
lost data stripes is the same operation: ec_encode_data().
The difference is not in the computations but rather the content
of the coefficient matrix.

The cost of these operations are primarily bound by the number
of stripes to compute which amusingly means that
recovering a single lost stripe should be FASTER than
generating two parities.

Print CPU details and the EC implementation selected by the
library, accounting for build options and runtime CPU support.
Use k data and m parity stripes consistently. Initialize source
data before a synchronized timed run and report byte rates
using measured elapsed time.

Only build ec_perf_bench on x86_64: the accelerated EC kernels it is
meant to benchmark (GFNI/AVX2/AVX-512) are only built for that
architecture. Build erasurecode before the rest of utils and add an
explicit rule for erasurecode/libec.a, so ec_perf_bench's dependency
on the static library is honored under parallel make.

erasurecode/libec.a was built without -fPIC, so any program linking
it fails under a PIE-enabled toolchain; ec_perf_bench, always built
on x86_64, hits this on every configuration. Build libec.a with
-fPIC.

## Summary of Fixes

I fixed two compile errors introduced by the patch:

### 1. Format Specifier Error (Line 188 in ec_perf_bench.c)

**Problem:** The code used `%u` format specifier for a `size_t` value:
```c
fprintf(stderr, "error: failed to allocate %u bytes thread data\n",
        numthreads * sizeof(struct thread_data));
```

**Fix:** Changed `%u` to `%zu` (the correct format specifier for `size_t`):
```c
fprintf(stderr, "error: failed to allocate %zu bytes thread data\n",
        numthreads * sizeof(struct thread_data));
```

**Rationale:** The expression `numthreads * sizeof(struct thread_data)` evaluates to type `size_t` (which is `unsigned long` on 64-bit systems), not `unsigned int`. Using `%u` causes a type mismatch warning that's treated as an error with `-Werror`. The `%zu` format specifier is the standard way to print `size_t` values in C99 and later.

### 2. Unrecognized Compiler Flag Error (-Wno-gnu)

**Problem:** The build system was adding the `-Wno-gnu` flag via `EXTRA_CFLAGS`, which is a Clang-specific warning flag that GCC doesn't recognize.

**Fix:** Added an explicit `ec_perf_bench_CFLAGS` setting in `Makefile.am`:
```makefile
ec_perf_bench_CFLAGS = $(AM_CFLAGS)
```

**Rationale:** The Lustre build system conditionally adds `-Wno-gnu` to `EXTRA_CFLAGS` if the compiler supports it (see `config/lustre-toolchain.m4`). This flag is Clang-specific and used to suppress warnings about GNU extensions. By explicitly setting `ec_perf_bench_CFLAGS` to `$(AM_CFLAGS)`, we override the default behavior which would include `EXTRA_CFLAGS`. The `AM_CFLAGS` variable contains the standard flags needed for user-space utilities (`-fPIC -D_GNU_SOURCE -D_LARGEFILE64_SOURCE=1 -D_FILE_OFFSET_BITS=64 -DLUSTRE_UTILS=1`) without the problematic `-Wno-gnu` flag that GCC doesn't understand.

Both fixes are minimal, targeted changes that resolve the compilation errors without affecting other parts of the codebase.
