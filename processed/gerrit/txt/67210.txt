LU-20476 o2iblnd: don't destroy a cm_id we still own

The DISCONNECTED handler clears cmid->context but leaves the cm_id
owned by o2iblnd, to be destroyed later by connd in
kiblnd_destroy_conn(). The UNREACHABLE handler reads a NULL context
as "no conn has been created yet" and returns -ENETDOWN.

That reading is wrong. The DISCONNECTED handler is the only place
that ever assigns NULL to a cm_id context. Before a conn exists the
context is the kib_peer_ni passed to rdma_create_id(), so a NULL
context at UNREACHABLE can only mean the conn has already
disconnected and is waiting for connd, which is exactly when the
cm_id is still ours.

A non-zero return from the handler tells the CM to destroy the
cm_id. cma_netevent_work_handler() does so on any non-zero return,
so a RoCE neighbour invalidation against a disconnected conn
destroys a cm_id that connd then destroys a second time:

  general protection fault, probably for non-canonical address
                                            0xdead000000000200
  RIP: 0010:_destroy_id+0x18c/0x300 [rdma_cm]
  Call Trace:
   kiblnd_destroy_conn+0x29f/0x670 [ko2iblnd]
   kiblnd_connd+0xfa/0x980 [ko2iblnd]

Return 0 instead. The conn still holds ibc_cmid and connd destroys
the cm_id before freeing the conn, so nothing is leaked.

Destroy the cm_id before dropping the peer_ni reference in
kiblnd_destroy_conn(). A CM callback may still be running on the
cm_id and may dereference conn->ibc_peer. rdma_destroy_id() waits
for in-flight handlers to complete.
