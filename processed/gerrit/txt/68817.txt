LU-20730 osd-zfs: the LFU record and an index walk

The ldiskfs half of the Object Stream over OBD_IDX_READ landed
without its ZFS counterpart, so an MDT on ZFS answered -EOPNOTSUPP
through it and which backend a user had decided whether the feature
existed at all.

rec_size() and rec(DORA_LFU) are the ldiskfs ones: the record is
built by dt_otable_lfu_rec() from rec(DORA_ATTR) and rec(DORA_XATTR),
both of which this iterator already serves, and it is built once per
object and kept, because the page builder asks the size before it
asks for the bytes.  ZFS keys its xattrs by the full trusted.* name
in the SA nvlist and in the xattr directory, which is the name the
builder passes, so nothing about the record differs between the two
backends.

DOIF_INDEX takes one more step here than it does on ldiskfs.
dmu_object_next() answers strictly after ooi_pos, which is why a
private iterator already starts at the hash rather than after it; an
index walk has to return the record *at* the hash, since that is the
key the page builder handed back for the record it had no room for,
so it starts one further back again.  Object 0 is the DMU meta-dnode
and never a target object, so clamping there loses nothing.

Verified on a ZFS filesystem of 2000 files, and the point of the test
is the resume: the whole stream fits one 1 MiB bulk, so a single call
exercises no boundary at all.  Shrinking the buffer forces them.

  buflen    RPCs   records   vs the ring
  1 MiB        1      2100   diff 0
  64 KiB       8      2100   diff 0
  32 KiB      15      2100   diff 0
  16 KiB      29      2100   diff 0
   8 KiB      58      2100   diff 0

The same buffer sweep on ldiskfs, which had only ever been run at 20
RPCs: 2446 calls over the 88k fixture, 2445 resumes, 88051 = 88051,
diff 0.
