LU-20611 llapi: run find over a device scan

Add llapi_find_device(). It passes the records of llapi_scan_device()
through the same checks that llapi_find() uses for a namespace walk.
The checks are not written again: the record is presented as the
lov_user_mds_data that every find_check_* helper already reads.

A field that the scan could not answer is left out of stx_mask, as
llite does when the MDT's answer is not authoritative. The layout and
directory-stripe buffers live for the whole scan, so an object without
one must say so, and not reuse the previous object's.

Some searches need something that a target scan does not have. They
are refused before the scan starts, because afterwards "no matches"
and "cannot answer" look the same:
- --xattr needs a mounted filesystem
- -printf %p needs a path; the check skips the same flags and width as
  the printer, so "%+5p" and "% 5p" are refused too
- --maxdepth, --mindepth and --threads describe a walk
A field that the inode format has no room for, such as a project id or
a birth time, is counted as undecided and reported at the end. The
negations differ: a walk sees no birth time for such an inode either,
so ! -btime matches it, but a walk is told a project id of 0, so
! --projid N stays undecided.
lfsp_filter is cleared, because the scan carries this function's own
state.

--ost and --mdt are answered from the target itself. Every object in
an MDT scan is on that MDT, and every object in an OST scan is on that
OST. find_tgt_index() matches each name against the label that the
backend read: a numeric index as given, and a UUID through
llapi_uuid_match(). A name of another target never matches, so the
predicate is false for every object, and true for every object under
"!". This is not an error, so one --ost can be used over many devices.
When no object on the target can match, the scan is skipped.

--ost is decided before the scan, removed from the search and put back
afterwards. check_obd_match() reads the layout, and an OST object has
none, so it would reject every object of the requested target. --mdt
uses check_mdt_match(), with fp_file_mdt_index set once from the
target. --mdt over an OST and --ost over an MDT are refused: an OST
object names its MDT only through an FLD lookup, which needs a client,
and --ost over an MDT asks about layouts, not about the target. The
layout options over an OST are refused for the same reason: an OST
object has no layout, so they would compare a default never read.

find_lmm_fits() checks the layout before layout_swab_lov_user_md()
uses it, because lcm_entry_count and lcme_offset come from a target
that may be in the middle of a write. It reads each field in the byte
order it found, as llapi_layout_get_by_xattr() does. An object whose
layout does not fit is undecided for the layout options.

Some layouts are seen only by a target scan, and are accepted:
- A directory default layout has a stripe count but no lmm_objects[]
  ("lfs setstripe -c 4 dir" is 32 bytes). The object array is measured
  by the buffer, as llapi_layout_objects_in_lum() does.
- LOV_MAGIC_SEL is written by lod and shown to a client as COMP_V1,
  and it is converted to that. LOV_USER_MAGIC_SPECIFIC is converted to
  V3; a walk sees it unchanged, so --pool can match such a directory on
  a scan and not on a walk.
Otherwise such objects would take the no-layout path and be compared
against the filesystem default layout.

--name is tested against every name in trusted.link. A walk meets a
hardlinked file once per link, but a scan meets the object once, so it
must test all names. The object is still reported once.
scan_linkea_entry() reads any entry, not only the first. A linkea
whose first entry does not parse no longer sets LLAPI_SCAN_LINKEA. A
linkea that ends before all its names are read makes the object
undecided, not a non-match. Before an object is called undecided,
find_device_prefilter() runs the other predicates, so an OST scan with
"-name X -type d" does not warn about objects that -type rejected.
find_prefilter() skips -name for a record with no name, because
fnmatch() does not accept NULL.

--links on a foreign directory: find_decide() read the lfm_length of a
foreign LMV as a stripe count. It now tests lmv_is_foreign() first,
like the --mdt-count, --hash-type and --hash-flag checks.
find_decide() now makes that check itself, for a walk and a scan
alike. On a walk too, -printf %Lc, %Lh, %Lp and %Lo now print nothing
for a foreign directory. Before, they printed lfm_length as a stripe
count and part of lfm_value as a pool name.

-printf answers from the record. %LF is the record's FID, the layout
directives read trusted.lov through llapi_layout_get_by_xattr(), %i is
the object id on the target, and %LP needs no open.
printf_format_want() decides the %p refusal and what a format needs to
read, so "-printf %i" does not read a layout.

Three -printf answers were wrong in a walk too. For a layout that only
says "the default", the stripe count and size printed
LLAPI_LAYOUT_DEFAULT. They now print nothing, except that a
Data-on-MDT component's count prints 0, as lfs getstripe says.
%Lo skips a component whose stripe count is not a number of objects
(the default, or -1 for all OSTs, on a component with no objects
yet). Before, it filled the buffer with "?," and lost the newline and
the later components.
A device scan has no shard FIDs, so %Lo prints nothing for a striped
directory. %s, %b and %k print nothing for an object the scan has no
size or blocks for, rather than 0.

On a walk, "! --foreign" prints an unstriped directory without
testing the other predicates, to save the getattr. A scan has the
attributes already, so it goes on to the attribute tests there. The
stripe tests (--mdt-count, --mdt-hash) stay skipped, as on a walk.

-btime and -newerbY change in a walk too. An object with no birth
time (off Lustre, or through the V1 ioctl) used to return
-EOPNOTSUPP, which ended the walk of the whole subtree. It is now a
non-match.

When a search only prints, an object without a layout does not get
the filesystem default layout, and the per-object layout messages are
quiet on a scan.

An object the scan delivers with no FID is printed as obj:ID: an OST
object with no LMA (its object id is in the directory entry, not in
the inode, so there is no IDIF to build), or an MDT object with no LMA
outside MDT0000. On MDT0000, llapi_scan_device() already gives such an
object its IGIF. The MDT FID in an OST object's trusted.fid is not
read yet; that is left for a later change. llapi_find_device.3
describes how a target scan answers differently.

A foreign LMV larger than the search's buffer grows the buffer, as a
walk does, so --foreign and the other LMV checks still see it.

A size the scan did not report is undecided for -size and -blocks,
whatever the layout says: a Data-on-MDT file's stripe count is 0, so
it would otherwise be decided on a stx_size the scan never reported.
The fix is Artem Blagodarenko's.
