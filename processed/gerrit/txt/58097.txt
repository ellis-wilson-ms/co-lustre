LU-17916 clio: switch to struct folio

Switch cl_page from struct page and page based API to
struct folio and the folio API.

The default folio order of 0, in the absence of fgf_set_order() and
mapping_set_folio_order_range(), on the buffered I/O path the folio
allocation size remains PAGE_SIZE [order 0]

The DIO bounce buffer now allocates folios of order 0 to align
with the existing logic.

User pages used for DIO can be embedded in large folios so
add support for identifying and tracking the page number inside
a large folio from user pages.

Introduce cl_page_batch* and clarify oti_cl_batch as pending
cl_page objects available for cl_commit_cbt to release additional
grant space in osc_queue_async_io(), other users of oti_fbatch
are moved to their respective local stack.

Fix bug introduced in filemap_get_folios_contig() improper handling
of number of folios returned. Also ensure that ref'd folio is released
upon llite.*.dump_page_cache completion for the case where _start() or
_next() is called without a subsequent _show()

Fix bug introduced in conversion to folio_batch addition of pgno to
vvp_set_batch_dirty() which changed the bit-wise flags from i which
walked every bit to pgno which did not advance properly.

Found a real bug here while tracking down a "sleeping in
atomic" warning the Janitor attributes to patches further up
this relation chain.  Details in the inline comment on
vvp_io.c; summary and evidence below.

vvp_set_batch_dirty() zeroes the saved interrupt flags
immediately before restoring them, so it returns with
interrupts disabled on the CPU.  One line:

    flags = 0;
    xa_unlock_irqrestore(&mapping->i_pages, flags);

Everything after that in the write syscall runs with IRQs off.
The first thing that notices is the mutex in
ll_inode_size_lock(), reached from ll_merge_attr() at the end
of ll_file_io_generic(), which is why the warning points there
rather than here.

How I got to it.  On a rocky8.10 VM with 58097 ps53 and nothing
else, instrumented ll_inode_size_lock() to log irqs_disabled()
and dump_stack():

  BUG-equivalent: irqs_disabled=1 in_atomic=0 preempt_count=0 comm=cp
    ll_inode_size_lock+0xa6/0xe0 [lustre]
    ll_merge_attr+0x15/0x40 [lustre]
    ll_file_io_generic+0xf9c/0x11f0 [lustre]
    do_file_write_iter+0x7c8/0xc70 [lustre]
    new_sync_write / vfs_write / ksys_write

in_atomic()=0 with irqs_disabled()=1 is the giveaway: a
spin_unlock_irqrestore() puts preempt_count back to zero but
restores EFLAGS from the value passed in, and with flags==0 the
interrupt-enable bit is clear.

Bisected it with probes: clean before cl_io_loop(), IRQs off
after; clean after __generic_file_write_iter(), off after
vvp_io_write_commit() -- which reaches vvp_set_batch_dirty()
through write_commit_callback().

A plain "cp /etc/hosts /mnt/lustre/f" reproduces it every time.
Deleting the "flags = 0;" line and changing nothing else:
runtests goes from hitting my 10-warning cap to zero
occurrences, PASS 1 (98s).

Scope: the block is inside #ifdef HAVE_ACCOUNT_PAGE_DIRTIED.
rocky8 defines it; rocky9 does not (it takes the
filemap_dirty_folio() branch instead), and a full runtests on
rocky9 with this patch produced no occurrences.  So this is
el8-and-older only.

Impact is understated by the warning being debug-only.  On a
production kernel there is no message at all -- the task simply
continues with interrupts disabled until something re-enables
them, which for a syscall path is the next context switch.

Evidence for it being from this patch rather than further up:
"flags = 0;" is an added line in this change, and counting the
BUG in runtests client syslogs across the chain gives 58097
ps53 = 119, 67791 ps7 = 115, 65094 ps33 = 121, 68541 ps10 =
112, 68619 ps4 = 111, against 0 for an unrelated change on
master running the same debug kernel.  The Janitor only labels
it a NEW warning on the patches at the top of the chain, which
is misleading.
