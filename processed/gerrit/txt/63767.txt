--- Commit Message ---
LU-20108 sec: support fscrypt natively for Linux 5.15

Currently Lustre only supports up to 5.8 kernels. This work
handles the replacement of fscrypt_inherit_context() with
fscrypt_prepare_new_inode() and fscrypt_set_context(). So the
encrypt context is done in a two step process.

(13 comments)

AI code review results below, please doublecheck

Problematic, see inline comments. The central helper llcrypt_prepare_new_inode() looks like it cannot work as written: unlike fscrypt_prepare_new_inode(), which derives the child key from the parent policy plus a fresh nonce, it reads the child inode's own on-disk context, which does not exist for the freshly allocated fake inodes this patch introduces. Combined with the lost IS_ENCRYPTED() guard in ll_dir_setdirstripe(), the embedded-llcrypt build (the configure default) looks like it would fail every create under an encrypted directory and every lfs setdirstripe anywhere. It would help to get a sanity-sec run with real keys rather than test_dummy_encryption before the next refresh. The new LL_IOC_GET_ENCRYPTION_NONCE ioctl is user-visible and has no test - would it be worth adding a sanity-sec case that compares the nonce of a parent and child?

AI code review results below, please doublecheck

Some concerns, see inline comments. The lookup path change in ll_lookup_it_finish() looks like a show-stopper: an encrypted directory created under an unencrypted parent (the usual `mkdir dir; setpolicy dir` layout) can no longer be looked up at all, so it is worth confirming before the next round. Two build configurations also look broken -- `--enable-crypto=in-kernel` (the one this patch is about) and `--disable-crypto`. Separately, the new LL_IOC_GET_ENCRYPTION_NONCE ioctl arrives without any test; a sanity-sec case that creates two files in the same encrypted directory and checks their nonces differ would cover both the ioctl and the nonce-generation rework.
