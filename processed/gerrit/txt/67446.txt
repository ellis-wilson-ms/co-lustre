LU-20510 osc: wait for OST_SYNC issued on the fsync error path

osc_io_fsync_start() issues asynchronous OST_SYNC RPCs unconditionally
via osc_fsync_ost(), but only records that it is in flight when no
earlier error has been latched:

	rc = osc_fsync_ost(env, osc, fio);
	if (result == 0) {
		cbargs->opc_rpc_sent = 1;
		result = rc;
	}

osc_io_fsync_end() waits only when opc_rpc_sent is set, so once
osc_cache_writeback_range() or osc_cache_wait_range() has failed, the
io is torn down with the RPC still in flight. Its completion then runs
osc_async_upcall() on &oio->oi_cbarg, which is in struct osc_session,
memory already returned to osc_session_kmem. The resulting freelist
corruption surfaces later, at an unrelated allocation, typically as:

  general protection fault: 0000 [#1] SMP DEBUG_PAGEALLOC
  RIP: 0010:memset_erms+0x9/0x10
   kmem_cache_alloc+0x307/0x430
   osc_session_init+0x31/0x150 [osc]
   cl_env_new+0x223/0x2e0 [obdclass]
   cl_env_get+0xe3/0x3a0 [obdclass]

The window is normally unreachable, since nothing fails writeback on a
healthy client, but it opens on OST I/O errors or client eviction, and
CL_FSYNC_RECLAIM makes it reachable from background reclaim writeback.

Record RPC as in flight whenever it was actually sent, regardless of
previously latched error, so osc_io_fsync_end() always waits for it.

Verified on slab-debug kernel with writeback-error injection. Without
this patch 6/13 runs crashed, with crash occurring in runs that
entered the window; with it, 0 of 10 runs crashed while 5 still
entered the same window.

Fix identical issue added in the same patch in mdc_io_fsync_start().
