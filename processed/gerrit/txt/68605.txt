LU-20687 lustre: check NULL and error objects before downcast

smatch reports 439 "dereferencing possible ERR_PTR()" errors plus 39
"passing zero to ERR_CAST" warnings across the tree.  They all come from
the ~46 inline downcast accessors (lu2dt_dev(), lu2cl(), mdt_obj(),
lu2lod_dev(), ...) that are built on container_of_safe(), which returns
its argument unchanged when it is NULL or an ERR_PTR.  A downcast that
can hand back an error pointer makes every caller a potential error
pointer dereference, and the tree is inconsistent about it: lov, lovsub
and lod_obj() use plain container_of() for exactly the same downcast,
and oap2osc()/oap2osc_page() are the same cast written both ways.

Before the accessors can be given the plain container_of() contract, the
places that really do feed them a NULL or an error have to say so.  Add
dt_object_find_slice() next to dt_locate_at(), which already has this
shape, and use it wherever lu_object_find_slice() was fed straight into
lu2dt(): obdclass/scrub.c, both osd scrubs and lfsck_internal.h.  Do the
same by hand in cl_object_find(), lov_sub_find(), cl_type_setup(),
md_object_find_slice() and mdd_object_find().

In the sysfs and debugfs handlers of mdt, ofd, mgs and osp the nullable
value is obd->obd_lu_dev, which is NULL before obd_setup() and after
obd_cleanup(), so test that rather than the downcast result.  Two more
downcasts make an existing NULL return explicit so that it is visible
without having to know what container_of_safe() does: obd2echo_dev(),
whose result echo_client_cleanup() tests, and mdt_obj2dt(), whose
lu_object_locate() can miss and whose result is already tested by
mdt_lib.c:823, mdt_lib.c:2302 and mdt_handler.c:7804.  Neither changes
behaviour, and a smatch run confirms neither moves a warning onto the
call sites that dereference the result without a test.

Two error codes change, both from the -ENODATA that lu2dt_dev() used to
fabricate for a NULL device: llog_test_device_init() and qmt_iocontrol()
now return -ENODEV, which is what the other handlers converted here
already return for the same condition.  Nothing else changes behaviour.

I traced every converted site and the IS_ERR_OR_NULL to IS_ERR conversions are all equivalent: lu_object_find_slice() cannot return NULL (lu_object_find() returns a pointer or ERR_PTR, and a failed lu_object_locate() is turned into ERR_PTR(-ENOENT)), so the fabricated -ENOENT arms that were dropped were dead.
