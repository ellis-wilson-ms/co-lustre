(4 comments)

[Claude] Design comments from the LU-20808 wire-protocol review, which also covered the WBC series (LU-10938, LU-13045). The full analysis is in https://jira.whamcloud.com/browse/LU-20808?focusedCommentId=502948#comment-502948

This patch makes MDS_BATCH (LU-14393) carry modifying operations, so it is the place to settle how it relates to OUT_UPDATE. They are separate protocols today: different opcodes and handlers (mdt_batch() was written from out_handle()), a but_update_header that repeats out_update_header's fields plus a count under its own magic, and different payloads (lustre_msg sub-requests vs object_update records). Both arrive on OUT_PORTAL until https://review.whamcloud.com/69436 ("LU-20879 ptlrpc: send batched RPCs to the MDS request portal") lands.

1. Share the container code (header, inline-or-bulk buffers, reply sizing, the sub-request walk) in target/, so the bounds checks exist once. mdt_batch() on master trusts the client's buh_count, burq_count and sub-request magic.
2. Keep the payloads separate: client sub-requests need the full MDT path (ucred, nodemap, permissions, quota, changelogs), and clients must never send object updates.
3. Define partial execution: the batch stops at the first error, so the client needs to know which sub-requests ran, and resend/reconstruct is still a TODO in mdt_batch(). OUT has the same open problem (LU-7319, LU-15550).
4. Use one verified way to say "acting under a lock I hold". The LOCKLESS opcodes here, LDLM_FL_INTENT_PARENT_LOCKED (36924), MDS_WBC_LOCKLESS (37100) and OBD_FL_LOCKLESS (45640) all skip MDT locks on the client's word. A per-sub-request lock handle that the MDT checks (granted, LCK_EX, this export, the parent or object resource) would cover all of them; LU-20808 proposes reserving the same field for MDT-to-MDT compound requests.
