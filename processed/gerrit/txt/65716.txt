--- Commit Message ---
LU-19906 quota: enforce QUOT consistently across OST

This patch ensures that when global or pool quota is
exhausted, OSTs deny further writes immediately, even if
local grants remain. A per-request flag
(qti_use_global_limit) is set in QMT context on global/pool
EDQUOT and reset on init or release. OST-side
logic in qsd_acquire_local() now denies writes if EDQUOT
is set, regardless of local grant. Debug logging is added to
QMT and QSD paths to trace all key transitions and
enforcement events.This change hardens quota enforcement,
improves traceability, and prevents further writes once
limits are reached.
added test_98 to reproduce the issue and verify the fix

This change is not required quota system is working as designed 
Quota EDQUOT / overshoot analysis
When a client issues a write, the OSC first checks the cl_quota_exceeded_ids map for the file's owner ID (uid/gid/projid):
If the flag is not set: the write proceeds to the OST. If the OST (QSD) has enough already-granted quota space, the write completes locally without contacting the QMT. If the OST is short on grant, the QSD sends a DQACQ request to the QMT. Quota is handed out in units of qunit (for block/data quota the minimum qunit is one max-BRW, ~4 MB, not 1 KB). If the QMT can satisfy at least one qunit, the OST gets the grant and the write succeeds.
If the OST cannot get more grant (user is within less than one qunit of the hard limit), the OST returns a reply that sets OBD_MD_FLUSRQUOTA, which causes the client to set cl_quota_exceeded_ids for that ID.
On the next write, because the flag is now set, the client refuses to buffer the page into async cache and switches that write to sync mode, sending it straight to the server for the final verdict. If no grant is available, the write fails with EDQUOT (surfaced to the app as EDQUOT/ENOSPC).
This is the mechanism that contains over-limit writes: the overshoot is bounded and not unbounded. The amount a user can exceed the hard limit is roughly proportional to the grant the OST(s) were already holding (up to about one qunit per active OST), so a small overshoot beyond the hard limit is expected behavior, not a bug.
On the client system observation: I was only able to overshoot by ~2 MB, which is itself not guaranteed and varies with how much grant each OST held at the time. To characterize this precisely on the customer system, we need to collect grant/qunit state during the run (per-OSC cur_grant_bytes, per-OST quota usage from lfs quota -v, and qunit values) to confirm what grant was outstanding when the writes stopped.
When I was able to write ~2mb OVER THE HARD LIMIT it was due to lowering the the quota limit which left ostensibly with extra grant.
Summary: Quota is working as designed. Writes can overshoot the hard limit by a small amount determined by the grant the OST already held; the overshoot is always bounded and self-correcting.
