LU-19605 lnet: push NI status change to peers

A node's per-NI status lives in its ping buffer, and ni_status points
directly into that buffer. Peers only learn of a new status when we
push to them, and lnet_peer_needs_push() only returns true when the
ping buffer sequence number has moved (or on a forced push). That
sequence number is bumped only when the buffer is rebuilt, which is
also the only caller of lnet_push_update_to_peers() on a non-router.

The health-driven status transitions update *ni_status in place, so
the buffer contents change but its sequence number does not. Nothing
queues a push, and a peer keeps its stale cached lpni_ns_status until
some unrelated event rebuilds our ping buffer or the peer pings us
again. Routers are unaffected: lnet_check_routers() forces the push
itself when lnet_update_ni_status_locked() reports a change.

Mark the ping buffer for update whenever lnet_ni_set_status() actually
changes the status, so that the monitor thread rebuilds it and pushes
the new state. lnet_mark_ping_buffer_for_update() only sets an atomic
and signals the monitor thread, so it is safe to call from the health
paths, which run under lnet_net_lock(). It is a no-op when routing is
enabled, leaving the router path as it was.

This is what sanity-lnet test_236 checks, and why it fails with
"Expect peer NI state down": the router never sees the local NI go
down after its health is set to 0.
