LU-20831 mdt: parallel cross-MDT rename of regular files

A cross-directory rename of a regular file still takes the
filesystem-wide rename lock (BFL) whenever the source parent
or the source object is on another MDT.  The BFL is an
exclusive lock on MDT0000's root held across the whole
distributed transaction, so every such rename in the
filesystem runs one at a time, and throughput is capped at
1 / hold time however many MDTs and clients there are.  With
DNE3 spreading directory trees over the MDTs, most
cross-directory renames are now cross-MDT.

The BFL prevents directory loops, and renaming a
non-directory cannot create one.  It does not order the
other locks either: since LU-17427 a rename takes its parent
and child locks across MDTs before the BFL, in a fixed
order, so dropping the BFL for a file rename adds no new
lock ordering.  Extend the FID-ordered parent locking that
cross-directory file renames already use within one MDT
(LU-17426) to the cross-MDT case, under a new tunable,
mdt.*.enable_parallel_rename_remote, on by default.

The mode the client sends is only a hint, so the decision is
made again once the source object is found, and falls back
to the BFL if it is a directory that needs it.  The old
recheck looked only at whether the source object was remote,
so a cross-directory rename of a directory within one MDT,
sent with a file mode by a client racing with a replacement
of the source name, ran without the BFL.  It now takes it.

A failure to lock the source of a rename or migration was
ignored, and the operation went ahead unlocked; the BFL hid
this for remote sources.  Return the error.

Count renames that skip the BFL with a remote source parent
or source file in md_stats as parallel_rename_remote.

Add man pages for the other parallel rename tunables and
for rename_stats, which this one refers to.

On a four-MDT VM cluster, eight tasks renaming files across
MDTs go from 142 to 594 renames/s, and mean latency falls
from 56 ms to 13 ms.  Ten tasks each moving 1000 files
between directories spread over the MDTs go from 124 to
773 renames/s.

Patch Set 1:

Found in review: a lost linkEA update between two renames of a hard-linked file. A cross-MDT rename of one link holds LOOKUP in the source parent's namespace and XATTR on the file's MDT; a rename replacing another link on the file's MDT holds LOOKUP|UPDATE. The bits don't conflict, and mdd_rename reads the linkEA before mdd_write_lock and writes that buffer back without rereading it (mdd_dir.c:3739, :3806), so one update can be lost.

This predates the patch: on master the replacing rename is local and takes no BFL, and unlink of another link locks the file with the same LOOKUP|UPDATE (mdt_reint.c:1420). The fix is the same in both places, adding XATTR to the victim's lock in rename and in unlink, and is better done as a separate change.
