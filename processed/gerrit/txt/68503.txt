LU-17000 lnet: fix inconsistent NULL handling

lnet_compare_gw_lpnis() and lnet_compare_routes() test both arguments
for NULL and then dereference both unconditionally, so a call with two
NULL arguments would crash.  Their only caller,
lnet_find_route_locked(), always passes a valid first argument - the
route being examined and the peer NI it has just checked.  Its second
argument is NULL until the first route is selected, and only for
lnet_compare_routes(): lnet_compare_gw_lpnis() is reached only when
lnet_compare_routes() returned 0, which means best_route is not NULL,
and best_gw_ni is assigned in the same statement group as best_route.
The caller already relies on that by reading best_route->lr_seq right
there.  Keep the NULL test lnet_compare_routes() needs, drop the three
dead ones, and state both contracts in the comments.

lnet_ni_add_interface() computes strlen(iface) in the initialiser of
iface_len, before the !iface test that follows.  Compute the length
once the arguments have been validated.

Reported by smatch as "we previously assumed 'lpni1'/'lpni2'/'r1'
could be null" and "variable dereferenced before check 'iface'".
