--- Commit Message ---
LU-20271 ptlrpc: clear rq_repdata in sptlrpc_cli_free_repbuf

For replayable requests like open/mcreate, the reply buffer might be
freed early while the request is still in the replay list.

When sptlrpc_cli_free_repbuf() is called, it clears rq_repmsg but
leaves rq_repdata and rq_repdata_len unchanged. If this request is
later replayed, ptl_send_rpc() hits an LBUG because it asserts that
rq_repdata must be NULL if rq_repbuf is NULL.

Clear rq_repdata and rq_repdata_len in sptlrpc_cli_free_repbuf() to
fix this.

Experimental feature testing in progress, please pay attention to the comments

The two-line fix looks correct: rq_repdata points into rq_repbuf (sptlrpc_cli_unwrap_reply() sets it to rq_repbuf + rq_reply_off), so after the policy free_repbuf() releases rq_repbuf it is a dangling pointer. Clearing it in the common wrapper covers the null and plain policies (gss_free_repbuf() already did this) and prevents the LASSERT(rq_repdata == NULL) in ptl_send_rpc() on resend/replay. It also protects the reply-truncated resend path in after_reply() (ptlrpc/client.c), which frees the repbuf and resends without clearing rq_repdata locally.

This fixes an LBUG, so it would be good to add a Fixes: tag. The early-free-while-still-replayable scenario in the message was introduced by c8e3992acf30 ("LU-9514 ptlrpc: free reply buffer earlier for open RPC"); please confirm and add the appropriate Fixes: line.

Since this is a crash fix, is a regression test practical (e.g. exercising open/mcreate replay, or reply truncation + resend, under a fault injection) so it fails before and passes after?

Minor: with this change, the manual rq_repdata = NULL clears in __ptlrpc_req_put() and mdc_reset_acl_req() become redundant. Those two sites also assign rq_reqdata_len = 0 where they appear to mean rq_repdata_len; if the patch is refreshed, consider dropping the now-redundant clears (and that stray assignment).
