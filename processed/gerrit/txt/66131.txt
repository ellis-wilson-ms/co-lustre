LU-19900 lov: DIO+APPEND corruption on PFL extent boundaries

An O_DIRECT|O_APPEND write which crosses a PFL component or
stripe boundary lands entirely in the stripe the append started
in, so the data is written at the wrong offset and the bytes
past the component end are not counted in the file size.

Direct IO submits a whole batch of pages to the sub-object of
its first page, so it must never span more than one stripe.
lov_io_rw_iter_init() trims the IO to the next stripe boundary
for that reason, but the append branch returns before it does,
because the lock range for append has to cover the whole
instantiated layout rather than just the written extent.

Trim direct IO appends as well, and let the IO loop continue
into the next stripe or component.  The trim is computed from
the position sampled before the lock is taken, so the size
check in the write start now restarts the IO whenever that
position has moved, in either direction, and ends the loop
when part of the write has already been done.  A crossing
append no longer completes under a single lock, so an appender
on another client can land between its halves.

Add sanity-pfl_101 which reproduces the problem without the fix.

Patch Set 2:

Superseded by https://review.whamcloud.com/69187 ("LU-19900 lov: split DIO appends at stripe boundaries").  Rather than trimming the append in lov_io_rw_iter_init() and dropping the lock between the halves (with the restart needed in vvp_io_write_start()), it limits each DIO page array of an append to one stripe chunk before the pages are pinned, so the whole append stays in one cl_io_loop() iteration under one lock.  It also resets the lov DIO stripe cache per page array (what the PS1 lov_page.c hunk was aiming at).  sanity-pfl_101 from this patch is included there as sanity-pfl_300, thanks Justin/Sergey.
