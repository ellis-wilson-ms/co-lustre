LU-19921 mgc: change sec flavor for local mount

Improve the MGC sptlrpc config log processing to support security
flavor changes across client remounts in local mount environments.

Previously, if a config_llog_data (cld) structure already existed
for the sptlrpc log, mgc_process_config() would skip re-processing
the sptlrpc log on subsequent mounts.

In single-node test environments (such as llmount.sh), the MGC device
is shared between the client and server and persists across client
unmount/remount cycles. Because the cld and its associated LDLM lock
handle (cld_lockh) are preserved in memory, changes to the SPTLRPC
security rules on the MGS would not be re-evaluated when the client
was remounted.

This update explicitly calls mgc_process_log(obd, cld->cld_sptlrpc)
for every mount. Before acquiring cld->cld_lock in mgc_process_log(),
any previously cached lock (cld_lockh) is detached and cancelled via
mgc_cld_detach_lock(). Cancelling old locks prior to re-enqueueing
ensures that stale MGC locks do not remain as orphans across client
remounts, while avoiding recursive locking on cld->cld_lock when the
cancel callback invokes mgc_blocking_ast() -> mgc_requeue_add().

In test_901, we accept [4x, 5x] locks because the sptlrpc log adds a
5th lock per mount, but persistent parameter updates (set_param -P)
during test setup can revoke the params lock, leaving either 4 or 5
locks per mount. Additionally, test_901 samples the baseline lock
count after one umount/mount cycle rather than on initial mount.
This establishes a steady-state baseline after initial MGC lock
acquisition and verifies that subsequent umount/remount cycles do
not leak any MGC locks.

Additionally, remove mutex_lock(&cld->cld_lock) from mgc_requeue_add()
to prevent a non-recursive mutex deadlock when LDLM blocking or cancel
ASTs (mgc_blocking_ast -> mgc_requeue_add) are triggered concurrently
while mgc_process_log() is holding cld->cld_lock during mgc_enqueue().
cld->cld_lostlock and rq_state are fully protected by
config_list_lock.
