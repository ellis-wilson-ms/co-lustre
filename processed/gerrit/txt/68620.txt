LU-19895 clio: use large folios for unaligned DIO

The unaligned DIO bounce buffer was filled from the order 0
pool, one page and one cl_page per PAGE_SIZE, so it never
benefited from the multi-order folio extents the aligned path
now builds.  It matters more than the aligned case in practice:
the client allocates this buffer itself, so no THP backed user
buffer is needed, and hybrid IO routes ordinary buffered writes
into exactly this path.

Fill the buffer from the compound page pools: the bulk from the
largest order which fits (within one brw_ext), the remainder
from order 0.  Per-chunk bookkeeping falls from one
cl_page/oap/brw_ext per PAGE_SIZE to one per folio extent -
16384 entries to ~320 for a 64MiB chunk.  The high order is
tried once; a binary decomposition would reach ~73 entries but
costs an all-or-nothing contiguous allocation per order, on
pools this node may otherwise never use.

ll_free_dio_buffer() follows the piecewise fill: it walks the
array in runs of a common order, takes that order from cdp_npgs
rather than folio_order(), stops at the first NULL so a partly
filled array is never handed back to the pool, and clears
cdp_page_count.

A zero length request fails with -EINVAL rather than building an
empty cdp.  Encrypted files keep order 0 entries
(cdp_no_coalesce).

The copy loop is reworked with the entries.  A write flushes
the dcache once per entry rather than once per copy; a short
write copy re-faults the user pages and retries; the
short_copies budget resets each pass, so it bounds a pass
rather than the whole sub-DIO; the refault covers what the next
pass will ask for, since asking for only what this one had left
lets the retry come up short again and spend the budget while
making progress; and a single write copy is
bounded because it runs under kmap_atomic() with pagefaults
disabled -- at 64KiB where copy_folio_from_iter_atomic()
exists and highmem is off, at the page boundary otherwise.

The entry order is clamped to cdp_max_ext_pgs as well, so a
buffer entry cannot exceed the target's pages-per-RPC any more
than a user buffer entry can.

sanity 119v covers the dio_large_folios gate, which needs this
buffer to observe, and 119w checks the pages-per-RPC clamp from
this side: with max_pages_per_rpc tuned to half of
CDP_EXT_MAX_PAGES, an unaligned DIO must not put a wider bucket
in rpc_stats.

sanity test_56ab ("lfs find --blocks") on patch set 15, session

The test writes 8 KiB at 16 MiB, 4 KiB at 16 MiB and 2 MiB at 16 MiB
into three files and expects exactly one of them to report more than
