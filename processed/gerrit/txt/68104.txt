LU-20607 llite: repair the mmap user buffer lock set

vvp_mmap_locks() adds a lock for every mmapped user buffer of a read
or write, so that faulting such a buffer during the copy does not
enqueue a conflicting lock underneath an io that already holds one.
Three defects leave that lock set empty or unusable:

our_vma() reuses the loop-continue condition of the old find_vma()
walk as the loop-break condition of the vma_iterator walk, so it
returns NULL for every address inside a Lustre MAP_SHARED mapping.

vvp_mmap_locks() only accepts ITER_IOVEC and ITER_KVEC iterators.
A single buffer read() or write() is an ITER_UBUF iterator on kernels
that have it, and is skipped before any vma is looked at.

cl_io_lock_alloc_add() returns 1 when the descriptor is already
covered by the lock set. vvp_mmap_locks() passes that 1 back to
vvp_io_rw_lock(), which then skips vvp_io_one_lock(), so the io runs
without a lock on the data it reads and transfers nothing.

readv() into a MAP_SHARED mapping of the same file therefore waits
forever in cl_sync_io_wait() when the OSC locks are dropped between
the mmap store and the read.

mmap_sanity tst5 covers this case and never caught it, because
cancel_lru_locks() writes "clear" from a child process and reaps it
with WNOHANG: it returns while the locks are still there. Write the
parameter directly instead, and add tst13, the readv()/writev() form
of tst5, which also turns off fast read so that the read reaches the
io engine.
