--- Commit Message ---
LU-20426 lnet: control per-operation latency stats

Per-operation latency capture has no runtime control, so an operator
who wants the data path free of it, or who wants to clear and
re-measure from a known point, has no way to turn it off.

Add the lnet_latency_stats_enabled module parameter, which gates the
latency accumulators. The global counters and the per-NI element
statistics are unaffected. A toggle that lands mid-flight yields a
negative delta, which lnet_record_latency() already discards.

Expose it as the "latency_stats" tunable, so it is settable with
"lnetctl set latency_stats 0|1", readable through "lnetctl global
show" and /sys/module/lnet/parameters, preset at modprobe time and
round-tripped by "lnetctl export" and "lnetctl import".

Add a sanity-lnet test that confirms pinging adds no latency samples
while disabled and resumes adding them once enabled. The setting
outlives reinit_dlc(), so the existing test now enables capture
itself rather than relying on the default.

AI code review results below, please doublecheck

Some concerns, see inline comments. The data-path gating itself looks complete and safe: every site that accumulates a latency sample is covered, and a toggle that lands mid-flight can only produce a negative delta, which lnet_record_latency() already discards via its `ns <= 0` guard.

The bigger question is plumbing. Every other LNet on/off knob (response_tracking, discovery, drop_asym_route, routing) is a module parameter plus an `lnetctl set <name> 0|1` verb, which means it is readable in /sys/module/lnet/parameters/, reported by `lnetctl global show`, and round-tripped by `lnetctl export`/`import`. This one is a new `lnetctl stats latency on|off` verb with no readback path at all, so an operator has no way to tell whether capture is currently on, and the setting is silently lost on module reload. Was following the existing tunable pattern considered?
