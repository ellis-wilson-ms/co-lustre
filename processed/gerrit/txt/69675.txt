LU-19344 llite: restore i_size gate and read confinement

240cad9a0a ("LU-19344 llite: set read size correctly") replaced the
read confinement from 4468f6c9d9 ("LU-16025 llite: adjust read count
as file got truncated") with an unconditional

        i_size_write(inode, kms);

in vvp_prep_size(), and dropped file_read_confine_iter().  Both
halves of that change are wrong.

kms is the "known minimum size", not the file size.  It is valid
only while extent locks are held; it is raised on lock grant and on
writes, and it is lowered by ldlm_extent_shift_kms() when the
highest extent lock is cancelled.  A lock is cancelled for reasons
that have nothing to do with a truncate -- a conflicting lock from
another client, LRU reclaim, eviction -- so a decrease in kms does
not mean the file shrank.  Assigning kms to i_size on every read
therefore makes the client under-report the file size and turns
reads inside the real file into spurious short reads and EOF.  The
code had only raised i_size since b=11081 for this reason.

It also did not fix the case it was aimed at.  osc_lock_lvb_update()
only raises kms on lock grant (size >= loi_kms), so after a truncate
by another node kms can stay stale-high.  With the confinement gone,
reads then return stale data past the new EOF, which is the
LU-16025 bug, and the cache read path, which uses i_size to decide
EOF, was left with no EOF check at all.

Restore the confinement and keep its cost down, which was the point
of 240cad9a0a:

 - vvp_prep_size() only raises i_size to kms again.

 - file_read_confine_iter() is back on the read path, but no longer
   wraps the attribute lookup in cl_io_init(CIT_MISC)/cl_io_fini().
   For CIT_MISC that only adds ll_layout_refresh() and the LOV
   layout lock (lov_conf_freeze()) to a per-read hot path, while
   cl_object_attr_get() does not need an initialized cl_io --
   ll_merge_attr_nolock() and ll_readahead_file_kms() call it the
   same way.

 - it returns early when the layout is not known, which is also when
   the cache read path is not used.

 - the read is still run when it starts at or beyond EOF, so that
   its side effects, in particular the atime update, are preserved;
   the data it returned is discarded afterwards.

 - cat_kms is initialised to 0 before the lookup, because the empty
   and released layouts do not set it and the cl_attr is the
   thread's shared buffer.

sanity/251b is restored.  240cad9a0a removed it by calling its
assumption wrong, but with the confinement back the read is
correctly confined to the real EOF and the offset is not advanced.
