LU-20611 lfs: share find's predicate parsing

Move lfs find's option table, the loop that reads it and the helpers
it calls into lfs_find_parse.c. The file is built into lfs, like
callvpe.c. Nothing is exported from the library and no ABI changes.

The helpers move unchanged, except that the continuation line of the
set_time() prototype is re-indented. The loop moves with only these
differences:
- one call to llapi_lov_string_pattern(), under case 'L', is joined
  onto one line
- every "goto err" becomes "goto out"
- the three out-parameters are set before the loop, and pathstart and
  pathend are written back after it
- prev_optind starts from 1 when optind is 0 (see below)

Note on the new interface: -1 means different things in @pathstartp
and @pathendp. In @pathstartp it means "no path". In @pathendp it
means "no option after the paths", and the caller must read it as
argc. This is the normal case for "lfs find -type f /mnt/a /mnt/b". A
caller that takes it literally walks only the first path. The header
says this.

Some failures in the loop return without setting ret, so lfs find has
always exited 0 after a bad --comp-flags. The parser reports this
through a stopped flag. The behaviour is kept, not fixed.

lfs_find_parse_init() prepares the structure. It sets fp_max_depth and
fp_time_margin, which must not be 0, keeps fp_min_depth and fp_quiet
as lfs_find() set them, and zeroes the rest. lfs_find_parse_fini()
frees the four find_param fields that a parse can allocate.

The interactive shell sets optind to 0 before it calls a command.
getopt() treats 0 as "start again" and scans from argv[1], but
prev_optind was taken from that 0, so pathstart was 0 and
"lfs> find /mnt/lustre -type f" searched "find" first and reported it
missing. The bug is in upstream lfs_find() too; it is fixed here
because the new header promises the correct value.
