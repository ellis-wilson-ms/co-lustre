LU-20409 lnet: Auto-bind NIs to local NUMA node by default

LNet now automatically binds each NI whose CPTs were not explicitly
configured to the CPTs local to the NUMA node of its underlying
hardware device. This prevents cross-NUMA performance degradation.

Each LND records the CPT of its device in ni_dev_cpt during startup
(e.g. derived from dev_to_node()), so the binding reuses that value
rather than re-resolving the device: NIs are bound to every CPT
sharing a NUMA node with ni_dev_cpt. LNDs without a backing device
leave ni_dev_cpt as CFS_CPT_ANY and the NI is left on all CPTs.

The device's NUMA node is only known once the LND has opened the
device during startup, but the LND also sizes its per-CPT scheduler
threads and memory pools against ni_cpts during that same startup,
and ni_cpts must not be mutated once the NI is live on the receive
path (lnet_nid2cpt() reads it locklessly). So each LND calls the new
lnet_ni_set_default_cpts() helper itself, after it has determined
ni_dev_cpt and before it allocates those per-CPT resources. This
keeps the LND's footprint matched to the bound CPT set and finalizes
ni_cpts before the NI is published. The helper self-gates on NIs
with default CPTs, so lnet_startup_lndni() calls it only as a
fallback for LNDs without a backing device (e.g. the loopback NI).

NI allocation defers the net's CPT set for default NIs until the
helper runs. When the device's NUMA node already covers all CPTs the
NI is left on the ni_cpts == NULL fast path. NIs with explicitly
configured CPTs are unaffected.

ni_dev_cpt is now initialized to CFS_CPT_ANY in lnet_ni_alloc_common()
so NIs whose LND never sets it are correctly treated as "unknown".

Running lnet_selftest without any configs on two 4-NUMA client nodes
with 200Gbps NIC over tcp.
