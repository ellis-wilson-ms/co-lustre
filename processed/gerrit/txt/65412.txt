LU-20090 nrs: add allowed dynamic classification types for TBF

Add an "allow=" key to the TBF policy start command. The key names a
classification type that a dynamic rule can use. A rule starts only
when its type equals an allowed type. A "nid" rule therefore needs
"allow=nid", even under "allow=nid+opcode".

    nrs_policies="tbf nid classify=dynamic allow=nid allow=nid+opcode"
    lctl get_param -n ost.OSS.ost_io.nrs_tbf_allowed_types

The head sorts the allowed types in descending order of granularity,
for the class bucket lookup of the next patch.

nrs_tbf_parse_cmd() now returns the error code of the parser, not
-EINVAL for every error.

Add sanityn/test_77tc.

Patch Set 3: Code-Review-1

Mostly looks good. The allowed-types machinery is straightforward and the legacy path (nac_count == 0) preserves backwards compatibility. A few concrete issues, mostly in the test and a couple of code smells:

1. test_77tc has a typo at sanityn.sh:5691: do_node (singular) is called with $osts, which can be a multi-node list from osts_nodes(). do_node treats $1 as a single hostname, so on multi-OST configurations this either fails or silently runs on the wrong place. Should be do_nodes.

2. struct nrs_allowed_type::nat_nr_rules is added but never read or written anywhere in this patch. If the intent is for the next patch in the series, drop it here; if it's intended for rule add/remove bookkeeping right now, the inc/dec is missing.

3. The new allow=foo handling in nrs_tbf_parse_value_pair is correct, but nrs_tbf_parse_value_pair() uses the RETURN() macro without an ENTRY; declaration. Same in the new code path in nrs_tbf_rule_start(). Either add ENTRY; to match the rest of the file's convention, or revert to plain return for these functions; the file is otherwise consistent about pairing them.

4. ptlrpc_lprocfs_nrs_allowed_types_seq_show treats -ENODEV as benign for the regular NRS head but not for the HP head, and the comments are interleaved with code in a way that obscures the control flow.

5. Minor: typos in kernel-doc comments (granulaity, Calcuate, enqual, optioinal/possiibly elsewhere in nrs_tbf_start are pre-existing — only flag the ones you introduce). NRS_ALLOWED_TYPES_MAX=16 is below the theoretical max of 63 combinations of the 6 valid fields; document why 16 is enough or bump it.

Commit message is clear and follows the wiki conventions.
