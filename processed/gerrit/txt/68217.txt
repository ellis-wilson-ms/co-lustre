LU-17000 obdclass: destroy LRU counter on lu_site_init() error

lu_site_init() initialises ls_lru_len_counter first and then has three
more ways to fail -- rhashtable_init(), the ls_bkts allocation and
lprocfs_stats_alloc() -- none of which destroys it again.  No caller
compensates, because a failed lu_site_init() is not paired with
lu_site_fini(): lov_device_alloc() unwinds to OBD_FREE_PTR(ld) and
vvp_device_alloc() to OBD_FREE_PTR(site), both of which free the
lu_site with the counter still live.

That is not only the per-cpu area.  With CONFIG_HOTPLUG_CPU,
percpu_counter_init() links the counter onto the global percpu_counters
list, so the freed lu_site leaves a list entry behind and the next CPU
hotplug event walks it.

Give the function one label per acquired resource, which also folds the
two open-coded unwinds into that chain.
